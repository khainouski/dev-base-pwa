### Q1. Какие NoSQL в продакшене (документ, wide-column, key-value, граф, time-series)? Под какую нагрузку?

**A:**
**Семейства:** **документные** (MongoDB, Couchbase) — вложенные документы, гибкая схема. **Широкая колонка** (Cassandra, ScyllaDB) — дизайн вокруг partition key. **Key-value** (Redis, DynamoDB) — кеш, сессии, низкая задержка. **Граф** (Neo4j) — обход связей. **Time-series** — метрики, события.

**Сильный ответ:** называет **хотя бы одну** систему с **нагрузкой** (чтение/запись, объём, SLA по задержке). Объясняет, **почему** SQL был плох (масштаб, гибкость схемы, паттерн доступа).

**Слабый ответ:** «юзали Mongo» без нагрузки; или все NoSQL считает взаимозаменяемыми.

**Мой ответ (по типам NoSQL):**

**1. Document Database** (MongoDB, Couchbase)
- *Когда использовать:*
  - **Каталог товаров** — товары разных категорий имеют разные характеристики, поэтому гибкая схема удобнее множества таблиц.
  - **CMS** — страницы и статьи могут иметь разную структуру, а новые поля добавляются без миграций.
  - **Пользовательские настройки** — у разных пользователей может быть разный набор настроек, который удобно хранить одним JSON-документом.
- *Почему:* лучший выбор, когда объекты имеют разную структуру или схема данных часто меняется.
- *Под какую нагрузку:* смешанное чтение/запись со смещением в сторону read-heavy; документ читается и обновляется почти всегда целиком, одним запросом; объём — от тысяч до десятков миллионов документов; задержка чтения важна, но не так критична, как у key-value.
- *Как хранится (пример):* данные — это JSON/BSON-документы в коллекции, без единой схемы для всех документов:
  ```text
  коллекция products:
  { "_id": "prod_101", "name": "iPhone 15", "specs": { "storage_gb": 256 } }
  { "_id": "prod_205", "name": "Футболка", "specs": { "size": "L", "color": "blue" } }
  ```
  Связанные данные обычно **вкладывают**, а не JOIN'ят — весь заказ с товарами читается одним запросом:
  ```json
  { "_id": "order_555", "items": [{ "product_id": "prod_101", "qty": 1 }] }
  ```
- *Минусы вложенных данных:*
  - Дублирование — один и тот же объект копируется в разные документы.
  - При изменении данных нужно обновлять все копии, а не одну запись.
  - Лимит размера документа в MongoDB — 16 МБ.
  - Растущий вложенный массив вызывает дорогую перезапись всего документа.
  - Сложно и дорого делать запросы/агрегации по вложенным элементам отдельно.
  - Нет ссылочной целостности (foreign key) — БД не проверяет, что вложенный ID существует.

**2. Key-Value Database** (Redis, DynamoDB)
- *Когда использовать:*
  - **Кеш** — нужен максимально быстрый доступ по ключу.
  - **Пользовательские сессии и JWT** — всегда известен session_id или token.
  - **Rate Limiting и счётчики** — нужны быстрые атомарные операции.
- *Почему:* лучший выбор, когда данные всегда ищутся по ключу и важна минимальная задержка.
- *Под какую нагрузку:* и чтение, и запись одинаково интенсивны, очень высокая частота операций (тысячи–десятки тысяч RPS); доступ строго точечный по ключу; задержка критична — счёт идёт на единицы миллисекунд.
- *Где хранится:* Redis — в памяти (+ опциональная персистентность на диск); DynamoDB — на SSD, память только как опциональный кеш (DAX).

**3. Wide-Column Database** (Cassandra, ScyllaDB)
- *Когда использовать:*
  - **Логи** — постоянный поток записей с высокой скоростью.
  - **Телеметрия и IoT** — миллионы событий и показаний датчиков.
  - **История действий пользователей** — большое количество событий, читаемых по UserID.
- *Почему:* лучший выбор для огромных объёмов данных и очень высокой скорости записи.
- *Когда использовать Cassandra в Go-микросервисах:* сервис подходит, если он:
  - принимает очень большой поток записей;
  - хранит десятки терабайт данных;
  - должен горизонтально масштабироваться;
  - должен продолжать работу при отказе отдельных узлов;
  - выполняет простые заранее известные запросы по ключу;
  - допускает eventual consistency.
- *Под какую нагрузку:* write-heavy — постоянный и очень большой поток записей (тысячи–десятки тысяч операций в секунду); объём данных — терабайты и выше; запросы почти всегда идут по partition key; согласованность обычно eventual.
- *Как хранится (пример):* строка — это ключ + динамический набор колонок, у разных строк набор разный:
  ```text
  sensor_42: { 10:00:00 → 22.5, 10:00:01 → 22.6, ... }
  sensor_43: { 10:00:00 → 18.1 }   ← у другой строки меньше "колонок"
  ```
  ```sql
  CREATE TABLE sensor_readings (
      sensor_id text,
      reading_time timestamp,
      temperature double,
      PRIMARY KEY (sensor_id, reading_time)
  );
  ```
  `sensor_id` — **partition key** (на каком узле кластера лежат данные), `reading_time` — **clustering key** (порядок хранения внутри партиции). Запись быстрая, потому что идёт последовательным дописыванием (commit log → memtable → SSTable), без чтения диска перед записью.
- *JOIN нет:* в Cassandra `JOIN` не существует вообще. Значит, если нужно доставать одни и те же данные по-разному (например, "показания датчика по ID" и "показания датчика по локации"), одним `JOIN`-запросом не обойтись — приходится создавать **отдельную таблицу под каждый паттерн запроса**, дублируя данные между ними.

**4. Graph Database** (Neo4j, Amazon Neptune)
- *Когда использовать:*
  - **Социальные сети** — друзья, подписчики, общие знакомые.
  - **Рекомендательные системы** — поиск связанных товаров или пользователей.
  - **Fraud Detection** — поиск цепочек связанных аккаунтов и транзакций.
- *Почему:* лучший выбор, когда главная задача — быстро обходить связи между объектами.
- *Под какую нагрузку:* read-heavy, сложные многошаговые обходы связей (несколько «прыжков» по графу); объём умеренный (миллионы узлов и рёбер); задержка важна для интерактивных сценариев — рекомендации, поиск мошенничества в реальном времени.
- *Как хранится (index-free adjacency, на примере Neo4j):*
  1. **Node store** — записи узлов, каждая фиксированного размера. Запись узла содержит: указатель на первую связь этого узла, указатель на первое свойство.
  2. **Relationship store** — записи связей, тоже фиксированного размера. Каждая запись содержит: ID узла-источника, ID узла-назначения, тип связи, и — самое важное — указатели на предыдущую/следующую связь для каждого из двух узлов, которые она соединяет.
  3. **Property store** — отдельно свойства (имена, значения), потому что у разных узлов их разное количество — не фиксированный размер, как у node/relationship записей.

  Фиксированный размер записи → адрес вычисляется напрямую (`ID × размер записи`), без индекса. Переход к соседям узла — чтение по указателю, `O(1)`, а не поиск. Поэтому многошаговые обходы не дорожают с глубиной — в отличие от SQL, где каждый следующий `JOIN` дороже предыдущего.

**5. Time-Series Database** (InfluxDB, VictoriaMetrics)
- *Когда использовать:*
  - **Мониторинг** — CPU, RAM, latency и другие метрики.
  - **IoT** — показания датчиков с временной меткой.
  - **Финансовые котировки** — изменение цен во времени.
- *Почему:* лучший выбор для хранения и анализа данных, где каждая запись привязана ко времени.
- *Под какую нагрузку:* write-heavy, append-only с очень высокой частотой вставок (метрики поступают непрерывно, раз в секунду и чаще); чтение — в основном агрегации по диапазону времени; объём растёт линейно, поэтому нужны TTL или downsampling.

### Q2. Как моделировали иначе, чем в реляционной схеме? Примеры денормализации или вложения.

**A:**
**Идея:** в NoSQL часто меняют **JOIN** на **предсобранные документы**, дублирование или сборку в приложении. **Вложение** (массив поддокументов) vs **ссылка** (id) — ключевой выбор.

**Сильный ответ:** конкретный пример (пользователь + заказы в одном документе vs отдельные коллекции). Обсуждает **аномалии обновления** при дублировании. Миграцию при смене паттерна доступа.

**Слабый ответ:** «без JOIN» как единственный плюс без компромиссов моделирования.

**Мой ответ:**
В NoSQL модель данных строится вокруг паттернов чтения, а не вокруг нормализации. Вместо хранения данных в отдельных таблицах с последующими JOIN часто используют embedding (вложенные документы) или денормализацию, чтобы получать все необходимые данные одним запросом.
Например, в сервисе каталога товаров каждая карточка товара хранилась как единый документ:

```json
{
  "id": 101,
  "name": "iPhone 16",
  "price": 1200,
  "images": ["...", "..."],
  "attributes": {
    "memory": "256 GB",
    "color": "Black"
  },
  "variants": ["..."]
}
```

Такой документ полностью соответствовал паттерну доступа: клиент почти всегда запрашивал карточку товара целиком, поэтому один запрос к MongoDB был эффективнее, чем чтение нескольких таблиц и выполнение JOIN.
Если же связанные данные часто изменяются и используются многими сервисами, я предпочитаю хранить только ссылку. Например, вместо вложенного продавца сохранять только sellerId, потому что профиль продавца — самостоятельная сущность со своим жизненным циклом.
Денормализация — это всегда компромисс. Она ускоряет чтение, но приводит к дублированию данных. Поэтому я дублирую только те данные, которые редко меняются или должны сохраниться как снимок состояния. Если со временем паттерны доступа меняются, модель тоже приходится пересматривать: переносить данные из ссылок во вложенные документы или наоборот и выполнять миграцию.

### Q3. Как обрабатывали eventual consistency в логике приложения? Явные паттерны read-your-writes?

**A:**
**Идея:** многие NoSQL дают **eventual** или настраиваемую согласованность (лаг репликации). **Read-your-writes** может требовать strong read, чтение с первичной или проверку версии.

**Сильный ответ:** описывает наблюдаемый лаг, поведение UI («изменение может появиться с задержкой»), **идемпотентные ретраи**. Знает **кворум** / R+W > N где уместно (например Cassandra).

**Слабый ответ:** предполагает мгновенную глобальную консистентность; «БД сама всё решает» без логики в приложении.

**Мой ответ:**
Многие NoSQL-системы обеспечивают eventual consistency (согласованность с задержкой). Это означает, что после записи данные могут стать видимыми на всех репликах не сразу из-за репликации или асинхронной обработки. Поэтому приложение не должно предполагать, что сразу после записи любое чтение вернёт обновлённые данные.

Если пользователю важно сразу увидеть результат своей операции (read-your-writes — гарантия, что пользователь после своей записи прочитает именно обновлённые данные), использую один из нескольких подходов: выполняю strong/consistent read (строго согласованное чтение), при котором чтение гарантированно возвращает последнюю подтверждённую запись, или читаю с primary (основной реплики), где запись уже зафиксирована и ещё не зависит от репликации. В некоторых случаях вместо повторного чтения сразу возвращаю обновлённый объект из операции Create или Update.

Если данные распространяются асинхронно, например через события, UI должен учитывать возможную задержку. Пользователь видит статус «Processing» или «Updating…», а изменения появляются после завершения репликации или обработки события. Это лучше, чем создавать ложное ощущение мгновенной консистентности.

Все операции, которые могут быть повторены из-за временных ошибок или задержек, делаю идемпотентными, то есть повторное выполнение одной и той же операции не изменяет результат и не создаёт дубликатов. Это позволяет безопасно выполнять ретраи при временных сбоях.

Если база поддерживает настраиваемую согласованность, например Cassandra, для критичных операций можно использовать quorum (кворум) — запись считается успешной только после подтверждения большинством реплик, а чтение выполняется также с большинства реплик. При настройке R + W > N (где R — число реплик, участвующих в чтении, W — число реплик, подтверждающих запись, N — общее число реплик) гарантируется, что чтение пересечётся хотя бы с одной репликой, содержащей последнюю запись. Это повышает консистентность, но увеличивает задержку и снижает доступность.
Главное — не рассчитывать, что база данных сама решит все проблемы согласованности. Логика приложения должна учитывать eventual consistency и корректно обрабатывать временное расхождение данных.

### Q4. Вторичные индексы, TTL, compaction — что доставляло боль в эксплуатации?

**A:**
**Зачем:** в проде боль реальна — **индексы тормозят запись**; **TTL** даёт неожиданные удаления; **compaction** даёт пики латентности (LSM).

**Сильный ответ:** мониторинг (латентность, диск), настройка (окна compaction), инцидент, где важны индекс или TTL. Осознание **горячих партиций**.

**Слабый ответ:** нет операционной истории — вероятен только dev-опыт.

**Мой ответ:**
Сначала кратко о каждом механизме:

- **Secondary indexes** (вторичные индексы) — позволяют быстро искать данные не только по Primary Key, но требуют обновления индекса при каждой записи, поэтому увеличивают стоимость операций записи.
- **TTL** (Time-To-Live) — автоматически удаляет запись через заданное время. Часто используется для кэша, сессий и временных данных.
- **Compaction** — фоновый процесс в LSM-базах (например, Cassandra, ScyllaDB, RocksDB), который объединяет SSTables, удаляет устаревшие версии данных и освобождает место на диске.

**Partition** — это группа данных, которая определяется partition key и хранится на определённом узле кластера. Например, если user_id — это partition key, то все записи одного пользователя будут храниться в одной партиции. Благодаря этому база быстро находит нужные данные и масштабируется горизонтально. При проектировании важно выбрать такой partition key, чтобы данные и нагрузка распределялись равномерно. Если слишком много запросов попадает в одну партицию, возникает hot partition, которая становится узким местом системы.

С точки зрения эксплуатации основные проблемы такие:

- **Secondary indexes** могут значительно замедлять запись, особенно при высокой нагрузке. Поэтому в NoSQL обычно стараются проектировать модель данных под основные запросы, а не создавать большое количество вторичных индексов.
- **TTL** удобен, но неправильная настройка может привести к неожиданному удалению данных или массовому истечению большого количества записей одновременно, что создаёт дополнительную нагрузку на систему.
- **Compaction** потребляет CPU и диск, поэтому во время его выполнения могут расти задержки чтения и записи. Обычно мониторят латентность, загрузку дисков и состояние compaction, а при необходимости настраивают стратегию или окна выполнения compaction, чтобы уменьшить влияние на пользователей.

Также важно следить за горячими партициями (**hot partitions**) — ситуацией, когда большая часть запросов приходится на один partition key. В этом случае именно одна партиция становится узким местом, даже если остальные узлы кластера практически не загружены.

Из метрик в первую очередь я бы мониторил латентность чтения и записи, загрузку дисковой подсистемы, количество и длительность compaction, а также распределение нагрузки по partition key, чтобы вовремя обнаруживать горячие партиции и деградацию производительности.

### Q5. Когда вы не выбрали бы знакомый вам NoSQL?

**A:**
**Сильный ответ:** сложные **ad-hoc запросы** под SQL; жёсткий **ACID** по многим строкам; маленький объём, когда кластер не окупается; команда без навыков эксплуатации.

**Слабый ответ:** «NoSQL всегда быстрее» — зависит от нагрузки.

**Мой ответ:**
Я не считаю, что NoSQL всегда лучше SQL — выбор зависит от требований системы. Я бы не выбрал NoSQL, если:

- нужны сложные ad-hoc SQL-запросы, аналитика, множество JOIN и возможность быстро строить новые запросы без изменения модели данных;
- требуются строгие ACID-транзакции между множеством строк или таблиц, например в финансовых или банковских системах;
- объём данных и нагрузка небольшие, поэтому распределённый кластер не окупается, а PostgreSQL или другая реляционная база будет проще и дешевле в эксплуатации;
- у команды нет опыта эксплуатации NoSQL, поскольку такие базы требуют понимания репликации, партиционирования, консистентности, мониторинга и других особенностей.

Для меня NoSQL — это инструмент для конкретных задач, а не замена реляционным базам. Если требования лучше закрывает SQL-база, я выберу её. Это обычно снижает сложность системы и стоимость её сопровождения.

### Q6. Горячие партиции / ключи: как находили и смягчали?

**A:**
**Идея:** один **partition key** получает непропорциональный трафик — throttling, перекос нагрузки, срыв SLA.

**Сильный ответ:** метрики (операции по партициям в облачных консолях), стратегии **перешардирования**, **salt** или случайный суффикс, кеш спереди. Признаёт ошибки дизайна ключа.

**Слабый ответ:** не слышал про hot partitions — красный флаг для опыта с Cassandra/Dynamo-стилем.

**Мой ответ:**
Hot partition возникает, когда слишком много запросов приходится на один partition key, из-за чего один узел кластера становится перегруженным, а остальные остаются недозагруженными. Это приводит к росту латентности, throttling и может нарушить SLA.

В первую очередь я бы искал проблему по метрикам: латентности чтения и записи, пропускной способности отдельных узлов, количеству операций по partition key и другим метрикам, которые доступны, например, в облачных консолях DynamoDB или средствах мониторинга Cassandra.

Если причина в неудачном выборе partition key, лучшее решение — перешардировать данные, то есть изменить схему ключа так, чтобы нагрузка распределялась равномернее. Если изменить ключ сразу нельзя, можно использовать salt (случайный префикс или суффикс), например вместо user:123 хранить данные как user:123:0…9, распределяя записи между несколькими партициями. Для часто читаемых данных также помогает кэш (например, Redis), который снижает нагрузку на базу.

Главный вывод — hot partition почти всегда говорит о неудачном дизайне partition key, поэтому при проектировании важно сразу учитывать ожидаемый профиль нагрузки и распределение запросов.

### Q7. Бэкап, восстановление, DR: что было автоматизировано?

**A:**
**Сильный ответ:** цели **RPO/RTO**, проверенные restore, кросс-регион репликация, runbook. Называет инструменты (снапшоты, vendor backup).

**Слабый ответ:** «инфра делает» без личной проверки восстановления.

**Мой ответ:**
Подход к резервному копированию всегда определяется целевыми RPO (Recovery Point Objective — максимально допустимая потеря данных) и RTO (Recovery Time Objective — максимально допустимое время восстановления).

Обычно автоматизируют создание резервных копий с помощью снапшотов (snapshots) или встроенных vendor backup-механизмов, а для критичных систем дополнительно используют кросс-региональную репликацию (cross-region replication), чтобы пережить отказ целого дата-центра.

Самое важное — регулярно проверять восстановление (restore). Бэкап считается рабочим только тогда, когда данные действительно можно восстановить в тестовой среде. Для этого обычно есть runbook — документ с пошаговой инструкцией по восстановлению и действиям во время аварии.

В моих проектах инфраструктурная команда отвечала за автоматизацию резервного копирования, но я считаю важным понимать RPO/RTO, знать, как выполняется восстановление, и не полагаться только на факт существования бэкапов без проверки restore.

### Q8. Какие драйверы/слои использовали? Пул соединений, таймауты из context?

**A:**
**Сильный ответ:** называет драйвер (например mongo-go-driver, go-redis), настройки **пула**, **context** на запросах, таймауты, **circuit breaker** где уместно.

**Слабый ответ:** нет понимания лимитов соединений и распространения контекста.

**Мой ответ:**
Выбор драйвера зависит от базы данных. Обычно использую официальные или наиболее распространённые библиотеки: pgx для PostgreSQL, go-redis для Redis, mongo-go-driver для MongoDB, gocql для Cassandra. Доступ к базе выношу в Repository (DAO) слой, чтобы бизнес-логика не зависела от конкретного драйвера.

*Что такое драйвер:* библиотека, которая "переводит" обычные Go-вызовы в сетевой протокол конкретной БД (BSON для MongoDB, RESP для Redis, свой бинарный протокол у Postgres) — сама открывает TCP-соединение, сериализует запрос, отправляет по сети, разбирает ответ обратно в Go-структуры. Плюс берёт на себя пул соединений, ретраи и балансировку между узлами кластера — самому это писать не нужно.

Все операции с базой выполняю через context.Context. Это позволяет передавать таймауты, дедлайны и отмену запроса по всей цепочке вызовов. Если HTTP-запрос отменился или истёк таймаут, запрос к базе также будет остановлен, и соединение быстрее вернётся в пул.

**Пул соединений — от чего зависит выбор параметров:**

| Параметр | Что делает |
|---|---|
| `MaxOpenConns` | Максимум соединений одновременно |
| `MaxIdleConns` | Сколько неактивных держать наготове (обычно = `MaxOpenConns`) |
| `ConnMaxLifetime` | Через сколько принудительно пересоздать соединение |
| `ConnMaxIdleTime` | Сколько может простаивать, прежде чем закроют |

Формула для `MaxOpenConns`: `max_connections БД ÷ число инстансов сервиса`, с запасом под другие сервисы и админ-доступ. Пример: `max_connections = 100`, 5 реплик сервиса → по 20 на реплику, не 100 на каждую (иначе `too many connections`).

Обычно ставят **10–25** на старте. Ориентир со стороны БД: `число ядер БД-сервера × 2` — больше не ускоряет, а только создаёт очередь внутри самой БД. Точное число подтверждают нагрузочным тестом и метрикой `db.Stats().WaitCount` (растёт → пул маловат).

**`max_connections` в Postgres:** по умолчанию `100`, это лимит на всю БД сразу (все сервисы + админы вместе). Нельзя бездумно поднимать — каждое соединение в Postgres это отдельный OS-процесс, ~5-10 МБ RAM. Правильное решение при нехватке — не поднимать лимит, а ставить **PgBouncer** перед БД: он держит тысячи клиентских соединений от сервисов, но мультиплексирует их через маленький стабильный пул реальных соединений к Postgres.

Для внешних сервисов или нестабильных зависимостей, где возможны длительные отказы, дополнительно использую Circuit Breaker, чтобы не создавать лавину бесполезных запросов и дать сервису время восстановиться. Circuit Breaker (предохранитель) — это паттерн отказоустойчивости, который временно прекращает отправлять запросы к сервису, если тот начал массово ошибаться.

### Q9. Опыт со change streams, курсорами или bulk-записью в масштабе?

**A:**
**Зачем:** шире CRUD — реактивные паттерны (**Mongo change streams**), пагинация (**курсор** vs offset), **bulk** для бэкфиллов.

**Сильный ответ:** хотя бы один паттерн с зачем (backpressure, память). Настройка размера батча.

**Слабый ответ:** только get/put по одному документу — может хватать для джуна.

**Мой ответ:**
Из этих паттернов мне ближе работа с курсорами и bulk-операциями.

Курсоры использовал для обработки больших выборок. Вместо того чтобы загружать все данные в память, данные читаются батчами, что позволяет контролировать потребление памяти и обрабатывать миллионы записей. Размер батча подбирается исходя из объёма данных и производительности системы.

Bulk-запись применяют для массовых вставок или обновлений, например при миграциях или backfill данных. Она значительно эффективнее тысяч отдельных операций, так как уменьшает количество сетевых запросов и повышает пропускную способность. При этом важно подобрать размер батча, чтобы не перегружать ни приложение, ни базу данных.

С MongoDB Change Streams я знаком теоретически. Они позволяют получать изменения в коллекциях в реальном времени и строить event-driven решения без постоянного polling. На практике использовать их мне не приходилось.

При работе с большими объёмами данных также важно учитывать backpressure — обработчик должен успевать обрабатывать поступающие данные. Если чтение происходит быстрее обработки, начинают расти очереди и потребление памяти, поэтому размер батча и скорость обработки нужно балансировать.
