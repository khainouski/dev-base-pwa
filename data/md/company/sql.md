### Q1. Нормализация vs денормализация ради чтения?

**A:**
**Идея:** **нормализация** (1NF–3NF+) снижает избыточность и аномалии обновления. **Денормализация** дублирует данные, чтобы избежать JOIN или ускорить чтение — часто в отчётных таблицах или read models.

**Сильный ответ:** язык **компромиссов** (стоимость записи vs чтения). Пример: материализованная колонка, обновляемая джобой, vs агрегация на лету.

**Слабый ответ:** «всегда нормализуем» или «всё денормализуем» без контекста.

**Мой ответ:**
- **1NF** — одно значение в каждой ячейке, никаких списков.
- **2NF** — все поля зависят от полного первичного ключа.
- **3NF** — неключевые поля зависят только от ключа, а не друг от друга.

Нормализация уменьшает дублирование данных и защищает от аномалий при обновлении. Поэтому при проектировании базы я всегда начинаю с нормализованной схемы (обычно до 3NF).

Денормализация — это осознанная оптимизация чтения. Её применяют, когда профилирование показывает, что JOIN, агрегации или сложные запросы становятся узким местом. Цена этой оптимизации — более сложные записи и необходимость поддерживать согласованность дублированных данных.

Поэтому здесь нет универсального ответа — это компромисс между стоимостью записи и стоимостью чтения:

- если данные часто меняются — предпочтительнее нормализация;
- если данные читаются значительно чаще, чем изменяются, — денормализация может дать существенный выигрыш.

**Пример:** в интернет-магазине для страницы товара нужно показывать средний рейтинг и количество отзывов. Можно при каждом запросе вычислять AVG(rating) и COUNT(*) по таблице reviews, а можно хранить в таблице products денормализованные поля rating_avg и reviews_count. Они обновляются при добавлении или удалении отзыва — в транзакции либо асинхронно через событие. Чтение становится быстрым, но усложняется запись и появляется риск временной рассинхронизации.

**Вывод:** сначала нормализую схему, затем измеряю производительность и только при наличии реального узкого места денормализую отдельные данные.

### Q2. Индексы: clustered vs non-clustered на высоком уровне; когда индекс не используется?

**A:**
**Clustered** (например PK в InnoDB): порядок таблицы совпадает с индексом — один на таблицу. **Non-clustered:** отдельная структура с указателями на строки.

Индекс могут не взять: **низкая селективность**, функции над колонкой (WHERE UPPER(name)), несовпадение типов, выбор sequential scan на маленькой таблице, устаревшая статистика.

**Сильный ответ:** **EXPLAIN** / планы; **покрывающие индексы** для частых запросов.

**Слабый ответ:** «индексы всегда ускоряют» — игнорирует цену записи и неверные индексы.

**Мой ответ:**
Индекс нужен, чтобы быстрее находить данные без полного сканирования таблицы. Но индекс ускоряет чтение ценой более медленных вставок, обновлений и удаления, поскольку его тоже нужно поддерживать.

**Clustered index** определяет физическую организацию строк таблицы — данные лежат на диске в порядке этого индекса. У таблицы может быть только один clustered index, потому что физически данные можно упорядочить лишь одним способом.

**Non-clustered index** — отдельная от таблицы структура: хранит индексируемое значение и ссылку на реальную строку. Таких индексов на таблице может быть много.

*В InnoDB (MySQL):* Primary Key — это clustered index, данные строк хранятся прямо в leaf-страницах его B-tree (`Primary Key B-tree → сама строка`).

*В PostgreSQL:* таблица хранится как **heap** — данные лежат в порядке вставки/обновления, а не в порядке какого-либо индекса. Поэтому **все** индексы в Postgres, включая индекс на Primary Key, — **non-clustered**: это независимые B-tree структуры, которые хранят значение ключа и ссылку на физический адрес строки — **TID** (tuple ID: номер страницы + смещение), а не саму строку, как в InnoDB (`B-tree index → TID → Heap → строка`). Понятие «кластерного индекса» в Postgres — это разовая операция `CLUSTER table USING index_name`, которая физически переупорядочивает таблицу по индексу один раз; порядок не поддерживается автоматически, и после новых INSERT/UPDATE снова размывается.

Индекс может не использоваться в нескольких случаях:

- низкая селективность (например, поле is_active, где почти все значения одинаковые);
- функции или вычисления над индексируемым столбцом (WHERE UPPER(name) = ...);
- несовпадение типов данных, которое приводит к неявным преобразованиям;
- маленькая таблица, где полный скан дешевле использования индекса;
- устаревшая статистика, из-за которой оптимизатор выбирает неоптимальный план.

Для анализа всегда использую EXPLAIN или EXPLAIN ANALYZE, чтобы посмотреть план выполнения запроса и понять, используется ли индекс. Если запрос часто читает только несколько колонок, можно создать покрывающий (covering) индекс, чтобы СУБД получила все необходимые данные из индекса без обращения к самой таблице.

### Q3. Уровни изоляции: какие аномалии при READ COMMITTED vs REPEATABLE READ?

**A:**
**READ COMMITTED:** нет грязного чтения; возможны **неповторяемое чтение** и **фантомы** (зависит от СУБД).

**REPEATABLE READ:** стабильный снимок в транзакции (точное поведение различается — MySQL vs PostgreSQL по фантомам).

**Сильный ответ:** называет **фантом**, **потерянное обновление**, какой уровень в проде. Знает цену **SERIALIZABLE**.

**Слабый ответ:** «транзакции всё чинят» без уровня изоляции.

**Мой ответ:**
**Уровни изоляции (SQL Standard):**
1. **READ UNCOMMITTED** — можно читать незакоммиченные изменения других транзакций (Dirty Read).
2. **READ COMMITTED** — видны только закоммиченные данные. Каждое чтение видит актуальное состояние базы на момент выполнения запроса.
3. **REPEATABLE READ** — все запросы внутри транзакции работают с одним и тем же снимком (snapshot) данных.
4. **SERIALIZABLE** — самый строгий уровень. Транзакции выполняются так, как будто они идут последовательно.

**В PostgreSQL:**
- **READ UNCOMMITTED** → работает как **READ COMMITTED**.
- **READ COMMITTED** *(по умолчанию)*.
- **REPEATABLE READ**.
- **SERIALIZABLE**.

**Основные аномалии:**
- **Dirty Read** — чтение незакоммиченных данных.
- **Non-repeatable Read** — повторное чтение одной строки возвращает другое значение.
- **Phantom Read** — повторный запрос возвращает другой набор строк.
- **Lost Update** — одна транзакция перезаписывает изменения другой.

**READ COMMITTED** (используется по умолчанию в PostgreSQL):
- ❌ Dirty Read
- ✅ Non-repeatable Read
- ✅ Phantom Read
- ✅ Lost Update

**REPEATABLE READ:**
- ❌ Dirty Read
- ❌ Non-repeatable Read
- ❌ Phantom Read *(в PostgreSQL благодаря MVCC)*
- ⚠️ Возможны аномалии сериализации (Write Skew).

**SERIALIZABLE** гарантирует максимальную консистентность данных, но:
- снижает производительность;
- возможны конфликты и ошибки сериализации;
- конфликтующие транзакции необходимо повторять.

**Что используют в продакшене:** чаще всего **READ COMMITTED**. Для критичных операций применяют `SELECT ... FOR UPDATE`, оптимистические блокировки или **SERIALIZABLE**.

**Итог:** важно понимать различия между **READ COMMITTED** и **REPEATABLE READ**, знать аномалии (**Dirty Read, Non-repeatable Read, Phantom Read, Lost Update**) и помнить, что **SERIALIZABLE** обеспечивает максимальную консистентность ценой производительности.

### Q4. N+1: как находить и исправлять?

**A:**
**Идея:** загрузили список, потом по запросу на строку связанные данные — типичная ловушка ORM.

**Сильный ответ:** логи / APM с числом запросов, JOIN, IN (...) пакетная загрузка, паттерн **DataLoader**, eager loading. Тесты, считающие запросы.

**Слабый ответ:** не слышал про N+1.

**Мой ответ:**
**N+1** — это проблема, когда сначала выполняется **1 запрос** для получения списка сущностей, а затем ещё **N запросов** для загрузки связанных данных для каждой записи. Например:

```sql
SELECT * FROM users; -- 1 запрос
SELECT * FROM orders WHERE user_id = 1;
SELECT * FROM orders WHERE user_id = 2;
SELECT * FROM orders WHERE user_id = 3;
-- ещё N запросов
```

**Как находить:**
- SQL-логи и количество запросов на один HTTP/gRPC-запрос.
- APM и distributed tracing.
- `EXPLAIN` для анализа дорогих запросов.
- Тесты, считающие количество SQL-запросов.

**Как исправлять:**
- `JOIN`, если это эффективно.
- Batch-загрузка через `WHERE id IN (...)`.
- **Eager Loading / Preload** в ORM.
- **DataLoader** для объединения множества запросов в один.

> **Важно:** `JOIN` не всегда лучший вариант. При связях **one-to-many** он может сильно увеличить количество строк, поэтому часто эффективнее выполнить **два запроса**: один за основными сущностями и один batch-запрос за связанными данными.

**Итог:** N+1 находят по логам и APM, а устраняют с помощью `JOIN`, batch-загрузки (`IN`), eager loading или DataLoader.

### Q5. Многошаговая атомарная операция: как уложили в SQL-транзакции?

**A:**
**Сильный ответ:** BEGIN…COMMIT, rollback при ошибке, выбор изоляции, **идемпотентность ретраев** (вне или внутри txn). Знает, что длинные транзакции — плохо для блокировок.

**Слабый ответ:** «юзали транзакции» без границ; вложенные / savepoints — плюс если уместно.

**Мой ответ:**
Если несколько операций должны выполниться **атомарно**, я объединяю их в одну SQL-транзакцию:

```sql
BEGIN;
-- INSERT / UPDATE / DELETE
COMMIT;
```

Если любой шаг завершается ошибкой — выполняется **ROLLBACK**, и все изменения отменяются.

**На что обращаю внимание:**
- Выбираю подходящий **уровень изоляции** в зависимости от требований к консистентности.
- Держу транзакцию **как можно короче**, чтобы уменьшить время удержания блокировок и вероятность дедлоков.
- Внутри транзакции выполняю **только операции с БД**. Вызовы внешних сервисов, Kafka, HTTP и т.п. выношу за её пределы (или использую Outbox Pattern).
- Если возможны повторы операции, обеспечиваю **идемпотентность**.

**Дополнительно:** при необходимости использую **SAVEPOINT** для частичного отката внутри транзакции.

**Итог:** чётко определяю границы транзакции (`BEGIN → COMMIT/ROLLBACK`), выбираю нужный уровень изоляции, делаю транзакции короткими и не смешиваю их с внешними вызовами.

### Q6. Оптимистичные vs пессимистичные блокировки — когда что применяли?

**A:**
**Оптимистичные:** UPDATE … WHERE version = ?; конфликт при конкурентной записи — хорошо при низкой конкуренции.

**Пессимистичные:** SELECT … FOR UPDATE — при высокой конкуренции или финансовых инвариантах.

**Сильный ответ:** реальный сценарий; **retry** при оптимистичных конфликтах.

**Слабый ответ:** одна стратегия на все случаи.

**Мой ответ:**
**Оптимистичные блокировки** используются, когда **конкуренция между транзакциями низкая**, а конфликты происходят редко. Обычно реализуются через поле `version` или `updated_at`:

```sql
UPDATE users
SET name = ?, version = version + 1
WHERE id = ? AND version = ?;
```

Если обновилось **0 строк**, значит запись уже изменила другая транзакция — возникает конфликт. В этом случае приложение перечитывает данные и **повторяет операцию (retry)** или сообщает пользователю о конфликте.

**Пессимистичные блокировки** используются, когда **конкуренция высокая** или нельзя допустить нарушение бизнес-инвариантов — строка блокируется до конца транзакции, поэтому другие транзакции не смогут изменить её раньше времени. Типичные сценарии: денежные переводы, резервирование товаров, списание остатков на складе.

**FOR UPDATE vs FOR UPDATE SKIP LOCKED**

Оба используются в транзакции для блокировки выбранных строк до `COMMIT`/`ROLLBACK`.

**FOR UPDATE:** если строка уже заблокирована другой транзакцией — **ждёт**. Использую, когда нужна именно эта конкретная строка: например, списание с конкретного счёта — транзакция B обязана дождаться, пока A завершит операцию с этим же счётом, иначе баланс разъедется.

```sql
SELECT * FROM accounts WHERE id = ? FOR UPDATE;
```
`Locked → WAIT`

**FOR UPDATE SKIP LOCKED:** уже заблокированные строки **пропускает** и берёт следующую свободную. Использую в очереди задач (job queue, outbox pattern) — несколько воркеров разбирают пул одинаковых по смыслу строк, и неважно, какую именно возьмёт конкретный воркер, важно не простаивать в ожидании друг друга.

```sql
SELECT * FROM outbox
WHERE status = 'pending'
ORDER BY created_at
LIMIT 1
FOR UPDATE SKIP LOCKED;
```
`Locked → SKIP → Next row`

Третий вариант — `FOR UPDATE NOWAIT`: вместо ожидания сразу возвращает ошибку, если строка занята. Использую, когда хочу быстро узнать о конфликте, а не блокировать запрос.

**Главное:** `FOR UPDATE` → нужна эта строка → **WAIT**. `FOR UPDATE SKIP LOCKED` → нужна любая доступная → **SKIP**.

**Что выбрать:**
- **Оптимистичные** — большинство CRUD-сценариев, где конфликты редки и важна высокая производительность; при конфликте — **retry**.
- **Пессимистичные** — финансовые операции, управление остатками, бронирование и другие случаи с высокой конкуренцией и строгими требованиями к консистентности.

### Q7. Взаимные блокировки: как дебажить и предотвращать порядок захвата?

**A:**
**Сильный ответ:** согласованный **порядок блокировок** (всегда A потом B), короче транзакции, индексы для гранулярности блокировок. Логи СУБД о жертве deadlock. Таймауты транзакций.

**Слабый ответ:** «дедлоков не бывает» — бывают при конкуренции.

**Мой ответ:**
**Deadlock (взаимная блокировка)** — ситуация, когда две или более транзакции держат разные блокировки и ждут друг друга. Например:
- транзакция **A** заблокировала строку **1** и ждёт строку **2**;
- транзакция **B** заблокировала строку **2** и ждёт строку **1**.

СУБД обнаруживает deadlock, выбирает одну из транзакций (**deadlock victim**) и откатывает её.

**Как дебажить:**
- анализировать логи СУБД с информацией о deadlock victim;
- смотреть SQL-запросы и порядок захвата блокировок;
- использовать APM и таймауты ожидания блокировок.

**Как предотвращать:**
- **всегда захватывать ресурсы в одном порядке** (например, сначала `A`, потом `B`) — это главное правило;
- делать транзакции как можно короче;
- не выполнять внутри транзакции HTTP/Kafka-вызовы;
- использовать индексы, чтобы блокировать меньше строк;
- после deadlock выполнять **retry** транзакции.

**Итог:** основная защита от deadlock — единый порядок захвата блокировок, короткие транзакции и повторная попытка после ошибки.

### Q8. Слои handlers → services → repositories? Где живёт SQL?

**A:**
**Идея:** **handler** — маппинг HTTP/gRPC, валидация, коды. **service** — бизнес-правила, оркестрация. **repository** — только SQL (или интерфейс к БД). Зависимости внутрь: handlers → services → интерфейсы репозиториев.

**Сильный ответ:** SQL только в репозитории; тесты с моками интерфейсов. Допускает прагматичные исключения.

**Слабый ответ:** SQL в хендлерах; «бог-сервис» без слоёв.

**Мой ответ:**
У меня в проекте такие аналогии:

| Классическое название | В проекте | Где лежит |
|---|---|---|
| handlers | controllers (HTTP и gRPC) | `internal/controller/http/v1`, `internal/controller/grpc/v1` |
| services | usecase | `internal/usecase` |
| repositories | adapters | `internal/adapter/postgres`, `internal/adapter/kafka_producer` |

SQL живёт только в репозитории — `internal/adapter/postgres`.

- **Handler** (`internal/controller/http|grpc`) — SQL не содержит. Только маппинг запрос↔ответ и коды ошибок.
- **Service/usecase** (`internal/usecase`) — SQL не содержит. Знает только интерфейс репозитория (Postgres), объявленный в самом usecase-пакете — это инверсия зависимостей: сервис зависит от абстракции, а не от pgx/SQL.
- **Repository** (`internal/adapter/postgres`) — единственное место с SQL-запросами и работой с pgx. Один файл на операцию (create/get/update/delete).

**Тестируемость:** usecase-тесты гоняются на моках интерфейса Postgres (mockery), без БД. SQL проверяется отдельно интеграционными тестами на реальном Postgres.

**Прагматичное исключение:** пул соединений (`pkg/postgres`) и обёртка транзакций (`pkg/transaction`) вынесены в `pkg/` как чисто инфраструктурный код без знания о домене — репозиторий сам «достаёт» транзакцию из контекста (`transaction.TryExtractTX(ctx)`), а не получает её явным параметром через интерфейс. Это немного смешивает ответственность (репозиторий знает про механизм транзакций), но ни строки SQL, ни знание о таблицах за пределы repository-слоя не выходит.

### Q9. database/sql vs ORM vs query builder — что использовали и почему?

**A:**
**database/sql:** полный контроль, многословно, без магии ORM. **GORM, sqlc, squirrel, Ent** — разные компромиссы: codegen vs reflection, типобезопасность vs гибкость.

**Сильный ответ:** конкретный выбор и почему (sqlc для SQL на этапе компиляции, GORM для скорости CRUD). История миграций в связке с инструментом.

**Слабый ответ:** «ORM — зло» без нюансов.

**Мой ответ:**
В Go есть несколько основных подходов к работе с SQL-базами, и выбор зависит от задачи.

**`database/sql`** — стандартная библиотека Go для работы с SQL.
- *Когда использовать:* нужен полный контроль над SQL и транзакциями; важны производительность и прозрачность запросов.
- *Минусы:* много ручного кода (`Scan`, mapping результатов).

**ORM (GORM, Ent)** — упрощает работу с моделями и стандартным CRUD.
- **GORM** — классическая ORM на reflection. Хорошо подходит для быстрого CRUD, административных панелей и небольших проектов.
- **Ent** — ORM с code generation и типобезопасным API. Уменьшает количество runtime-ошибок, но добавляет собственный слой абстракции.
- *Минусы ORM:* часть SQL скрыта; возможны N+1-запросы; сложнее оптимизировать нестандартные запросы.

**Query Builder (Squirrel (Белка))** — позволяет программно собирать SQL, сохраняя контроль над ним.
- *Когда использовать:* динамические фильтры; поиск; сортировка; отчёты; запросы с большим количеством необязательных условий.

**sqlc** — генератор типобезопасного Go-кода из SQL. Разработчик пишет обычный SQL, а `sqlc` генерирует готовые методы.
- *Плюсы:* SQL остаётся явным; проверка запросов и типов на этапе генерации; меньше ручного `Scan`; нет runtime reflection; удобно оптимизировать запросы через `EXPLAIN`.

**Чем sqlc отличается от Squirrel:** это разный момент, когда появляется финальный SQL. У `sqlc` генерация Go-кода из SQL-запросов происходит **до запуска программы**, на этапе сборки — если запрос написан с ошибкой или не совпадают типы, это видно сразу при генерации, а не в рантайме. У Squirrel SQL-строка собирается динамически **во время выполнения программы** — гибко для условных фильтров, но ошибку в собранном запросе увидишь только тогда, когда он реально уйдёт в базу.

**Мой выбор:** для production-сервисов обычно использую `sqlc` вместе с `pgx` или `database/sql`, потому что получаю явный SQL, типобезопасность и предсказуемую производительность. Если нужен быстрый CRUD без сложной бизнес-логики — GORM. Если запросы динамические — Squirrel.

**Миграции:** историю изменений схемы храню отдельно в виде версионируемых SQL-файлов и применяю через **golang-migrate**.

```text
migrations/
├── 000001_create_users.up.sql
├── 000001_create_users.down.sql
└── 000002_add_status.up.sql
```

### Q10. Как прокидывали context.Context в вызовы БД? Таймауты, отмена?

**A:**
**Сильный ответ:** ctx первым параметром в методах репозитория; **QueryContext** / **ExecContext**; таймаут через context.WithTimeout на запрос; отмена в длинных выборках.

**Слабый ответ:** Query без контекста — мешает graceful shutdown и наблюдаемости.

**Мой ответ:**
`context.Context` передаю первым параметром через все слои приложения: HTTP/gRPC-хендлер → сервис → репозиторий. Это позволяет использовать один контекст для всего жизненного цикла запроса.

В репозитории использую контекстные методы работы с БД: `QueryContext`, `QueryRowContext`, `ExecContext` (или аналогичные методы `pgx`, принимающие `ctx`).

Для операций с БД обычно задаю таймаут через `context.WithTimeout`, чтобы запрос не мог выполняться бесконечно:

```go
ctx, cancel := context.WithTimeout(ctx, 3*time.Second)
defer cancel()
```

Если клиент отменил запрос, истек дедлайн или сервис завершает работу (graceful shutdown), контекст автоматически отменяется, а драйвер прекращает выполнение SQL-запроса и освобождает соединение.

Для длительных выборок и обработки большого количества строк также использую тот же `ctx`, чтобы чтение можно было остановить сразу после отмены.

**Итог:** всегда прокидываю `context.Context` через все слои, использую контекстные методы драйвера и задаю таймауты. Это позволяет корректно отменять запросы, избегать зависших операций и поддерживать graceful shutdown.

### Q11. Настройки пула в проде (max open, max idle, lifetime)?

**A:**
**Идея:** **SetMaxOpenConns** ограничивает нагрузку на БД; **SetMaxIdleConns** reuse; **SetConnMaxLifetime** — избегаем старые соединения / failover; **SetConnMaxIdleTime** — сбрасывает простаивающие.

**Сильный ответ:** настройка относительно max_connections СУБД и числа подов (не умножать слепо). Алерты на время ожидания соединения.

**Слабый ответ:** пул по умолчанию без мысли — частый источник сбоев под нагрузкой.

**Мой ответ:**
В Go обычно настраиваю четыре основных параметра пула. Аналогия для всех четырёх: парковка = пул, места на парковке = соединения, машины = запросы, которым нужно соединение.

- `SetMaxOpenConns` — максимальное количество одновременно открытых соединений (и занятых, и свободных). *Пример:* сколько всего мест на парковке — 51-я машина просто ждёт, пока освободится место.
- `SetMaxIdleConns` — сколько свободных (никем не используемых) соединений держать открытыми про запас, а не закрывать сразу после того, как запрос завершился. *Пример на цифрах:* под нагрузкой было занято 20 мест (`MaxOpenConns = 20`). Нагрузка спала, активны только 3 машины — 17 мест освободилось. Если `MaxIdleConns = 10`, то 10 освободившихся мест остаются занятыми про запас (следующая машина паркуется мгновенно, место уже готово), а оставшиеся 7 закрываются — здесь аналогия заканчивается: в реальности держать место «занятым про запас» не бесплатно, каждое такое соединение — это отдельный процесс на стороне Postgres, занимающий память на сервере, даже если по нему ничего не происходит.
- `SetConnMaxLifetime` — время жизни соединения с момента создания, независимо от того, используется оно сейчас или простаивает. *Пример:* сколько машина может стоять на месте вообще, прежде чем её попросят уехать, даже если она исправна, — полезно, когда соединение может «залипнуть» на упавшем или выведенном из ротации узле за балансировщиком.
- `SetConnMaxIdleTime` — максимальное время простоя, после которого свободное соединение закрывают. *Пример:* сколько машина может стоять на месте без дела, прежде чем её попросят уехать, — ночью нагрузка упала, лишние машины на парковке просто не нужны.

`SetMaxOpenConns` выбираю исходя не только из нагрузки приложения, но и из `max_connections` базы данных, количества подов и других сервисов, работающих с этой БД. Важно, чтобы суммарное количество соединений всех экземпляров приложения не превышало возможности СУБД: например, если у базы `max_connections = 100`, а приложение развёрнуто в 10 подах, каждый под не должен ставить `MaxOpenConns` больше ~8–9, иначе при масштабировании база начнёт отказывать в новых подключениях.

`SetMaxIdleConns` позволяет переиспользовать уже открытые соединения и уменьшить стоимость их создания. Обычно его делают меньше или равным `MaxOpenConns`.

`SetConnMaxLifetime` помогает периодически обновлять соединения, что полезно при failover, работе через прокси или балансировщик. `SetConnMaxIdleTime` закрывает долго простаивающие соединения и освобождает ресурсы.

После настройки обязательно смотрю статистику пула (`db.Stats()`) и метрики ожидания соединений. Если начинает расти время ожидания или количество запросов, ожидающих свободное соединение, значит пул слишком маленький либо запросы к БД работают слишком долго.

**Итог:** размер пула рассчитываю относительно лимитов БД и количества экземпляров приложения, а затем корректирую по метрикам под реальной нагрузкой.

### Q12. Как устроены миграции (goose, golang-migrate, Atlas, Flyway sidecar)? Кто применяет в CI/CD?

**A:**
**Сильный ответ:** версионированный SQL или Atlas HCL; CI накатывает на staging; prod с апрувом или безопасным автоматом; **expand/contract** для zero-downtime. Стратегия отката.

**Слабый ответ:** ручной ALTER в проде без истории.

**Мой ответ:**
Для миграций я использовал `golang-migrate`. Схема хранится в виде версионированных SQL-файлов, где каждая миграция состоит из пары `up` и `down`.

```text
migrations/
├── 000001_create_users.up.sql
├── 000001_create_users.down.sql
├── 000002_add_status.up.sql
└── 000002_add_status.down.sql
```

Такой подход позволяет отслеживать историю изменений схемы, откатывать миграции при необходимости и применять их одинаково во всех окружениях.

В CI/CD миграции лучше выполнять отдельным job **до деплоя новой версии приложения**. Это исключает ситуацию, когда несколько реплик сервиса одновременно пытаются изменить схему базы данных.

Обычно на **staging** миграции применяются автоматически, а для **production** добавляется approval или другой механизм безопасного запуска.

Если миграция несовместима со старой версией приложения, использую подход **expand/contract**:
1. Добавить новую колонку или таблицу.
2. Выпустить код, совместимый со старой и новой схемой.
3. Перенести данные при необходимости.
4. Отдельным релизом удалить старую схему.

Откат возможен через `down`-миграции, но для изменений, связанных с потерей данных, безопаснее использовать **forward-fix** или заранее подготовленный план восстановления, а не автоматически выполнять rollback.

**Итог:** использую `golang-migrate` с версионированными SQL-файлами, миграции выполняются отдельным этапом CI/CD перед деплоем, а для изменений без downtime применяется стратегия **expand/contract**.

### Q13. Как оформить метод репозитория с несколькими операторами в одной транзакции?

**A:**
**Сильный ответ:** объект Tx из BeginTx; передача *sql.Tx или closure; defer rollback; commit при успехе. **Unit of work**. Тест с реальной БД или контейнером.

**Слабый ответ:** несколько auto-commit вызовов и ожидание атомарности.

**Мой ответ:**
В моём проекте транзакционная граница находится на уровне **use case**, потому что именно use case знает, какие операции должны выполниться атомарно.

**1. Use Case** (`internal/usecase/create_user.go`) — объединяет несколько вызовов репозитория в одну транзакцию:

```go
transaction.Wrap(ctx, func(ctx context.Context) error {
    if err := u.postgres.CreateUser(ctx, user); err != nil {
        return err
    }
    if err := u.postgres.SaveOutboxKafka(ctx, event); err != nil {
        return err
    }
    return nil
})
```

Именно здесь принимается решение, что обе операции должны либо успешно завершиться вместе, либо вместе откатиться.

**2. Unit of Work** (`pkg/transaction/wrap.go`) — `Wrap()`:
1. вызывает `pool.Begin(ctx)`;
2. получает `pgx.Tx`;
3. делает `defer tx.Rollback(ctx)`;
4. кладёт `tx` в `context.Context`;
5. вызывает callback;
6. если ошибок нет — выполняет `tx.Commit(ctx)`.

Таким образом вся логика `Begin / Commit / Rollback` находится в одном месте.

**3. Repository** (`internal/adapter/postgres/*.go`) — каждый метод репозитория начинает работу одинаково:

```go
txOrPool := transaction.TryExtractTX(ctx)
```

`TryExtractTX()`:
- если в `ctx` есть транзакция — возвращает `pgx.Tx`;
- если транзакции нет — возвращает обычный `pgxpool.Pool`.

После этого репозиторий просто вызывает `txOrPool.Exec(ctx, ...)` или `txOrPool.Query(ctx, ...)`. Поэтому один и тот же метод может работать как внутри транзакции, так и без неё.

**Альтернативная реализация:** часто транзакцию передают явно:

```go
tx, _ := db.BeginTx(ctx, nil)
repo.CreateUser(ctx, tx, user)
repo.SaveOutboxKafka(ctx, tx, event)
```

или используют общий интерфейс `DBTX`. Плюс такого подхода — по сигнатуре метода сразу видно, что используется транзакция. В моём проекте выбран другой вариант — `Unit of Work + context.Context`, чтобы не менять сигнатуры методов репозитория.

**Тестирование:**
- **Unit-тесты** — use case тестируется на моках репозитория.
- **Интеграционные тесты** — на реальной PostgreSQL проверяются оба сценария: успешный `Commit` и `Rollback`, если одна из операций завершилась ошибкой.

**Итог:**
- **Use Case** определяет границы транзакции.
- **transaction.Wrap** управляет `Begin → Commit/Rollback`.
- **Repository** через `TryExtractTX(ctx)` автоматически работает либо с `Tx`, либо с `Pool`.
- Несколько SQL-операций выполняются атомарно благодаря **Unit of Work**.
