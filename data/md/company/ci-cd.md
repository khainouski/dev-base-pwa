### Q1. Какая CI (GitHub Actions, GitLab CI, Jenkins, TeamCity, Circle и т.д.)? Триггеры?

**A:**
**Сильный ответ:** правила (PR, main, теги, cron); matrix (OS, версии Go); self-hosted vs облачные минуты. Монорепо vs пайплайн на сервис.

**Слабый ответ:** «был Jenkins» без понимания содержимого пайплайна.

**Мой ответ:**
**CI-платформа** — сервис, который по событию в репозитории (пуш, PR, тег, расписание) автоматически запускает пайплайн (тесты, линт, сборку, деплой). Основные игроки: GitHub Actions (нативно на GitHub, YAML-workflow'ы в `.github/workflows`), GitLab CI (нативно на GitLab, `.gitlab-ci.yml`), Jenkins (self-hosted, скриптуемый через Groovy/Jenkinsfile, максимальная гибкость и максимальные накладные расходы на поддержку), CircleCI/TeamCity (облачные/self-hosted альтернативы с похожей моделью).

**Триггер** — событие, по которому запускается пайплайн: push в конкретную ветку, открытие/обновление PR, создание тега (обычно для релизов), schedule/cron (регулярные прогоны — nightly-тесты, security-сканы), `workflow_dispatch`/manual trigger (запуск вручную).

Какую платформу выбрать — зависит от того, где уже живёт код и инфраструктура. Если репозиторий на GitHub — GitHub Actions почти всегда выбор по умолчанию: нулевая настройка интеграции, огромный маркетплейс готовых actions, бесплатные минуты для публичных репо. GitLab CI — аналогично, если весь стек на GitLab (плюс у GitLab CI традиционно сильнее встроенная поддержка environments/review apps "из коробки"). Jenkins — оправдан, когда нужна кастомная логика, которую SaaS-платформы не потянут, или когда инфраструктура must быть полностью on-premise (регуляторные требования, отсутствие доступа к облаку) — но платите за это временем на поддержку самого Jenkins-мастера, плагинов, апдейтов.

**Правила триггеров** — не "гоняем всё на всё событие", а осознанный набор:

- PR — быстрый набор проверок (юниты, линт, статический анализ) — блокирующий гейт перед мерджем, должен быть быстрым, чтобы не тормозить разработку.
- push в main — после мерджа, полный набор + сборка артефакта/образа, часто с деплоем на staging.
- Теги (`v*`) — отдельный релизный пайплайн: сборка версионированного артефакта, публикация, деплой на prod — не совпадает с обычным CI на каждый коммит.
- Cron/schedule — то, что дорого гонять на каждый PR (полный интеграционный suite, security/dependency-сканы, nightly performance-тесты) — по расписанию, не блокируя разработчиков.

**Matrix** — тестирование по нескольким осям одновременно, а не последовательными джобами: например, `os: [ubuntu, macos, windows] × go-version: [1.22, 1.23]` — CI сам разворачивает это в декартово произведение отдельных параллельных джобов. Важно для библиотек/инструментов, где пользователи на разных платформах/версиях языка; для внутреннего сервиса, который всегда деплоится на одну конкретную платформу — matrix обычно избыточен, разве что для проверки совместимости с несколькими версиями Go при апгрейде.

**Self-hosted vs облачные минуты** — компромисс стоимость/контроль:

- Облачные раннеры (GitHub-hosted, etc.) — ноль поддержки инфраструктуры, но лимитированные минуты (платите сверх бесплатного лимита), холодный старт каждой VM.
- Self-hosted раннеры — свои машины (часто уже под нагрузкой, быстрее), полный контроль над окружением/кешами (можно держать прогретый Docker-кеш, локальные зависимости), но нужно самим поддерживать, патчить, масштабировать под нагрузку — это отдельная инфраструктурная работа, не бесплатная просто потому что "не платим провайдеру за минуты".

**Монорепо vs пайплайн на сервис** — влияет на архитектуру CI:

- Один сервис = один репозиторий = один пайплайн — просто, но при десятках сервисов — десятки почти идентичных workflow-файлов, дублирование конфигурации.
- Монорепо — один пайплайн должен уметь определять, что изменилось, и гонять только релевантные проверки (path-based triggers — `on: push: paths: ['service-a/**']`), иначе каждый PR гоняет тесты всех сервисов сразу, даже если тронут один файл в одном из них — CI становится непропорционально медленным при росте монорепо.

### Q2. Стадии: golangci-lint, go test, race, coverage gates, статанализ?

**A:**
Типичный порядок: кеш зависимостей → lint (быстрый fail) → unit → race → сборка → **интеграция** → образ → registry.

**Сильный ответ:** конфиг `golangci-lint` в репо; падение на `go vet`; скан уязвимостей (Snyk, Trivy). Race в CI несмотря на стоимость.

**Слабый ответ:** только `go build` без тестов в CI.

**Мой ответ:**
Стадии CI-пайплайна для Go-сервиса — последовательность проверок, упорядоченная по принципу fail fast: дешёвые и быстрые проверки идут первыми, чтобы обнаружить проблему до того, как потратите время на дорогие этапы (сборка, интеграционные тесты, публикация образа).

```text
кеш зависимостей → lint (быстрый fail) → unit → race → сборка → интеграция → образ → registry
```

1. **Кеш зависимостей** — восстановить `go.sum`/module cache, чтобы не качать всё заново на каждый прогон.
2. **Lint** — `golangci-lint`, агрегатор десятков линтеров (`govet`, `staticcheck`, `errcheck`, `gofmt` и т.д.) в один прогон с единым конфигом. Идёт первым, потому что самый быстрый и ловит опечатки/явные ошибки раньше, чем тратить время на тесты. **`go vet` падает жёстко, не warning** — это не стилистические придирки, а реальные баги (например, неправильный формат в `Printf`, некорректное использование `sync.Mutex` через копирование), поэтому его нельзя просто залогировать и продолжить. **Конфиг `golangci-lint` в репозитории** (`.golangci.yml`), не дефолтный набор "как есть" — осознанно включённый/выключенный набор линтеров версионируется вместе с кодом, а не полагается на дефолты инструмента, которые могут поменяться между версиями.
3. **Unit-тесты** — быстрая логика, без внешнего I/O.
4. **Race** — `-race`: отдельная инструментированная сборка тестов, которая на рантайме отслеживает конкурентный доступ к памяти между горутинами и падает с точным отчётом при обнаружении гонки без синхронизации. Дороже по времени/памяти в разы, поэтому либо совмещается с обычным прогоном юнитов (проще, но каждый прогон дороже), либо выносится в параллельный отдельный CI-job (сложнее пайплайн, но не задерживает быстрый юнит-фидбэк). Несмотря на цену — гонять обязательно, иначе конкурентные баги долетают до прода необнаруженными.
5. **Coverage gate** — порог покрытия, блокирующий мердж, если новый код недостаточно покрыт (обычно **diff coverage** — покрытие именно изменённых строк, а не общий процент по всему репо).
6. **Статанализ** — более широкая категория, чем линтер: SAST-сканеры на уязвимости зависимостей/кода (Snyk, Trivy, gosec).
7. **Сборка** — компиляция бинарника/образа, подтверждает, что всё линкуется.
8. **Интеграционные тесты** — самые дорогие, требуют реальной инфраструктуры (БД/брокер), поэтому позже всех остальных проверок.
9. **Образ → registry** — публикация только после того, как всё предыдущее прошло зелёным.

### Q3. Как жили долгие интеграционные тесты (ночные vs на PR, параллель)?

**A:**
**Сильный ответ:** на PR — быстрые; ночные или только main для медленных E2E; параллельные job'ы; явная политика retry.

**Слабый ответ:** всё на каждом PR — очередь 30+ минут и никто не задаёт вопросов.

**Мой ответ:**
Разделение по скорости — не все интеграционные/E2E тесты одинаково дёшевы: часть даёт быстрый сигнал (секунды-минуты), часть — дорогая (полные сценарии, много внешних систем, нагрузочные) и не обязана блокировать каждый PR.

**На PR — только быстрое подмножество.** Не весь интеграционный suite гоняется на каждый PR — отбирается критичный набор (smoke-тесты, основные happy-path сценарии, тесты, покрывающие часто ломающиеся места), который укладывается в приемлемое время блокирующего гейта (единицы минут). Остальное — не блокирует мердж.

**Медленные/полные E2E — ночью или только на main.** Полный интеграционный/E2E suite (все edge-cases, кросс-сервисные сценарии, нагрузочные, security-сканы) гоняется по schedule (cron, ночью) или триггерится только на push в main (после мерджа, не перед) — фидбэк по ним приходит с задержкой, но это осознанный компромисс: разработчик не ждёт часами на каждый PR ради проверки, которая редко ловит регрессии именно в этом PR.

**Параллельные джобы.** Внутри самого suite — либо `t.Parallel()` там, где тесты не делят состояние, либо шардирование на уровне CI (matrix-стратегия, несколько джобов, каждый гоняет свою часть тестов на отдельной машине/контейнере) — суммарное время падает кратно числу шардов вместо линейного роста с числом тестов.

**Явная политика retry, а не стихийная.** Если тест иногда флакует по известной, принятой причине (например, редкий сетевой таймаут во внешнем сервисе, а не баг в самом тесте) — retry настраивается явно и ограниченно (например, "до 2 повторов только для помеченных как flaky тестов, с логированием факта повтора для последующего отслеживания") — не "жать перезапуск джобы вручную, пока не позеленеет", и не бесконтрольный global retry на весь suite, который маскирует реальные баги под видом "просто флакнуло".

### Q4. Артефакты: container registry, бинарники — как тегировали версии?

**A:**
**Сильный ответ:** иммутабельные теги (git sha); semver на релизах; не только `latest` в проде. **Продвижение** между окружениями.

**Слабый ответ:** Docker Hub без стратегии тегов.

**Мой ответ:**
**Артефакт** — то, что собирается один раз в CI и затем переиспользуется на всех этапах (тестирование → staging → prod) без пересборки: Docker-образ в container registry (ECR/GCR/Docker Hub/Harbor) или скомпилированный бинарник (GitHub Releases, S3, internal artifact storage).

**Иммутабельные теги — git SHA как основной тег.** Каждый образ/бинарник тегируется хешем коммита, из которого он собран (`myapp:a1b2c3d`) — это гарантирует, что тег однозначно и навсегда указывает на конкретное состояние кода. В отличие от `latest` или мутабельного тега вроде `myapp:dev`, который перезаписывается на каждый билд — с git SHA невозможна ситуация "у меня в проде тег v1.2, но неясно, что реально внутри, потому что тег переиспользовался".

**Semver — отдельно, на релизах.** Git SHA — для каждого билда без исключения (в том числе промежуточных, PR-билдов), а human-readable semver-тег (`v1.4.0`) навешивается дополнительно, только в момент официального релиза — обычно как алиас/дополнительный тег на уже существующий образ с SHA-тегом, а не отдельная пересборка. Semver даёт понятную для людей версию (majore/minor/patch по SemVer-семантике), git SHA — техническую точность для CI/CD автоматизации.

**Не только `latest` в проде.** `latest` — удобен для локальной разработки/быстрого прототипирования, но в проде опасен: невозможно понять, какая именно версия реально задеплоена без похода в registry за метаданными, откаты через `latest` невозможны (вчерашний `latest` уже перезаписан сегодняшним), и при параллельном деплое разные поды могут случайно подхватить разные версии образа под одним и тем же тегом, если registry/kubelet закешировал по-разному.

**Продвижение между окружениями — один артефакт, разные деплои.** Собираем образ один раз в CI по коммиту, тегируем SHA, и именно этот образ (не пересобранный заново) деплоим сначала на staging, прогоняем там проверки, и затем тот же самый образ (по тому же тегу/digest) продвигаем в prod — обычно через отдельный шаг CD, который меняет только конфигурацию окружения (env vars, replica count), не запускает `docker build` заново. Это исключает класс багов "на staging всё ок, а в проде другое поведение", потому что бинарные байты гарантированно идентичны — пересборка на разном окружении (другая версия базового образа, другой кеш слоёв) теоретически может дать разный результат даже из того же кода.

### Q5. CD: автодеплой в staging? Прод — ручной gate, канарейка, feature flags?

**A:**
Staging: часто авто на merge в main. Prod: ручной approve, GitOps (Argo), канарейка, feature flags для рискованных изменений.

**Сильный ответ:** откат за минуты; кто апрувит прод.

**Слабый ответ:** прод через SSH и `./deploy.sh` — аудит и повторяемость страдают.

**Мой ответ:**
**CD (Continuous Deployment/Delivery)** — автоматизированный процесс доставки уже собранного и протестированного артефакта в окружение. Delivery — до prod готово к деплою одной кнопкой; Deployment — доезжает до prod полностью автоматически, без ручного шага.

**GitOps** — модель, в которой желаемое состояние окружения (какая версия задеплоена, конфигурация) описано декларативно в git-репозитории, а отдельный контроллер (Argo CD, Flux) следит за расхождением между git и реальным кластером и сам приводит его в соответствие — деплой = merge PR в git-репо с манифестами, а не ручной `kubectl apply`.

**Канарейка (canary deployment)** — новая версия сначала раскатывается на небольшую долю трафика/подов (например, 5%), метрики сравниваются со старой версией, и только при отсутствии деградации доля постепенно увеличивается до 100%.

**Feature flag** — переключатель, скрывающий/включающий новую функциональность в рантайме, независимо от факта деплоя кода — позволяет задеплоить код "выключенным" и включить позже без нового деплоя, или откатить поведение мгновенно (флаг off) без отката всего релиза.

**Как был устроен процесс CI/CD:** после **push** в репозиторий автоматически запускался **GitLab Runner**, который выполнял CI/CD pipeline.

**1. Pull Request (CI).** При создании Pull Request запускались основные проверки качества кода.

**Code Quality:**
- `gofmt` / `gofumpt` — проверка форматирования кода.
- `go vet` — поиск потенциальных ошибок.
- `golangci-lint` — статический анализ кода (включает `govet` как один из линтеров — `go vet` отдельно нужен как быстрый ранний fail перед более медленным полным прогоном `golangci-lint`).

**Dependencies:**
- `go mod tidy` + `git diff --exit-code go.mod go.sum` — проверка, что зависимости в `go.mod`/`go.sum` уже "прибраны", без изменений после tidy.
- `go mod verify` — проверка целостности скачанных модулей.

**Contracts & Code Generation** (если проект использует gRPC):
- `validate proto` / `buf lint` — валидация и стиль `.proto` файлов.
- `buf breaking` — проверка отсутствия breaking changes (см. отдельный вопрос про ломающие изменения в protobuf).
- `go generate` / `protoc` — генерация кода, затем `git diff --exit-code` — проверка, что сгенерированный код закоммичен и не разошёлся со спекой.
- `migrations check` — проверка миграций БД.

**Tests:**
- `go test ./...` — unit-тесты.
- Coverage + Coverage Diff — покрытие относительно основной ветки (diff coverage, не общий процент).

**Build:**
- `go build ./...` — сборка приложения.
- `docker build` — сборка Docker-образа.
- После зелёного CI образ публикуется в Registry — это тот самый неизменяемый артефакт (см. Q4, git SHA-тег), который дальше **не пересобирается**, а лишь продвигается между окружениями.

**Что происходит после успешного CI:** дальше возможны разные варианты организации CD — у меня встречались оба.

**Вариант 1. Подход крупных компаний (Big Tech).** После прохождения CI:

- автоматически запускаются миграции (или подготавливаются к запуску);
- автоматический деплой в **Dev** — под каждую feature-ветку создаётся отдельное окружение, поднимается своя инфраструктура (БД, Kafka, Redis), разработчик может переключить фронтенд на свой backend для тестирования.

Для **Staging** и **Production** — отдельные дополнительные этапы:
- создание **release branch**, merge из `main/master`, повторная проверка миграций;
- **ручной approval перед прод** — апрувит тимлид/владелец сервиса (не сам автор PR — разделение ролей, чтобы не мержил и не деплоил один и тот же человек без второй пары глаз);
- деплой в Staging → после проверки — в Production.

**Вариант 2. GitOps.** Отдельный репозиторий с инфраструктурой (Kubernetes manifests, Helm/Kustomize, ArgoCD/Flux-конфигурации), свой набор конфигов на каждое окружение (dev/staging/production). Деплой = не `docker build` заново, а изменение манифеста (какой тег/SHA/версию деплоить) — контроллер сам приводит кластер в соответствие. Перед Staging дополнительно: security scan, approval, smoke- и e2e-тесты после деплоя.

**Как это соотносится с канарейкой/feature flag из определений выше:** в описанных двух вариантах прод-деплой — это **manual gate + постепенный rollout через approval**, не автоматическая канарейка с сравнением метрик — канарейка требует отдельной инфраструктуры (traffic splitting, автоматический анализ метрик), которая была не везде. Feature flags использовались отдельно от самого факта деплоя — рискованный код мог быть задеплоен в prod уже выключенным флагом, и включался позже вручную, независимо от pipeline.

**Откат:** за счёт иммутабельных тегов (Q4) откат — это просто повторный деплой предыдущего тега/SHA, без пересборки — занимает минуты, а не полный цикл CI заново.

### Q6. Как согласовывали миграции БД с деплоем (expand/contract, обратная совместимость)?

**A:**
**Сильный ответ:** expand (nullable колонка) → деплой → бэкфилл → contract — фазами. Никогда несовместимая схема + старый код одновременно.

**Слабый ответ:** большой bang-миграция в деплое без двух шагов — риск даунтайма.

**Мой ответ:**
При изменении схемы БД придерживаюсь подхода **Expand → Backfill → Contract**, чтобы обеспечить обратную совместимость между новой и старой версиями приложения и избежать простоя во время деплоя.

**1. Expand.** На первом этапе выполняются **обратно совместимые** изменения схемы. Например:

- добавляется новая **nullable** колонка;
- создаётся новая таблица;
- добавляется новый индекс.

На этом этапе **ничего не удаляется и не переименовывается**, поэтому старая версия приложения продолжает работать без изменений.

**2. Deploy.** После выполнения миграции деплоится новая версия приложения. Она должна уметь работать **одновременно со старой и новой схемой БД**, чтобы обеспечить безопасный rollout и возможность отката.

**3. Backfill.** Если необходимо перенести существующие данные, выполняется **backfill**. Это может быть:

- отдельная миграция;
- фоновый worker;
- batch-job.

На этом этапе данные постепенно копируются или заполняются в новой структуре, не влияя на работу пользователей.

**4. Contract.** После того как:

- весь трафик переведён на новую версию приложения;
- данные полностью перенесены;
- старая схема больше не используется,

можно безопасно удалить:

- старые колонки;
- старые таблицы;
- устаревшие индексы;
- другой больше неиспользуемый код.

**Главный принцип:** никогда нельзя допускать ситуацию, когда старая версия приложения работает с уже несовместимой схемой базы данных. Поэтому потенциально несовместимые изменения всегда выполняются **поэтапно**.

**Что означают этапы:**

- **Expand** — добавление новых объектов без нарушения обратной совместимости, например nullable-колонка, новая таблица, новый индекс.
- **Backfill** — постепенный перенос существующих данных в новую структуру.
- **Contract** — удаление старой схемы только после того, как новая версия приложения полностью перешла на неё.

### Q7. Откаты: что автоматизировано vs runbook?

**A:**
**Сильный ответ:** rollback в Kubernetes, предыдущий тег образа; откат БД сложен — часто forward-fix; runbook для данных.

**Слабый ответ:** откат не тестировали — деплой «на удачу».

**Мой ответ:**
Для отката приложения и базы данных используются разные подходы.

**Откат приложения.** Откат приложения обычно полностью автоматизирован. Если используется Kubernetes, можно:

- выполнить **rollback Deployment**;
- развернуть предыдущий Docker-образ по его тегу;
- вернуть предыдущий Helm Release (если используется Helm).

После этого Kubernetes постепенно заменяет новые Pod'ы предыдущей стабильной версией приложения.

**Откат базы данных.** С базой данных ситуация сложнее. Если миграции выполнялись по схеме **Expand → Backfill → Contract**, то после отката приложения старая версия обычно продолжает работать, так как схема остаётся обратно совместимой. Но если миграция уже изменила или удалила данные, полноценный rollback базы данных может быть невозможен или слишком рискован. Поэтому в production чаще используют **forward-fix** — не откатывают базу назад, а быстро выпускают новую версию приложения или новую миграцию, которая исправляет проблему.

**Что автоматизировано:** обычно автоматически выполняются:

- rollback Deployment в Kubernetes;
- переключение на предыдущий Docker-образ;
- восстановление предыдущего Helm Release;
- автоматический rollout предыдущей версии приложения.

**Что выполняется по Runbook:** обычно вручную или по заранее подготовленной инструкции (Runbook) выполняются:

- восстановление данных;
- исправление ошибочных данных;
- запуск SQL-скриптов;
- запуск backfill-job;
- выполнение сложных операций с БД.

**Что такое Runbook.** **Runbook** — это документ с пошаговой инструкцией по действиям во время инцидента. Он обычно содержит:

- последовательность действий при откате;
- необходимые команды;
- SQL-скрипты;
- проверки после восстановления;
- критерии успешного завершения работ.

### Q8. Вшивали ли метаданные сборки / git SHA в бинарники или лейблы контейнеров?

**A:**
**Сильный ответ:** `-ldflags` (version, commit, build time); OCI labels; связь логов с ревизией кода.

**Слабый ответ:** «не знаем, какая версия в проде» — кошмар инцидентов.

**Мой ответ:**
Да, это распространённая практика, которая позволяет быстро определить, какая именно версия кода сейчас работает в production.

**Метаданные в бинарнике.** Во время сборки в Go можно передать значения через `-ldflags`. Обычно в бинарник вшивают версию приложения (`version`), Git SHA (`commit`), время сборки (`buildTime`). Например:

```bash
go build -ldflags "-X main.version=v1.2.3 \
  -X main.commit=ab12cd34 \
  -X main.buildTime=2026-07-29T12:00:00Z"
```

После этого приложение может вернуть эту информацию через команду:

```bash
./app version
```

или через endpoint:

```text
GET /version
```

или

```text
GET /health
```

**Метаданные Docker-образа.** Кроме бинарника, ту же информацию обычно добавляют в Docker Image через **OCI Labels**. Например:

```dockerfile
LABEL org.opencontainers.image.version="v1.2.3"
LABEL org.opencontainers.image.revision="ab12cd34"
LABEL org.opencontainers.image.created="2026-07-29T12:00:00Z"
```

Эти метаданные позволяют быстро определить, какой именно образ запущен.

**Зачем это нужно.** Это значительно упрощает эксплуатацию системы. По Git SHA можно:

- определить, какой commit сейчас работает в production;
- быстро найти соответствующий Pull Request;
- понять, какой pipeline собрал этот образ;
- сопоставить ошибки в логах и метриках с конкретной ревизией кода.

Это особенно полезно при расследовании инцидентов и откате на предыдущую версию.

### Q9. Какие сбои пайплайна видели (кеш, флаки, лимиты ресурсов)?

**A:**
**Сильный ответ:** отравление кеша; OOM на раннерах; флаки; rate limit registry. Как отлаживали (локальный repro, verbose CI).

**Слабый ответ:** «это DevOps» без личного участия в отладке — слабо для senior.

**Мой ответ:**
За время работы чаще всего встречаются проблемы не в самом коде приложения, а в инфраструктуре CI/CD.

**1. Проблемы с кэшем (Cache).** Иногда используется устаревший или повреждённый кэш:

- кэш зависимостей (`~/go/pkg/mod`) — например, ключ кеша не учёл смену версии Go в `.golangci.yml`/toolchain, CI восстановил кеш от старой версии, и сборка падает на несовместимых артефактах, хотя локально (без чужого кеша) всё собирается нормально;
- кэш Docker-слоёв — закешированный промежуточный слой не инвалидировался при изменении зависимости выше по `Dockerfile`, и в образ попадает старая версия пакета;
- кэш сборки — аналогично, устаревшие промежуточные объекты компиляции.

Симптом всегда один: **локально всё работает, а в CI — нет**, при идентичном коде. Диагностируется отключением кеша (прогон "с нуля") — если проблема исчезает, дело именно в нём. Решается очисткой кеша и, если повторяется, пересмотром ключа кеша (чтобы он реально инвалидировался при релевантных изменениях, не только при смене `go.sum`).

**2. Недостаток ресурсов (OOM).** Во время сборки или запуска тестов Runner может превысить лимит памяти (**Out Of Memory**). Это часто происходит:

- при больших интеграционных тестах;
- при сборке крупных Docker-образов;
- при запуске нескольких тяжёлых процессов одновременно.

Решения:

- увеличить лимиты памяти Runner;
- уменьшить параллелизм;
- разбить пайплайн на несколько независимых Job.

**3. Flaky Tests.** Иногда тесты проходят локально, но периодически падают в CI. Основные причины:

- гонки данных (Race Condition);
- зависимость от времени;
- использование внешних сервисов;
- случайный порядок выполнения тестов.

Такие тесты стараются исправлять, а не просто перезапускать.

**4. Rate Limit Registry.** При публикации Docker-образов иногда возникают ограничения Registry. Например:

- слишком большое количество запросов;
- временная недоступность Registry;
- ошибки авторизации.

Обычно помогает повторная попытка (Retry) или настройка собственного Registry.

**Как отлаживали проблемы:** обычно использовали несколько подходов:

- воспроизводили проблему локально;
- запускали те же команды, что выполняет CI;
- включали подробный вывод (`--verbose`, `-v`);
- анализировали логи GitLab Runner;
- проверяли использование CPU, памяти и диска;
- при необходимости временно отключали кэш, чтобы убедиться, что проблема не связана с ним.
