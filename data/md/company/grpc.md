# REST vs WebSocket vs gRPC — база, от которой отталкиваться в ответах

## 1. REST

**Что это:** архитектурный стиль поверх обычного HTTP/1.1 (или HTTP/2) — строго **request-response**. Клиент всегда инициирует, сервер сам никогда ничего не "толкает" без предварительного запроса. Формат тела — обычно JSON, без строгой типизации на уровне протокола (типы проверяются только если явно подключить OpenAPI/JSON Schema).

**Когда применять:**
- Публичные API, где клиенты — сторонние разработчики, браузеры, мобильные приложения — простота и повсеместная поддержка важнее эффективности.
- CRUD-операции без реального времени: получить/создать/обновить/удалить ресурс.
- Когда нужна максимальная совместимость — HTTP понимают все: браузеры, curl, любой язык программирования без спецтулинга.
- Данные разовые/эпизодические — не нужен постоянно открытый канал.

**Не подходит для:** real-time обновлений, постоянного двустороннего обмена, высокочастотных вызовов между внутренними сервисами (накладные расходы на JSON + отсутствие мультиплексирования в HTTP/1.1).

Если всё же нужна "потоковость" поверх обычного REST, есть компромиссные техники — все однонаправленные или менее эффективные, чем настоящий стриминг:

- **Long polling** — клиент делает запрос, сервер держит соединение открытым, пока не появятся данные, потом отвечает, клиент тут же переспрашивает заново. Имитирует push ценой постоянных переоткрытий.
  - *Пример:* старые чаты и уведомления до массового распространения WebSocket (классический пример — ранние версии веб-мессенджеров).
  - *Минусы:* каждое переоткрытие — новый TCP/TLS handshake и HTTP-заголовки; сервер держит открытые соединения на каждого ожидающего клиента (расход памяти/файловых дескрипторов); при большом числе клиентов плохо масштабируется.

- **Short polling** — клиент просто дёргает эндпоинт каждые N секунд. Проще всего, но самый неэффективный и с наибольшей задержкой.
  - *Пример:* проверка статуса длительной фоновой задачи ("готов ли отчёт?") раз в 5 секунд из UI.
  - *Минусы:* задержка до N секунд между реальным событием и тем, когда клиент о нём узнает; впустую тратятся запросы, когда ничего нового нет — нагрузка на сервер растёт линейно с числом клиентов, даже если событий почти нет.

- **Webhooks** — сервер сам делает HTTP-запрос на эндпоинт клиента (клиент временно становится "сервером" для этого вызова). Push-уведомления без держания соединения открытым, но клиент должен сам выставлять доступный эндпоинт.
  - *Пример:* уведомление от Stripe/GitHub о событии (платёж прошёл, PR смёржен) — сторонний сервис сам стучится к вам, когда что-то случилось.
  - *Минусы:* клиенту нужен публично доступный HTTPS-эндпоинт (проблема для локальной разработки, мобильных/desktop-приложений за NAT); нужно самому реализовывать retry и защиту от дублей, если доставка не удалась с первого раза; нет гарантии порядка доставки нескольких webhook'ов.

- **Chunked transfer / SSE** — сервер отдаёт один ответ порциями, без ожидания пока весь ответ будет готов (см. Q4 ниже).
  - *Пример:* SSE — лента живых уведомлений в браузере (`EventSource`); chunked — стриминг ответа от LLM токен за токеном в чат-интерфейсе.
  - *Минусы:* только одно направление (сервер → клиент), для обратного канала всё равно нужен отдельный обычный REST-запрос; SSE держит одно долгоживущее HTTP-соединение на клиента — прокси/балансировщики с маленьким idle timeout могут его обрывать.

## 2. WebSocket

**Что это:** отдельный протокол (не REST, не HTTP-запрос в привычном смысле) — устанавливается через "апгрейд" из обычного HTTP-запроса, дальше работает как постоянно открытый двунаправленный (full duplex) канал поверх TCP. Формат сообщений — сырые байты/текст, никакой схемы из коробки, парсинг на вас.

**Когда применять:**
- **Браузер ↔ сервер** в реальном времени — это область, где WebSocket нативен (`new WebSocket(...)` работает из коробки везде), а альтернативы (gRPC bidi streaming) практически недоступны без обвязки.
- Чат, live-уведомления в UI, совместное редактирование в вебе, биржевые котировки на фронтенде.
- Нужен именно **один** постоянно открытый канал с обеих сторон, без строгой типизации сообщений.

**Не подходит для:** строгой типизации контракта (сами придумываете формат), множества независимых параллельных потоков через одно соединение (в отличие от HTTP/2 у gRPC), backend-to-backend взаимодействия, где важна кодогенерация клиентов.

## 3. gRPC

**Что это:** RPC-фреймворк поверх HTTP/2, контракт описывается в `.proto` (Protobuf) — строго типизированный, из него генерируется клиентский и серверный код на десятках языков. HTTP/2 даёт **мультиплексирование**: много независимых gRPC-вызовов/стримов через одно TCP-соединение без блокировки друг друга.

**4 вида RPC** (разбираются подробно ниже, Q1):
- **Unary** — один запрос, один ответ (как обычный REST-вызов).
- **Server Streaming** — один запрос, поток ответов.
- **Client Streaming** — поток запросов, один ответ.
- **Bidirectional Streaming** — независимые потоки в обе стороны одновременно (full duplex).

**Когда применять:**
- **Микросервис ↔ микросервис** — оба конца под вашим контролем, браузер не участвует напрямую.
- Нужна строгая типизация контракта между сервисами (Protobuf-схема как источник истины) и автогенерация клиентов.
- Высокочастотные внутренние вызовы — бинарный Protobuf компактнее и быстрее парсится, чем JSON.
- Любой из 4 паттернов стриминга (экспорт больших данных, bulk upload, real-time синхронизация между сервисами).

**Не подходит для:** прямого вызова из браузера без доп. слоя (нужен gRPC-Web + прокси, и то с ограничениями — bidi streaming через браузер практически недоступен), публичных API для сторонних разработчиков (менее привычно/удобно, чем REST+JSON).

## 4. Уровни сети — коротко, для общей картины

### Полная модель OSI (7 уровней) — для ориентира

| Уровень | Название | Что делает | Примеры |
|---|---|---|---|
| L7 | Application | Смысл данных для приложения | HTTP, gRPC, WebSocket, DNS |
| L6 | Presentation | Формат/кодировка данных | TLS-шифрование, сжатие, сериализация |
| L5 | Session | Управление сессией соединения | Установка/поддержание сессии (на практике часто сливается с L4/L7) |
| L4 | Transport | Доставка байтов между хостами | TCP, UDP |
| L3 | Network | Маршрутизация между сетями | IP |
| L2 | Data Link | Передача кадров внутри локальной сети | Ethernet, Wi-Fi, MAC-адреса |
| L1 | Physical | Сами биты — сигналы, кабель, радиоволны | Витая пара, оптика, радиоэфир |

На практике бэкенд-разработчику из всего этого регулярно нужны только **L7, L4 (иногда L6 из-за TLS)** — остальное (L1-L3, L5) обычно скрыто ОС и сетевым оборудованием.

### Как это выглядит для REST/gRPC/WebSocket конкретно

```text
L7 (Application)   REST → HTTP/1.1   gRPC → HTTP/2   WS → HTTP Upgrade → WebSocket Protocol
L6 (Presentation)  TLS (шифрование — обычно HTTPS/wss://, почти всегда включено)
L4 (Transport)     TCP (у всех троих; QUIC/UDP для HTTP/3 — отдельная тема)
L3 (Network)       IP
L2/L1              Ethernet / Wi-Fi
```

REST, WebSocket и gRPC — все живут на **L7**, просто используют разные протоколы поверх одного и того же транспорта (TCP) и одного и того же шифрования (TLS).

**L4 (Transport)** — отвечает только за доставку байтов между хостами (TCP: гарантирует порядок и доставку; UDP: без гарантий). L4 **не понимает**, что внутри — HTTP-запрос, gRPC-вызов или что-то ещё, для него это просто поток байт.

**L7 (Application)** — это уровень, где живёт смысл данных: HTTP-заголовки, пути, методы, gRPC-фреймы, WebSocket-сообщения.

**Почему это важно на практике:** балансировщики нагрузки бывают L4 и L7.
- **L4-балансировщик** распределяет по IP/порту, не заглядывая внутрь пакета — не понимает HTTP/2-мультиплексирование, поэтому не может грамотно раскидать отдельные gRPC-стримы внутри одного TCP-соединения.
- **L7-балансировщик** понимает HTTP/2 и может балансировать на уровне отдельных RPC-вызовов/стримов — то, что нужно для gRPC. Именно поэтому не любой прокси одинаково хорошо "стримит" (вспомните пункт про прокси в компромиссах Streaming из Q4).

### Q1. Unary vs server-streaming vs client-streaming vs bidirectional — реальный пример каждого?

**A:**
**Unary:** один запрос — один ответ. **Server-streaming:** один запрос — много ответов (большой поток, лог). **Client-streaming:** много запросов — один ответ (bulk upload). **Bidi:** двусторонние живые потоки — чат, синхронный обмен.

**Сильный ответ:** конкретная фича на каждый тип; знает, когда HTTP проще стриминга.

**Слабый ответ:** не различает типы стримов; путает с «WebSockets» вообще.

**Мой ответ:**
В gRPC есть четыре основных типа RPC, и выбор зависит от того, сколько сообщений отправляет каждая сторона.

**1. Unary (один запрос → один ответ)** — самый распространённый вариант: клиент отправляет один запрос, сервер возвращает один ответ.

Когда использовать:

- получение пользователя по ID;
- создание заказа;
- авторизация;
- обновление профиля.

**2. Server Streaming (один запрос → поток ответов)** — клиент делает один запрос, а сервер постепенно отправляет множество сообщений.

Когда использовать:

- просмотр большого списка данных;
- экспорт миллионов записей;
- поток логов;
- прогресс длительной операции.

Например, вместо того чтобы вернуть сразу миллион записей пользователей и занять много памяти, сервер может отправлять их небольшими порциями по мере чтения из базы. Главное преимущество такого подхода — клиент начинает получать данные сразу, не дожидаясь завершения всей операции.

**3. Client Streaming (поток запросов → один ответ)** — клиент отправляет множество сообщений, после чего сервер возвращает один итоговый ответ.

Когда использовать:

- bulk upload файлов;
- импорт большого количества данных;
- пакетная запись событий;
- отправка телеметрии.

Например, клиент может отправить тысячи записей о пользователях, а сервер после обработки всех данных вернуть итог: сколько записей успешно импортировано и сколько завершилось ошибкой.

**4. Bidirectional Streaming (поток запросов ↔ поток ответов)** — и клиент, и сервер одновременно отправляют сообщения независимо друг от друга.

Когда использовать:

- чат;
- онлайн-игры;
- биржевые котировки;
- совместное редактирование документов;
- постоянная синхронизация устройств.

Например, в чате каждый участник может одновременно отправлять сообщения и получать сообщения других пользователей, не ожидая окончания предыдущего запроса.

Unary (или обычный request-response, будь то REST или gRPC Unary) проще Streaming, когда нужно выполнить одну операцию и получить один ответ.

**Краткое сравнение:**

| Тип RPC | Клиент | Сервер | Пример |
|----------|---------|---------|---------|
| **Unary** | 1 запрос | 1 ответ | GetUser, CreateOrder |
| **Server Streaming** | 1 запрос | поток ответов | Логи, экспорт данных, список пользователей |
| **Client Streaming** | поток запросов | 1 ответ | Bulk import, загрузка файлов, телеметрия |
| **Bidirectional Streaming** | поток запросов | поток ответов | Чат, биржевые котировки, совместное редактирование |

### Q2. Как HTTP/2 связан с мультиплексированием и flow control в вашем опыте?

**A:**
**HTTP/2:** много потоков на одном TCP; сжатие заголовков; **HPACK**; flow control по потокам. gRPC использует фрейминг HTTP/2.

**Сильный ответ:** **head-of-line** vs HTTP/1.1; меньше соединений за NAT. Не нужно глубоко в HPACK без сетевой роли.

**Слабый ответ:** «gRPC бинарный — быстрый» — недостаточно.

**Мой ответ:**
gRPC работает поверх **HTTP/2**, и именно возможности HTTP/2 делают возможными эффективные RPC-вызовы и стриминг.

**1. Мультиплексирование (Multiplexing)** — главное преимущество HTTP/2. Оно позволяет передавать несколько независимых потоков (**streams**) через **одно TCP-соединение**. В HTTP/1.1 запросы по одному TCP-соединению выполнялись последовательно (если не использовать pipelining, который практически не применялся), поэтому клиенты обычно открывали несколько TCP-соединений к одному серверу для увеличения параллелизма. В HTTP/2 каждый запрос разбивается на небольшие **фреймы (frames)**. Фреймы разных потоков могут передаваться вперемешку по одному TCP-соединению, а затем на принимающей стороне собираются обратно в нужный поток. Для gRPC это означает, что несколько RPC-вызовов или stream'ов могут одновременно работать через одно TCP-соединение без необходимости открывать дополнительные соединения. Каждый независимый поток называется **Stream**.

**HTTP/1.1:** один запрос — один ответ. Следующий запрос обычно ждёт завершения предыдущего (или открывается новое TCP-соединение):

```text
TCP #1
Request 1 ──▶ Response 1

TCP #2
Request 2 ──▶ Response 2
```

**HTTP/2:** каждый запрос превращается в отдельный **Stream**. HTTP/2 разбивает каждый Stream на небольшие **Frames** и передаёт их вперемешку по одному TCP-соединению:

```text
             Одно TCP-соединение
Stream 1: A1 ─ A2 ─ A3
Stream 2: B1 ─ B2
Stream 3: C1 ─ C2

Передача:
A1 → B1 → A2 → C1 → B2 → A3 → C2
```

На принимающей стороне HTTP/2 собирает Frames обратно в нужный Stream.

**2. Flow Control** — HTTP/2 реализует механизм **Flow Control (управление потоком)**, который предотвращает ситуацию, когда быстрая сторона отправляет данных больше, чем медленная сторона успевает обработать. Для каждого потока и для всего соединения поддерживаются собственные **Flow Control Windows**. Пока получатель не увеличит окно передачи (**WINDOW_UPDATE**), отправитель обязан приостановить отправку данных. Это особенно важно для:

- Server Streaming;
- Client Streaming;
- Bidirectional Streaming.

Например, если клиент медленно читает поток сообщений, HTTP/2 автоматически ограничит скорость передачи данных, предотвращая переполнение памяти клиента.

**3. Фрейминг (Framing)** — HTTP/2 передаёт данные не целиком, а небольшими **фреймами**. gRPC сериализует сообщения (обычно с помощью **Protocol Buffers**), после чего HTTP/2 разбивает их на фреймы и отправляет по сети. На принимающей стороне фреймы собираются обратно в полноценные gRPC-сообщения. Именно этот механизм позволяет эффективно реализовать Streaming RPC.

**4. Сжатие заголовков (HPACK)** — HTTP/2 использует алгоритм **HPACK** для сжатия HTTP-заголовков. Поскольку в gRPC многие заголовки повторяются между запросами, это уменьшает объём передаваемых данных и снижает сетевые накладные расходы. Для большинства backend-разработчиков достаточно понимать, что HTTP/2 автоматически оптимизирует передачу заголовков — детали алгоритма HPACK обычно не требуются. Заголовки передаются **только в `HEADERS` Frame**, а данные — в `DATA` Frame.

**Head-of-Line Blocking:** в HTTP/1.1 существовала проблема **Head-of-Line Blocking**: запросы внутри одного соединения ожидали завершения предыдущих запросов либо приходилось открывать несколько TCP-соединений. HTTP/2 устраняет эту проблему **на уровне HTTP**, позволяя нескольким потокам выполняться параллельно внутри одного TCP-соединения. При этом важно помнить, что **Head-of-Line Blocking на уровне TCP остаётся**: если TCP-пакет потерялся, последующие данные также будут ждать его повторной передачи. Полностью эту проблему решает уже HTTP/3, который работает поверх QUIC.

### Q3. Дедлайны: как пробрасывали из gRPC Context вниз по вызовам?

**A:**
**Сильный ответ:** клиент ставит deadline; интерцепторы передают metadata; дочерние контексты наследуют оставшееся время; различают **timeout** и **cancel**.

**Слабый ответ:** игнор ctx в хендлерах — утечки ресурсов.

**Мой ответ:**
В gRPC управление временем жизни запроса строится на **context.Context**. Обычно **клиент задаёт deadline (или timeout)**, а сервер получает уже готовый `ctx`, содержащий информацию о дедлайне и возможности отмены запроса.

Контекст передаётся через все слои приложения без создания нового `context.Background()`:

```text
gRPC Handler
      │
      ▼
   Service
      │
      ▼
 Repository
      │
      ▼
PostgreSQL / Redis / gRPC / HTTP
```

Это позволяет автоматически отменять все операции, если клиент отменил запрос или истёк дедлайн.

**Дочерние контексты** создаются через `context.WithTimeout()` или `context.WithDeadline()`, но **не могут жить дольше родительского** — они всегда наследуют оставшееся время.

```go
dbCtx, cancel := context.WithTimeout(ctx, 3*time.Second)
defer cancel()
```

Если у родительского `ctx` осталось меньше 3 секунд, дочерний завершится раньше.

**Deadline, Timeout и Cancel:**

- **Deadline** — конкретный момент времени, до которого операция должна завершиться (`WithDeadline`).
- **Timeout** — максимальная продолжительность выполнения (`WithTimeout`).
- **Cancel** — явная отмена контекста (клиент закрыл соединение, вызван `cancel()`, завершился родительский контекст и т.д.).

Во всех случаях операции получают ошибку `context.Canceled` или `context.DeadlineExceeded`.

**Metadata и Interceptors:** через **gRPC Interceptors** обычно читают и добавляют **metadata**, например:

- Authorization;
- Request-ID;
- Trace-ID;
- Correlation-ID.

**Deadline передавать вручную не нужно.** Если клиент задал deadline, gRPC автоматически передаст его следующему сервису (через заголовок `grpc-timeout`) и восстановит его во входящем `context.Context`.

### Q4. Фича на server-streaming или bidirectional RPC. Почему стрим лучше chunked HTTP или polling?

**A:**
**Сильный ответ:** латентность (первый байт быстро), объём (не один огромный JSON), push с сервера. Компромиссы: сложность, прокси (часть L7 плохо стримит), история reconnect.

**Слабый ответ:** стриминг «потому что gRPC» без подбора задачи.

**Мой ответ:**
Я выбираю Streaming не потому, что использую gRPC, а потому, что он лучше подходит для определённых сценариев.

Если данные появляются постепенно или должны доставляться в реальном времени, **Server Streaming** или **Bidirectional Streaming** позволяют передавать сообщения сразу после их появления, без ожидания завершения всей операции.

Например:

- **Server Streaming** — поток логов, экспорт большого объёма данных, прогресс длительной операции.
- **Bidirectional Streaming** — чат, совместное редактирование документов, онлайн-игры, обмен событиями между сервисами.

Для обычных CRUD-операций или небольших ответов я бы использовал **Unary RPC**, поскольку он проще и легче поддерживается.

**Почему Streaming лучше, чем Polling и Chunked HTTP** — три причины (как в критериях сильного ответа):

**1. Латентность — первый байт быстро.** При polling (short/long, разобраны выше) клиент узнаёт о новых данных только на следующем опросе — задержка до целого интервала между запросами. При Streaming соединение уже открыто, сервер отправляет сообщение сразу после его появления — клиент получает первый байт данных максимально быстро, без ожидания следующего цикла опроса.

**2. Объём — не один огромный JSON.** Обычный HTTP-запрос при большом объёме данных формирует один большой ответ целиком на сервере, потом передаёт его целиком клиенту. Streaming отправляет данные небольшими сообщениями по мере готовности — клиент начинает обработку сразу, ниже потребление памяти на обеих сторонах.

**3. Push с сервера, а не постоянный опрос.** Сервер сам отправляет новые события, когда они появляются, а не ждёт, пока клиент спросит. Это убирает большинство "пустых" запросов polling и снижает сетевые накладные расходы.

**По сравнению именно с Chunked HTTP** (не polling) разница более тонкая — оба передают данные порциями по мере готовности. Но gRPC Streaming добавляет: двоичный Protobuf вместо текстового JSON, строгую схему сообщений, встроенный Flow Control HTTP/2 и полноценный Bidirectional (chunked — принципиально только одно направление, сервер → клиент). Chunked остаётся нормальным выбором для простых HTTP API; Streaming выигрывает, когда обе стороны уже на gRPC.

**Компромиссы Streaming** (то, ради чего вообще стоит спрашивать "а точно ли нужен стриминг?"):

- **Сложность** — сложнее обработка ошибок, нужно явно закрывать поток и освобождать ресурсы; логика клиента/сервера сложнее, чем один request-response.
- **Прокси** — часть L7-прокси, балансировщиков и API Gateway хуже поддерживают долгоживущие стриминговые соединения (буферизуют, режут по idle timeout).
- **Reconnect** — нужно продумывать стратегию переподключения и повторную доставку сообщений после разрыва (checkpoint/offset — подробнее в Q5 ниже).

Поэтому Streaming стоит использовать только тогда, когда его преимущества (латентность, объём, push) реально нужны — не "потому что gRPC".

### Q5. Back-pressure (медленный consumer) и ошибки посреди стрима?

**A:**
**Идея:** flow control HTTP/2; приложение не должно бесконечно буферить. Ошибки могут оборвать стрим; клиент обрабатывает частичный результат.

**Сильный ответ:** лимиты скорости, размер чанка, cancel при отключении клиента; статус RPC с **details**. Ретраи для стримов сложнее, чем unary.

**Слабый ответ:** нет идеи о медленном consumer — риск OOM.

**Мой ответ:**

**Проблема.** Back-pressure — это когда consumer (клиент) читает данные медленнее, чем producer (сервер) их отправляет. Если ничего не делать, сервер начинает бесконечно накапливать неотправленные данные в памяти — риск OOM.

**Базовый уровень защиты — HTTP/2 Flow Control.** Это встроенный механизм: сервер не может отправить больше данных, чем позволяет "окно" (window) получателя. Пока клиент не прочитает уже отправленное и не освободит окно, сервер физически не сможет слать новые данные — он просто блокируется на отправке. Это защищает от переполнения памяти автоматически, без участия вашего кода.

**Но приложение всё равно должно само контролировать три вещи:**

- **Лимиты скорости** — даже с Flow Control сервер может производить данные быстрее, чем нужно отдавать; ограничивают темп генерации (например, `time.Ticker` между отправками), чтобы не упираться в window HTTP/2 постоянно.
- **Размер чанка** — слишком мелкие сообщения увеличивают накладные расходы на каждое (заголовки, сериализация); слишком крупные — держат много данных в памяти одним куском и увеличивают задержку до первого байта. Размер подбирают под конкретный кейс.
- **Cancel при отключении клиента** — если клиент отвалился (закрыл соединение, истёк `ctx`), сервер обязан прекратить генерировать и отправлять данные немедленно, проверяя `ctx.Done()` на каждой итерации — иначе стрим продолжит впустую работать в фоне.

**Ошибки посреди стрима.** RPC завершается gRPC-статусом (`codes.Internal`, `codes.Unavailable` и т.д.), при необходимости — со структурированными `details`. Важно: клиент **не теряет** данные, которые уже успешно пришли до ошибки — он получает их плюс код/причину, почему стрим оборвался дальше.

**Почему retry для стрима сложнее, чем для unary.** В unary retry простой — либо весь запрос прошёл, либо нет, можно просто повторить целиком. В стриме к моменту ошибки часть сообщений уже могла дойти и быть обработана — повторить "всё с начала" означало бы задвоить уже обработанные данные. Поэтому вместо наивного retry используют:
- идемпотентные операции на стороне получателя (повтор с тем же ID не создаёт дубль);
- открытие нового стрима вместо повтора старого;
- возобновление с последней подтверждённой позиции (**checkpoint/offset**) — стрим продолжается не с нуля, а с места, где остановился.

### Q6. Нужны ли были heartbeat/keepalive на уровне приложения? Как настраивали idle timeout?

**A:**
**Сильный ответ:** keepalive (server/client), ping для мёртвых соединений; idle таймауты на **балансировщиках** — частая причина обрывов. App-heartbeat для длинных bidi через прокси.

**Слабый ответ:** нет настройки — стримы падают в проде непонятно почему.

**Мой ответ:**
**Keepalive** — это механизм проверки, что соединение всё ещё активно. Существует два вида:

- **TCP Keepalive** — работает на уровне TCP (Transport Layer, L4)), настраивается операционной системой и обычно использует большие интервалы (минуты или часы). Предназначен для обнаружения давно разорванных TCP-соединений.
- **gRPC Keepalive** — работает на уровне приложения (L7) и использует **HTTP/2 PING Frame**. Клиент и сервер периодически обмениваются PING, чтобы быстро обнаружить потерю соединения и поддерживать долгоживущие RPC.

**Heartbeat** — это уже механизм уровня приложения. Вместо служебного PING приложение само отправляет специальные сообщения вроде `"heartbeat"` или `"ping"`. Используется, когда нужно показать, что приложение продолжает работать, или не дать прокси и балансировщикам закрыть долго простаивающее соединение. Например:

```text
Client -----------------> Server
       HEARTBEAT
Client <----------------- Server
          OK
```

**Idle Timeout** — это максимальное время, в течение которого соединение может оставаться без активности. Если за это время не было ни данных, ни keepalive, балансировщик, прокси или сервер может закрыть соединение. Например:

```text
Idle Timeout = 60 секунд
0 сек      последнее сообщение
30 сек     тишина
60 сек     Load Balancer закрывает соединение
```

**PING для «мёртвых» соединений:** иногда соединение физически уже разорвано (например, пропал интернет), но TCP ещё не сообщил об этом приложению. Такое соединение называют **«мёртвым» (dead connection)**. Keepalive отправляет **HTTP/2 PING**. Если ответа нет за заданное время, соединение считается мёртвым и закрывается.

**App Heartbeat** — это heartbeat, реализованный самим приложением, а не транспортом. Он особенно полезен для **долгоживущих bidirectional stream**, когда по соединению долго нет обычных сообщений. Некоторые прокси или балансировщики не учитывают HTTP/2 PING или имеют свои ограничения, поэтому периодические heartbeat-сообщения помогают сохранить соединение открытым. Например:

```text
Client ---> HEARTBEAT
Server ---> HEARTBEAT_ACK
```

**Практический опыт:** в gRPC обычно использую встроенный **HTTP/2 Keepalive** — клиент и сервер периодически обмениваются **PING**, чтобы обнаруживать мёртвые соединения и не держать их открытыми бесконечно. Также важно учитывать **Idle Timeout** на сервере, прокси и балансировщиках (например, Nginx, Envoy, AWS ALB), так как они могут закрыть долго неактивный стрим. Поэтому интервалы keepalive должны быть меньше, чем настроенный idle timeout. Для обычных unary RPC встроенного keepalive обычно достаточно. Для **долгоживущих bidirectional stream**, особенно если между сообщениями бывают большие паузы, может дополнительно использоваться **application heartbeat** — специальные heartbeat-сообщения, которые поддерживают активность соединения и позволяют быстрее обнаружить потерю связи.

### Q7. Как версионировали и шарили .proto (Buf, git submodules, registry)?

**A:**
**Buf:** модули, lint, breaking — распространённый путь. Иначе: монорепо, submodule, артефакт прото.

**Сильный ответ:** CI на ломающие изменения; семантическое версионирование API-пакетов.

**Слабый ответ:** «все копируют .proto» — drift.

**Мой ответ:**
Обычно сервис-провайдер владеет контрактом API. `.proto` хранится в репозитории сервиса, где реализован gRPC-сервер, и является **Single Source of Truth**. Остальные сервисы используют именно этот контракт, а не поддерживают собственные копии.

Для распространения `.proto` используют разные подходы в зависимости от инфраструктуры компании:

- **Buf Schema Registry** — современный подход. CI публикует `.proto` (`buf push`), а остальные сервисы подключают его как зависимость. Buf также предоставляет генерацию кода, управление модулями, **lint** и проверку **breaking changes**.
- **Монорепозиторий** — все сервисы используют общую директорию с контрактами.
- **Отдельный Git-репозиторий** — подключается через Git Submodule или как обычная зависимость.
- **Proto как артефакт** — публикация схем в корпоративный Registry (например, Nexus или Artifactory).

При изменении API придерживаются **семантического версионирования** (`v1`, `v2`) и запускают в CI проверку **breaking changes**, чтобы не нарушить совместимость со старыми клиентами.

### Q8. Ломающие изменения в protobuf: номера полей, reserved, oneof — история миграции?

**A:**
Правила: не переиспользовать номера; **reserved** для удалённых полей; добавлять поля, не ломать семантику; **oneof** для вариантов. Учёт JSON-маппинга.

**Сильный ответ:** dual-write или флаги при раскатке; сохранение unknown полей.

**Слабый ответ:** «просто меняем proto» — ломает старых клиентов.

**Мой ответ:**
Главный принцип при эволюции Protobuf-контрактов — **не ломать существующих клиентов**. Поэтому предпочтительны только **обратно совместимые (additive) изменения**, а любые breaking changes требуют отдельной миграции или новой версии API.

**Какие изменения безопасны:** обычно безопасно:

- добавить новое поле;
- **добавить новый RPC** — расширяем сервис новым методом, не трогая существующие:
  ```proto
  service UserService {
    rpc GetUser(UserRequest) returns (UserResponse);
    rpc DeleteUser(UserRequest) returns (Empty);   // ← новый метод, добавлен позже
  }
  ```
  Старые клиенты просто не знают о `DeleteUser` и никогда его не вызывают — их код вообще не меняется и продолжает работать как раньше. Ломается только в обратную сторону: если **удалить** существующий RPC, старые клиенты, которые его вызывают, начнут получать ошибку `Unimplemented`.

- **добавить новое значение `enum`** — но только если клиенты написаны так, что не падают на незнакомом значении:
  ```proto
  enum Status {
    STATUS_UNKNOWN = 0;
    STATUS_ACTIVE = 1;
    STATUS_BANNED = 2;   // ← добавили позже
  }
  ```
  Проблема в том, **как клиент это обрабатывает**. Плохо — если клиент делает исчерпывающий `switch` без ветки по умолчанию:
  ```go
  switch status {
  case STATUS_ACTIVE: ...
  case STATUS_BANNED:  ...
  // ❌ нет default — старый клиент, который не знает про STATUS_BANNED,
  //    получив это значение, ничего не обработает и молча пропустит кейс (или упадёт, если ждал одного из известных значений)
  }
  ```
  Хорошо — клиент всегда предусматривает `default`/"неизвестное значение" как отдельный явный случай, тогда получение нового `enum`-значения от более новой версии сервера не ломает его, а просто обрабатывается как "неизвестный статус, безопасный fallback".

Старые клиенты, как правило, игнорируют неизвестные поля, поэтому добавление новых полей обычно не нарушает обратную совместимость.

**Что считается Breaking Change:** ломающими считаются:

- изменение номера поля (`field number`);
- изменение типа существующего поля;
- удаление поля без миграции;
- повторное использование номера удалённого поля;
- изменение семантики существующего поля или RPC.

Важно помнить, что в Protobuf сериализация основана именно на **номерах полей**, а не на их именах. Поэтому поле можно переименовать, сохранив его номер, но менять сам номер нельзя.

**Конкретный пример, почему переиспользование номера ломает всё:**
```proto
// было
message User {
  string old_email = 3;
}
// стало — переиспользовали номер 3 под другое поле
message User {
  int32 age = 3;
}
```
На проводе Protobuf хранит только `(номер поля, тип wire-формата, значение)` — имени поля там нет вообще. Старое сообщение, закодированное как `old_email = "a@b.com"`, при декодировании новой схемой будет прочитано как `age = <мусорные байты email'а, интерпретированные как int32>` — тихое повреждение данных без ошибки декодирования, самое опасное, что может случиться.

**Сохранение unknown-полей — отдельный важный момент.** Если сервис A получает сообщение с полем, которого не знает (например, старая версия схемы), Protobuf **не отбрасывает** это поле молча — оно остаётся в сообщении как "unknown field" и **сохраняется** при повторной сериализации/пересылке дальше. Это критично для промежуточных сервисов (gateway, прокси, message broker), которые пересылают сообщения, не зная всей схемы целиком — новое поле, добавленное production-сервисом A, долетит через промежуточный сервис B (который его не знает) в целости до сервиса C, который его понимает. Если бы unknown-поля отбрасывались, это сломало бы rolling deployment, где сервисы временно живут на разных версиях схемы.

**`reserved`:** если поле больше не используется, его лучше зарезервировать:

```proto
message User {
  reserved 3;
  reserved "old_email";
}
```

Это защищает от случайного повторного использования номера или имени поля в будущем и помогает избежать несовместимых изменений.

**`oneof`:** используют, когда сообщение может содержать только один из нескольких взаимоисключающих вариантов данных. Например:

```proto
oneof payment_method {
  Card card = 1;
  BankTransfer bank = 2;
}
```

Добавление нового варианта в `oneof` обычно возможно, но требует проверки совместимости всех клиентов и их бизнес-логики, поскольку старые клиенты могут не знать о новом варианте.

**История миграции:** если необходимо изменить существующее поле, обычно используют поэтапную миграцию:

1. добавить новое поле;
2. некоторое время записывать данные сразу в старое и новое поле (**dual-write**);
3. обновить всех потребителей;
4. перестать использовать старое поле;
5. пометить старое поле как `reserved`.

Если изменение затрагивает поведение системы, дополнительно могут использовать **feature flags** и **постепенный rollout**, чтобы безопасно перевести клиентов на новый контракт.

### Q9. Reflection vs сгенерированный код — что в сервисах?

**A:**
**Generated:** типобезопасность, скорость, дефолт для Go. **Reflection** (grpcurl, dynamic) — отладка, generic gateway.

**Сильный ответ:** знает цену reflection vs compile-time проверок.

**Слабый ответ:** не понимает reflection в контексте gRPC.

**Мой ответ:**
**Термины:**

- **Reflection** — механизм, позволяющий программе во время выполнения (**runtime**) получать информацию о типах, сообщениях и методах gRPC и работать с ними динамически, без заранее сгенерированного кода.
- **Runtime** — время выполнения программы.
- **Compile time** — этап компиляции, когда компилятор проверяет код ещё до запуска программы.
- **Типобезопасность (Type Safety)** — гарантия, что используются правильные типы данных. Ошибки (например, неверный тип аргумента или отсутствие поля) обнаруживаются компилятором ещё на этапе **compile time**, а не во время выполнения.
- **Generic Gateway** — универсальный gRPC Gateway или прокси, который может принимать и перенаправлять запросы к разным gRPC-сервисам, не имея заранее сгенерированных клиентов. Для этого он использует Reflection или дескрипторы `.proto`.

В продакшене практически всегда используют **сгенерированный код** (`protoc`). Он обеспечивает **типобезопасность**, высокую производительность и позволяет находить ошибки ещё на этапе **compile time**. Для Go это стандартный и рекомендуемый подход.

**Reflection** используют только там, где требуется динамическая работа с gRPC, когда типы неизвестны заранее. Например:

- **grpcurl** — вызов и исследование gRPC API без сгенерированного клиента;
- динамические клиенты и SDK;
- **Generic Gateway** или прокси;
- инструменты тестирования, диагностики и инспекции сервисов.

На практике бизнес-логика сервисов почти всегда работает со **сгенерированным кодом**, а **Reflection** используется для инфраструктурных задач, отладки и динамических сценариев.

Главный компромисс: **Generated code** быстрее, типобезопаснее и проверяется компилятором на этапе **compile time**, тогда как **Reflection** более гибкий, но имеет дополнительные накладные расходы и переносит часть проверок на **runtime**.

**Цена Reflection (Cost of Reflection)** — плата за гибкость. Reflection позволяет работать с типами динамически во время **runtime**, но за это приходится платить:

- ниже производительность (дополнительные проверки и поиск метаданных во время выполнения);
- отсутствие compile-time проверок типов;
- больше вероятность ошибок, которые проявятся только в runtime;
- код становится сложнее читать, поддерживать и рефакторить.
