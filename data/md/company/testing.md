### Q1. Что по вашим правилам тестируется юнитом, а что интеграцией?

**A:**
Unit: быстро, изолированно, детерминированно — чистая логика, замоканный I/O. Интеграция: реальная БД, HTTP, очередь — медленнее, ловит сборку и SQL.

**Сильный ответ:** язык пирамиды тестов; не тестировать фреймворки в юнитах; контрактные тесты на границе.

**Слабый ответ:** «всё интеграция» (медленно) или «только юниты» (пропуск SQL).

**Мой ответ:**
В основе моего понимания лежит **пирамида тестирования**. В её основании находятся unit-тесты — их должно быть больше всего, потому что они позволяют найти основную часть ошибок максимально рано, при этом они быстрые, дешёвые в поддержке, детерминированные и запускаются при каждом изменении кода. Выше располагаются интеграционные тесты, которые проверяют взаимодействие нескольких реальных компонентов системы — например, приложения с PostgreSQL, Kafka, Redis или внешними HTTP-сервисами. На вершине находятся End-to-End (E2E) тесты, которые проверяют полный пользовательский сценарий через всю систему. Они самые медленные, дорогие в поддержке и сложнее в диагностике, поэтому их обычно меньше всего.

**Слои — как названы в проекте vs как называются обычно:**

| Как называется у меня в проекте | Пакет | Как называется обычно (общепринятые термины) |
|---|---|---|
| Controller (HTTP и gRPC) | `internal/controller/http/v1`, `internal/controller/grpc/v1` | Handler / Transport Layer / Presentation Layer |
| UseCase | `internal/usecase` | Service / Application Layer / Business Logic Layer |
| Domain | `internal/domain` | Domain / Entity Layer (совпадает по названию) |
| Adapter (Postgres) | `internal/adapter/postgres` | Repository / Data Access Layer (DAL) / Persistence Layer |
| DTO | `internal/dto` | DTO (Data Transfer Object) — совпадает |

У меня — терминология из Clean Architecture (Robert C. Martin): Controller, UseCase, Entity/Domain — это точные термины из его диаграммы кругов. Структура проекта скопирована с популярного Go-шаблона evrone/go-clean-template, построенного по этой же диаграмме.

Handler, Service, Repository — более общие термины, не привязанные к одной доктрине, используются в большинстве туториалов и в общей индустрии (Repository вообще из отдельной традиции — Martin Fowler, PoEAA).

Разница только в словаре, не в поведении: Controller = Handler, UseCase = Service, Adapter/Postgres = Repository — один и тот же слой, разное название.

**На какие слои принято писать юнит-тесты:**

- Domain / Entity — да, всегда. Чистая логика, без I/O, моки не нужны.
- UseCase / Service — да, всегда. Зависимости (репозиторий, внешние клиенты) мокаются через интерфейсы.
- Handler / Controller — частично, только если есть нетривиальный маппинг ошибок в коды. Если тонкий — не тестируем юнитом, покрывается интеграционным тестом.
- Repository / Adapter (SQL, Kafka и т.п.) — нет. Мокать протокол/SQL бессмысленно, нужен реальный движок → интеграционные тесты.
- Сгенерированный код (gen/, .pb.go) — нет, не наша ответственность.

Правило: юнитами покрываем то, что является чистой логикой поверх интерфейсов (domain + usecase); всё, что реально говорит с внешней системой — только интеграционными тестами.

### Q2. Table-driven tests в Go: как оформили бы для чистой функции?

**A:**
Паттерн: `tests := []struct{ name; in; want }{...}` и `t.Run(tt.name, ...)`. Подтесты для изоляции и **parallel** где безопасно.

**Сильный ответ:** краевые случаи в таблице (пусто, nil, Unicode); хелперы фикстур; осторожность с `reflect.DeepEqual`.

**Слабый ответ:** копипаст тестов на каждый случай.

**Мой ответ:**
**1. Что это вообще такое (одно предложение):** вместо одной функции-теста на каждый сценарий — один список ("таблица") входов и ожидаемых результатов, и один цикл, который их все прогоняет.

**2. Базовый скелет — просто чтобы видеть форму:**

```go
func Test_Something(t *testing.T) {
    // === ARRANGE (подготовка) ===
    // было: код, который готовил мок/вход прямо в теле функции
    // стало: те же данные, но как строки таблицы — по одной на сценарий
    tests := []struct {
        name string // имя кейса
        in   string // вход
        want string // ожидаемый результат
    }{
        {name: "кейс 1", in: "a", want: "A"},
        {name: "кейс 2", in: "b", want: "B"},
    }

    for _, tt := range tests {
        t.Run(tt.name, func(t *testing.T) {
            // === ACT (действие) ===
            // было: вызов написан отдельно в каждой функции
            // стало: тот же вызов, но написан ОДИН раз для всех строк таблицы
            got := SomeFunc(tt.in)

            // === ASSERT (проверка) ===
            // было: проверка написана отдельно в каждой функции
            // стало: та же проверка, написана ОДИН раз для всех строк таблицы
            require.Equal(t, tt.want, got)
        })
    }
}
```

Это и есть весь паттерн. Всё остальное ниже — это отдельные "фичи", которые можно добавлять к этому скелету по одной.

**3. `t.Run` — зачем он вообще нужен:** `t.Run(tt.name, func(t *testing.T) {...})` — оборачивает каждый кейс в отдельный подтест.

Без него: если кейс 1 упадёт (например, паника или `t.Fatal`) — весь цикл прервётся, и вы не узнаете, что там с кейсом 2, 3, 4.

С ним: каждый кейс независим. Упал один — остальные всё равно прогонятся, и в консоли будет видно точно какой:

```text
--- FAIL: Test_Something/кейс_1
--- PASS: Test_Something/кейс_2
```

**4. `t.Parallel()` — что это и когда ставить:**

```go
t.Run(tt.name, func(t *testing.T) {
    t.Parallel() // <-- эта строка
    ...
})
```

Что делает: без неё Go гоняет подтесты один за другим, по очереди. С ней — говорит "этот новременно с другими такими же" (в отдельных горутинах). Итог — тесты проходят быстрее,особенно если их много.

Когда ставить — правило одно: если тест не трогает общее состояние — не пишет в одну и ту же переменную/файл/таблицу в БД, которую трогает другой тест одновременно. Для чистых функций (вход → выход, без сторонних эффектов) — всегда безопасно. Если тест мутирует что-то общее — не ставьте, будчайные падения теста.

**5. Краевые случаи в таблице (пусто, nil, Unicode):** смысл — таблица должна проверять не только "нормальный" вход, но и границы — там прячутся реальные баги.

| Тип краевого случая | Пример | Почему это важно |
|---|---|---|
| Пусто | `""` вместо `"Alex"` | Проверяет, что обязательное поле реально требуется, а не молча принимается |
| Nil | `nil` вместо указателя/слайса | В Go nil-слайс и пустой слайс `[]T{}` — разные вещи; nil-указатель может вызвать панику, если код его не ждёт |
| Unicode | `"Алексей"`, `"李雷"`, эмодзи | Русский/китайский текст занимает несколько байт на один символ. Если код где-то считает длину строки через `len()` (байты) вместо `utf8.RuneCountInString()` (симвоый не увидеть на латинице |
| Границы | ровно 255 и ровно 256 символов при лимите max=255 | Проверяет саму границу, а не за |

```go
{name: "empty name", in: "", wantErr: true},
{name: "unicode name", in: "Алексей 李雷", wantErr: false},
{name: "name at max length", in: strings.Repeat("a", 255), wantErr: false},
{name: "name over max length", in: strings.Repeat("a", 256), wantErr: true},
```

Идея: если тестировать только "нормальные" примеры вроде "Alex" — баги на границах никогдлько у реального пользователя в проде.

**6. Хелперы-фикстур — что это и зачем:** проблема — если вход не одно значение, а структура с несколькими полями, в каждой строке таблицы приходится повторять их все:

```go
{name: "case A", user: User{Name: "Ann", Email: "a@b.com", Phone: "+1555...", Age: 30}},
{name: "case B", user: User{Name: "",    Email: "a@b.com", Phone: "+1555...", Age: 30}}, ame
```

Читать это неудобно — непонятно с первого взгляда, что именно отличает "case B" от нормы.

Решение — функция-хелпер, которая строит валидный объект "по умолчанию", а конкретный кейс меняет только нужное поле:

```go
func validUser(opts ...func(*User)) User {
    u := User{Name: "Ann", Email: "a@b.com", Phone: "+1555...", Age: 30} // дефолт
    for _, opt := range opts {
        opt(&u) // применяем точечное изменение
    }
    return u
}
```

Использование в таблице:

```go
{name: "case A", user: validUser()},
{name: "empty name", user: validUser(func(u *User) { u.Name = "" })},
```

Теперь сразу видно: "empty name" — это норма, но с пустым именем. Ничего лишнего не нужно вычитывать.

**7. Осторожность с `reflect.DeepEqual` — конкретная ловушка:** `require.Equal` внутри себя (для не-примитивных типов) фактически делает то же, что reflectруктуры "по всем полям". Это ломается в двух известных местах:

`time.Time`: у него есть скрытое внутреннее поле ("монотонные часы"). Два значения времени,т одну и ту же секунду, могут не совпасть побайтово при сравнении структур, еслисоздавались по-разному (одно через `time.Parse`, другое вручную через `time.Date`).

```go
require.Equal(t, want, got)        // может ложно упасть
require.True(t, want.Equal(got))   // правильно: у time.Time есть свой метод .Equal()
```

`float64` / `NaN`: математическое свойство — `NaN != NaN`, даже сам с собой. Если в таблице случайно окажется `NaN`, сравнение всегда будет "не равно", и это не баг кода, а особенность плавающей точки.

**Пример полного unit-теста (AAA):**

```go
func Test_CreateUser_Success(t *testing.T) {
    transaction.IsUnitTest = true // 0. Настройка окружения теста

    // === ARRANGE (подготовка) ===
    postgres := new(mocks.Postgres)                        // 1. Создаём мок репозитория
    postgres.On("CreateUser", Any, Any).Return(nil)         // 2. Говорим моку: "если тебя вызовут с CreateUser — верни nil (успех)"
    postgres.On("SaveOutboxKafka", Any, Any).Return(nil)    // 2. Аналогично для второго метода
    defer postgres.AssertCalled(t, "CreateUser", Any, Any)  // 3. После теста проверим, что метод РЕАЛЬНО был вызван
    defer postgres.AssertCalled(t, "SaveOutboxKafka", Any, Any)

    u := usecase.New(postgres, nil) // 4. Собираем usecase с моком вместо реального Postgres

    input := dto.CreateUserInput{ // 5. Готовим входные данные
        Name: "Alex", Email: "alex@example.com",
        Phone: "+15551234567", BirthDate: "2000-01-01",
    }

    // === ACT (действие) ===
    output, err := u.CreateUser(context.Background(), input) // 6. Вызываем тестируемый метод

    // === ASSERT (проверка) ===
    require.NoError(t, err) // 7. Проверяем результат
    require.NotEqual(t, uuid.Nil, output.ID)
}
```

Три фазы (AAA) — это и есть структура, которую вы используете во всех пяти тестах:

1. Arrange — собрать мок, сказать ему что возвращать, собрать usecase, подготовить вход
2. Act — один вызов тестируемого метода
3. Assert — проверить, что вернулось (и что мок был/не был вызван)

**Что именно меняется по каждому пункту:**

| Пункт AAA | Обычные функции | Table-driven |
|---|---|---|
| Arrange | Код внутри каждой функции (создать мок, задать вход) | Превращается в данные — одна строка `{name, in, want}` в таблице |
| Act | Вызов метода написан заново в каждой функции | Написан один раз, в теле `t.Run`, переиспользуется для всех строк |
| Assert | Проверка написана заново в каждой функции | Написана один раз, там же, переиспользуется для всех строк |

### Q3. Coverage: трекаете в CI? Branch vs line? Порог и зачем?

**A:**
Line coverage — частая метрика; branch строже. Пороги (80%) можно обойти игрой — важнее смысл ассертов.

**Сильный ответ:** coverage в CI как сигнал, не единственный gate; diff coverage на PR; исключение сгенерированного кода. 100% часто не окупается.

**Слабый ответ:** «coverage бесполезен» или гонка за % без содержательных проверок.

**Мой ответ:**
**Line coverage** — самая частая метрика в CI, считает какие строки кода исполнились хотя бы раз. Даётся почти любым инструментом "из коробки" (`go tool cover`, jacoco, istanbul и т.д.) — низкий порог входа, поэтому и стандарт по умолчанию. Ничего дополнительного не нужно — встроено в стандартный Go toolchain:

```bash
go test -coverprofile=coverage.out -covermode=count ./...
```

**Branch coverage** строже — проверяет, что каждое условное ветвление (if/else, switch) пройдено в обе/все стороны, а не просто что строка с условием была исполнена хотя бы раз с одним из исходов. Line coverage может показывать 100%, а половина веток внутри if при этом ни разу не тестировалась. Go встроенно branch coverage не считает вообще — `go tool cover` даёт только line/statement coverage. Чтобы получить именно branch coverage, нужен сторонний инструмент, который инструментирует исходный код перед компиляцией (вставляет счётчики в каждую ветку if/else/switch), например gobco (`github.com/rillig/gobco`):

Порог (например, 80%) — не самоцель, и его легко обойти игрой: написать вызов кода без содержательного ассерта (просто дёрнуть функцию, ничего не проверив по существу) — строки исполнятся, метрика вырастет, а реальная проверка поведения не появится. Погоня за числом стимулирует именно такое поведение под дедлайн. Важнее смысл ассертов, чем процент покрытых строк — 60% с осмысленными проверками полезнее 95% с пустыми вызовами.

**Как использовать coverage правильно:**

- В CI — как сигнал, не единственный gate. Публиковать отчёт на PR для видимости, а не жёстко блокировать мердж по фиксированному проценту — иначе появляется стимул обходить метрику вместо того, чтобы писать содержательные тесты.
- Diff coverage важнее общего процента по репозиторию — проверять, покрыт ли именно новый/изменённый в PR код, а не общий процент, который может годами тащить непокрытый легаси и маскировать реальное состояние нового кода.
- Исключать сгенерированный код (кодоген, .pb.go, миграции и т.п.) из расчёта — тестировать чужой/автоматически сгенерированный код бессмысленно, он только портит метрику и создаёт ложное ощущение проблемы.
- 100% coverage часто не окупается — последние проценты обычно уходят на тривиальный boilerplate (геттеры, `String()`, error-wrapping), а не на реальную бизнес-логику; время дешевле потратить на качество ассертов в уже покрытых местах, чем на закрытие последних процентов.

### Q4. Флаки: как находили первопричину?

**A:**
Причины: время, гонки, random, внешние сервисы, общее состояние, порядок тестов.

**Сильный ответ:** карантин флаки; фикс корня; не `time.Sleep` без fake clock; retry в CI только в крайнем случае.

**Слабый ответ:** политика «перезапускать пока не зелёное».

**Мой ответ:**
Flaky test (флаки-тест) — тест, который непредсказуемо переключается между PASS и FAIL при повторных запусках без изменений в коде. Отличие от обычного бага: обычный тест ловит реальную регрессию детерминированно (упал → починили код → всегда проходит), а флаки-тест "иногда падает сам по себе" — доверие к красному/зелёному статусу CI теряется, что опаснее, чем кажется: команда начинает игнорировать красный CI ("а, это опять флаки"), и в этот момент реальные баги начинают проскакивать.

**Категории причин (что стоит держать в голове как чеклист):**

- Время — тест зависит от реального `time.Now()`/таймаутов, и на медленной/загруженной машине (CI-раннер) не укладывается в ожидаемое окно.
- Гонки (race conditions) — несколько горутин пишут/читают общие данные без синхронизации; тест иногда успевает проверить состояние до завершения асинхронной операции, иногда — после.
- Random — используется `math/rand` без фиксированного seed'а, и один из сгенерированных случаев ломает неявное предположение теста (например, генерируется пустая строка там, где тест не ожидал пустую строку).
- Внешние сервисы — тест реально стучится в сеть/БД/API, которые иногда недоступны/медленные/rate-limit'ят.
- Общее состояние — тесты пишут в общий пакетный `var`, общий файл, общую тестовую БД — и порядок/параллельность запуска влияет на результат.
- Порядок тестов — тест A неявно зависит от побочного эффекта, оставленного тестом B (сработавшим до него), и падает, если порядок изменился (например, при `-shuffle=on` или параллельном запуске).

**Как находили первопричину:**

1. Сначала — воспроизвести детерминированно, а не гадать по логам одного упавшего прогона:

```bash
go test -run TestX -count=100 ./...  # гоняем один тест много раз подряд
go test -race ./...                  # включаем детектор гонок
go test -shuffle=on ./...            # гоняем тесты в случайном порядке — ловит скрытые зависимости по порядку
```

   Если тест падает не при каждом запуске — уже сама частота падения (1 из 100 vs 1 из 3) подсказывает категорию: очень редкое падение чаще похоже на гонку по времени, частое — на явную зависимость от состояния/порядка.

2. Дальше — бинарный поиск по причине через изоляцию. Запускаем упавший тест в одиночку (`-run TestX`) — если проходит стабильно в одиночку, но падает в общем прогоне — почти наверняка "общее состояние" или "порядок тестов", а не внутренняя логика самого теста. Если падает и в одиночку — ищем внутри: гонка (`-race` покажет конкретную строку), либо зависимость от `time.Now()`/реального сетевого вызова.

3. `-race` детектор — если гонка, он прямо укажет, какие две горутины трогают одну переменную без синхронизации — это не догадки, а точный отчёт с двумя стек-трейсами.

4. Если внешняя зависимость (сеть/БД) — смотрим, есть ли в CI-логах именно ошибка соединения/таймаута в момент падения (а не логическая ошибка ассерта) — если да, причина внешняя, не в тестируемом коде.

### Q5. Как мокали зависимости: mockgen, ручные фейки, интерфейсы + заглушки?

**A:**
mockgen: быстро, но многословно. Ручные фейки: читаемо, похоже на поведение. Интерфейсы — узкие (идиома Go).

**Сильный ответ:** когда что; тесты ломаются при компиляции при смене интерфейса.

**Слабый ответ:** глобальные моки — плохо для параллельных тестов.

**Мой ответ:**
**mockgen** — генератор моков (`go.uber.org/mock/mockgen` или устаревший `golang/mock`) — по интерфейсу автоматически создаёт структуру-мок со строгой типизацией вызовов и ожиданий (`EXPECT().Method(args).Return(...)`). Есть и другие похожие генераторы (mockery поверх `testify/mock`) — суть та же, разница в синтаксисе.
```go
m := NewMockUserRepo(ctrl)
m.EXPECT().GetByID(1).Return(&User{Name: "Bob"}, nil)
```

**Ручные фейки (hand-written fakes)** — не сгенерированный код, а вручную написанная реализация интерфейса с упрощённой, но реальной логикой (например, `map[ID]Entity` вместо настоящей БД) — не просто фиксирует факт вызова, а реально ведёт себя похоже на настоящую зависимость.
```go
type FakeRepo struct{ data map[int]*User }
func (f *FakeRepo) GetByID(id int) (*User, error) { return f.data[id], nil }
```

**Интерфейсы + заглушки** — общий фундамент обоих подходов: зависимость абстрагируется узким интерфейсом (Go-идиома — интерфейс объявляется на стороне потребителя и содержит минимум методов, которые реально нужны), а в тесте подставляется любая его реализация — мок или фейк, тестируемому коду разницы нет.
```go
type UserRepo interface{ GetByID(id int) (*User, error) }
func NewService(repo UserRepo) *Service { return &Service{repo: repo} }
```

**Когда что использовать** — не "один способ всегда", а по ситуации:

- mockgen/генераторы — когда важно behavior verification: что было вызвано и с какими аргументами, а не как зависимость ведёт себя внутри. Быстро получить мок под любой интерфейс без ручного труда, но код многословный (много boilerplate на каждый метод) и он "чужой" — не читается как обычная бизнес-логика.
- Ручные фейки — когда важно state verification: как компонент реагирует на последовательность операций (например, что второй вызов видит результат первого). Читаются как обычный код, легче понять с первого взгляда, но требуют ручной поддержки — если реальная зависимость меняет поведение, фейк не обновится сам.
- Интерфейсы — узкие, по Go-идиоме (в духе `io.Reader`/`io.Writer` — 1-2 метода, максимум по числу реально используемых операций), объявлены на стороне потребителя (consumer-side interfaces), а не на стороне реализации — это даёт Interface Segregation "бесплатно": мокать/фейкать нужно ровно то, что реально используется, а не весь возможный контракт реализации.

**Сильная часть, которую обязательно проговорить:**

- "Когда что" — явно назвать критерий выбора (behavior vs state verification), а не просто перечислить варианты как взаимозаменяемые.
- Тесты ломаются на этапе компиляции при смене интерфейса — если интерфейс объявлен явно и мок/фейк реализует его типизированно, изменение сигнатуры метода в интерфейсе тут же обнаруживается компилятором в точке, где мок передаётся как аргумент этого интерфейсного типа — до того, как тест вообще запустится. Это ключевое преимущество перед, например, dynamic-typed языками, где несовпадение сигнатур всплывёт только в рантайме при вызове. Практика для усиления этой гарантии — явный compile-time assertion `var _ Interface = (*Mock)(nil)` в самом файле мока/фейка, чтобы ошибка проявлялась сразу при сборке пакета мока, а не только в точке использования.

### Q6. Когда fake (in-memory) лучше тяжёлого мок-фреймворка?

**A:**
Fake: реализует интерфейс с простым состоянием в памяти — читаемо, проверяет реальные сценарии. Моки с `Called()` — хрупки.

**Сильный ответ:** in-memory репозиторий для доменных тестов; моки для внешних систем.

**Слабый ответ:** «всё мокаем» — переуточнённые тесты.

**Мой ответ:**
**Fake** — реализует интерфейс с простым состоянием в памяти (например, `map[uuid.UUID]domain.User` вместо реального Postgres) — ведёт себя как настоящая зависимость: записали → можно прочитать, обновили → следующий вызов видит изменение. Читаемый обычный Go-код, без специального DSL.

**Тяжёлый мок-фреймворк** — сгенерированный код вокруг `Called(args...)`: не имитирует поведение, а просто фиксирует факт вызова и заранее прописанный ответ на него.

**Когда fake лучше:** когда важна последовательность операций и реальное состояние между вызовами (state verification), а не факт единичного вызова (behavior verification). Пример: тест на сценарий create→update→get — fake реально хранит данные, поэтому если код ошибся в порядке операций, тест упадёт по существу. С моком пришлось бы вручную прописывать возврат каждого следующего вызова — тест начинает симулировать правильное поведение сам, а значит ничего реально не проверяет.

Моки с `Called()`-стилем — хрупкие: тест жёстко завязывается на то, как именно вызывается зависимость (сколько раз, в каком порядке, с какими точными аргументами), а не на то, что должно получиться. Рефакторинг, не меняющий наблюдаемое поведение, легко ломает такой тест.

Дополнительно "тяжесть" фреймворка — это не только про state/behavior, но и про накладные расходы: объём boilerplate-кода, необходимость перегенерировать при любом изменении интерфейса, порог входа в синтаксис конкретного фреймворка (`.On()`/`.EXPECT()`/matchers). Fake — обычный Go-код, читается любым разработчиком без знания DSL.

**На практике:**

- In-memory fake-репозиторий — для доменных тестов, где важна корректность сценария целиком (create→update→get, инварианты), а не просто факт вызова.
- Моки — для внешних систем (платёжный шлюз, брокер сообщений), где важен именно контракт взаимодействия: что вызвано, сколько раз, с какими параметрами — а не что происходит "внутри" самой системы.

**Граница/риск, которую тоже стоит назвать:** fake оправдан, только пока интерфейс достаточно простой, чтобы имитация была дешёвой — для интерфейса с десятками методов и сложной семантикой fake становится дороже мока в поддержке. И fake несёт свой риск: он может незаметно разойтись с реальным поведением зависимости (например, не воспроизводить specific ошибку unique-constraint) и давать ложную уверенность — стоит периодически сверять его поведение с реальностью через интеграционный тест на том же контракте.

### Q7. Опыт с httptest для хендлеров?

**A:**
`httptest.ResponseRecorder` + `NewRequest` — без реального порта; быстрые тесты хендлеров.

**Сильный ответ:** table-driven, golden файлы или проверка status/body; тесты middleware.

**Слабый ответ:** только ручной curl.

**Мой ответ:**
Цель: `net/http/httptest` — пакет для тестирования HTTP-транспортного слоя (хендлеров/контроллеров) — того слоя, который принимает запрос, парсит его, вызывает бизнес-логику и формирует HTTP-ответ (коды, заголовки, тело). Внутри пакета — два разных механизма под разные задачи: один вообще без сети (порт не открывается), второй — с реальной сетью на loopback (порт открывается намеренно). Какой выбрать, зависит от того, что именно нужно проверить — сам хендлер в изоляции или весь HTTP-стек целиком.

**Минимальный пример — чтобы сразу было видно, что вообще происходит:**

```go
func helloHandler(w http.ResponseWriter, r *http.Request) {
    fmt.Fprintf(w, "Hello, %s", r.URL.Query().Get("name"))
}

func TestHelloHandler(t *testing.T) {
    req := httptest.NewRequest(http.MethodGet, "/hello?name=Alex", nil)
    rec := httptest.NewRecorder()

    helloHandler(rec, req)   // обычный вызов функции — не сервер, не сеть

    require.Equal(t, http.StatusOK, rec.Code)
    require.Equal(t, "Hello, Alex", rec.Body.String())
}
```

По шагам, что тут делает каждая строка:
- `httptest.NewRequest(...)` — строит `*http.Request` **в памяти**, без реального TCP-соединения — просто структура данных с методом, URL, телом.
- `httptest.NewRecorder()` — фейковая реализация `http.ResponseWriter`: вместо записи в сокет пишет в обычные поля структуры (`rec.Code`, `rec.Body`, `rec.Header()`).
- `helloHandler(rec, req)` — вызывается напрямую как обычная функция. Порт не открывается, сервер не запускается — весь "запрос" от начала до конца существует только в памяти текущего теста.
- `rec.Code` / `rec.Body.String()` — после вызова просто читаем, что хендлер туда записал, и сравниваем с ожидаемым.

**Два разных механизма внутри пакета, для разного уровня изоляции:**

- `NewRequest` + `NewRecorder` (как в примере выше) — без сети вообще. Тестирует сам хендлер: парсинг запроса, вызов зависимости, маппинг результата в HTTP-ответ.
- `NewServer` — поднимает настоящий сервер на случайном локальном порту, к нему стучится реальный `http.Client` по сети (localhost) — уже ближе к интеграционному тесту:
  ```go
  srv := httptest.NewServer(http.HandlerFunc(helloHandler))
  defer srv.Close()

  resp, _ := http.Get(srv.URL + "/hello?name=Alex")
  // реальный сетевой запрос на localhost, реальный роутинг/middleware/сериализация
  ```

Итог по слоям: Recorder+NewRequest — точечно про Controller/Handler-слой, в изоляции от сети; NewServer — про весь HTTP-путь целиком, но всё ещё без внешней инфраструктуры (БД, брокеров) — между чистым юнитом хендлера и полным интеграционным тестом.

Опыт — с первым механизмом, Recorder+NewRequest: тестирую хендлер без реального порта — быстро, детерминированно, безопасно параллелить (`t.Parallel()`), т.к. нет конфликта портов между тестами.

Дальше — то же самое, что в минимальном примере выше, только масштабированное на несколько сценариев сразу:

**Table-driven** — строка таблицы = HTTP-сценарий (тело запроса → ожидаемый статус/body), цикл через `t.Run`:

```go
tests := []struct {
    name       string
    body       string
    wantStatus int
}{
    {name: "valid", body: `{"name":"Alex"}`, wantStatus: http.StatusCreated},
    {name: "missing field", body: `{}`, wantStatus: http.StatusBadRequest},
}
for _, tt := range tests {
    t.Run(tt.name, func(t *testing.T) {
        req := httptest.NewRequest(http.MethodPost, "/users", strings.NewReader(tt.body))
        rec := httptest.NewRecorder()
        handler.ServeHTTP(rec, req)
        require.Equal(t, tt.wantStatus, rec.Code)
    })
}
```

Проверка ответа: точечно (`rec.Code` + распарсить нужные поля body) для простых случаев, или golden-файлы (`require.JSONEq` против эталонного JSON на диске, с флагом `-update` для осознанного обновления) — для больших/сложных ответов.

**Middleware — это обёртка вокруг хендлера** (например `recoverer` — ловит панику и отвечает 500 вместо падения сервера). Чтобы проверить саму обёртку, а не реальную бизнес-логику внутри хендлера, оборачиваю простую заглушку ("стаб") вместо настоящего хендлера:
```go
stub := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
    panic("boom")            // заглушка нарочно паникует
})
handler := recoverer(stub)    // recoverer — то, что реально тестируем

handler.ServeHTTP(rec, req)   // паника не долетает до теста — recoverer её поймал
require.Equal(t, http.StatusInternalServerError, rec.Code)
```
Настоящего роутера со списком реальных хендлеров тут нет — только один middleware и одна искусственная заглушка, поэтому тест проверяет ровно одну вещь (работает ли `recoverer`), а не всю систему хендлеров сразу.

### Q8. Интеграционные тесты против реальной БД или контейнеров (Testcontainers, docker-compose в CI)?

**A:**
Testcontainers: поднимает БД в CI; compose для локалки + CI. Цена: медленнее CI, флаки при нехватке ресурсов.

**Сильный ответ:** миграции в сетапе; очистка между тестами; параллельный прогон / шардирование suite.

**Слабый ответ:** «как в проде» только вручную.

**Мой ответ:**
**Определения:**

- Testcontainers — контейнер (Postgres, Kafka) поднимается программно из кода теста, на случайном порту, уничтожается после прогона — полная изоляция и воспроизводимость без предварительной настройки.
- docker-compose — инфраструктура поднимается отдельным шагом до тестов, тесты подключаются к уже работающим сервисам по фиксированному адресу.

У меня — docker-compose, та же инфраструктура для локальной разработки и CI (`make up` → `make integration-test`). Testcontainers предпочёл бы, если бы важна была воспроизводимость "из коробки" без предварительного шага поднятия compose-стека.

**Цена:** оба варианта на порядок медленнее юнитов (реальный I/O, реальный движок) и подвержены флакам при нехватке ресурсов CI-раннера — контейнер долго стартует под нагрузкой, health-check не успевает, таймаут.

**Как реализовано у меня сейчас** (честно, как есть, без приукрашивания):

- **Расположение:** `test/integration/`, билд-тег `//go:build integration` — не собираются в обычный `go build`/`go test`, только явно (`make integration-test`).
- **Инфраструктура:** docker-compose, не Testcontainers — `make up` поднимает Postgres/Kafka заранее, тесты подключаются по фиксированным `localhost:5432` и т.д.
- **Запуск сервиса:** внутри теста реально стартует весь `app.Run()` (не мокается ничего) — `SetupSuite()` поднимает HTTP+gRPC+воркер+consumer как в проде, только на реальном тестовом Postgres/Kafka.
- **Миграции:** `ResetMigrations()` в `SetupSuite` — `migrate.Down()` + `migrate.Up()` один раз перед всем сьютом, приводит схему к чистому состоянию **перед стартом**.
- **Клиент:** типизированный HTTP-клиент, сгенерированный из той же OpenAPI-спеки (`user_client`, обёртка над `gen/http/user_v1/client`) — тесты бьют по реальному HTTP, как настоящий потребитель API.
- **Изоляция между тестами:** нет truncate/rollback между отдельными тестами (`SetupTest`/`TearDownTest` пустые) — вместо этого уникальные тестовые данные (разные email/имена в каждом тесте), чтобы тесты не конфликтовали друг с другом на общей БД.
- **Параллельность/шардирование:** нет — сьют гоняется последовательно, одним процессом.
- **CI:** отсутствует — запускается только вручную (`make up` → `make integration-test`).

**Фреймворк — `testify/suite`:** структура `Suite` встраивает `suite.Suite` (инфраструктура запуска, отчёты) и `*require.Assertions` (`s.NoError(...)` вместо `require.NoError(t, ...)`). `SetupSuite()`/`TearDownSuite()` — один раз до/после всех тестов; `SetupTest()`/`TearDownTest()` — перед/после каждого (у меня пустые). Каждый `func (s *Suite) Test_X()` — отдельный тест-кейс, framework находит их через reflection по префиксу `Test_`. Точка входа для обычного `go test` одна: `func Test_Integration(t *testing.T) { suite.Run(t, &Suite{}) }`.

**Что бы улучшил, но пока не сделано** (то, что обычно ожидают в сильном ответе):

- **Явная очистка между тестами** (truncate/rollback) вместо уникальных данных — текущий подход хрупкий: с ростом числа тестов риск случайного пересечения данных растёт, а debugging "почему тест иногда падает" усложняется.
- **Параллельный прогон** (`go test -p N`, каждому пакету — своя изолированная БД/схема или свой Testcontainers-контейнер) и **шардирование suite** по CI-джобам (matrix-стратегия: `strategy: matrix: shard: [1,2,3,4]`) — при росте числа интеграционных тестов линейное время CI станет узким местом, это решает обе проблемы.
- **CI-шаг** — сейчас интеграционные тесты запускаются только вручную, а значит легко забыть прогнать перед мержем; стоит добавить отдельный CI job (`make up && make integration-test` в GitHub Actions).

### Q9. Длительность suite? Параллелили, шардировали?

**A:**
**Сильный ответ:** целевое время; `t.Parallel()` где безопасно; разные job'ы CI; короткие vs ночные suite.

**Слабый ответ:** проверки по 2 часа на PR без оптимизации.

**Мой ответ:**
**Целевое время:** юниты — секунды на весь пакет, интеграционные — единицы минут. Это конкретная цифра, на которую ориентируюсь, а не абстрактное "побыстрее" — если suite начинает выходить за эти рамки, это сигнал заниматься оптимизацией, а не мириться с постепенным ростом.

**Измерение:** `go test -json` / `gotestsum` + сохранение истории в CI. Важен именно **тренд**, а не разовое число — тест, который постепенно растёт от прогона к прогону, сигнализирует о регрессии до того, как станет по-настоящему медленным.

**`t.Parallel()`** — включаю там, где тесты не делят мутируемое состояние; число одновременных прогонов регулируется флагом `-parallel N` (по умолчанию — `GOMAXPROCS`). Обязательно гоняю такие тесты ещё и с `-race` — сама параллелизация тестов часто становится источником новых флаки-тестов, а не только ускоряет прогон.

**Разные CI-джобы** — юниты и интеграционные тесты запускаю не последовательно одним шагом, а отдельными параллельными джобами, у каждого своё целевое время из первого пункта.

**Шардирование** — при росте suite один большой набор тестов делю на несколько групп (шардов), каждая гоняется в своей CI-джобе параллельно (matrix-стратегия). Шарды делю по **историческому времени выполнения**, а не просто поровну по числу тестов — иначе один шард с медленными тестами становится узким местом, пока остальные уже давно закончили.

**Короткие vs ночные suite** — быстрый обязательный набор гоняется на каждый PR и блокирует мерж при падении; более полный и дорогой набор (например, с расширенными сценариями или доп. нагрузкой) — по расписанию (ночью), не задерживая разработчиков в моменте.

Честно говоря, что это пока не реализовано, а не выдавая желаемое за действительное — сильнее звучит на интервью, чем плавно "и то, и это уже настроено".

### Q10. Кто владел падающими интеграционными тестами в пайплайне?

**A:**
**Сильный ответ:** явный владелец (команда чинит красный CI); не игнорировать красные сборки. CI как **gate** релиза.

**Слабый ответ:** «флаки пайплайна» как норма.

**Мой ответ:**
**Владелец** — команда/автор PR, который сломал сборку, а не выделенный "тестовый" человек/QA. Если интеграционный тест упал из-за конкретного изменения — ответственность на том, кто это изменение внёс, а не перекладывается на кого-то, кто "отвечает за тесты вообще". Если причина неочевидна (тест упал не в связанном PR, а стал нестабильным сам по себе) — владение переходит к команде, которой принадлежит тестируемый компонент (по code owners/области ответственности), а не остаётся "ничьим".

CI — gate, а не просто индикатор. Branch protection должен физически не давать смерджить PR с непройденными обязательными проверками — иначе "кто владеет падающими тестами" превращается в риторический вопрос: если можно смерджить и так, ответственность размывается и никто реально не чинит.

### Q11. Как тестировать идемпотентное потребление из очереди?

**A:**
**Сильный ответ:** симуляция дубликатов доставки; проверка одного побочного эффекта; ключ идемпотентности / таблица дедупликации; property-based тесты.

**Слабый ответ:** предполагает exactly-once — для большинства очередей неверно.

**Мой ответ:**
**Идемпотентность** — сколько раз ни обработай одно и то же сообщение (при at-least-once доставке дубли — норма), эффект должен быть только один.

**Как тестировать:**

1. Симулировать дубли напрямую — вызвать обработчик с одним и тем же сообщением N раз подряд, без реального Kafka (тестируем логику, не брокер).
2. Проверять не "не упало", а именно эффект — после N вызовов в БД должна быть ровно 1 запись, не 5. Это и есть суть проверки, а не факт отсутствия ошибки.
3. Проверить сам механизм дедупликации отдельно — запись ключа идемпотентности и применение эффекта должны быть в одной транзакции. Иначе есть окно гонки: упали между "записали ключ" и "применили эффект" — либо эффект потеряется, либо продублируется при повторе.
   ```go
   tx.Exec("INSERT INTO processed_messages (id) VALUES ($1)", msgID)  // упадёт на unique constraint, если дубль
   applyEffect(tx, msg)   // в той же транзакции
   tx.Commit()
   ```
4. Проверить конкурентные дубли, не только последовательные — запустить несколько горутин, обрабатывающих одно сообщение одновременно (реальный сценарий — rebalance партиций, два инстанса на миг оба считают себя владельцем). Последовательный тест гонку не поймает, параллельный — поймает.
5. Property-based — не один жёсткий кейс "2 дубля подряд", а случайное число/порядок повторов, проверяя один и тот же инвариант: результат после любого числа повторов = результат после одного вызова.
