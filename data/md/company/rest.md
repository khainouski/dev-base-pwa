### Q1. Resource-oriented URL vs RPC-стиль путей? Компромиссы?

**A:**
**Resource:** /users/123/orders — существительные, HTTP-глаголы к действиям — подходит CRUD и кеш. **RPC-стиль:** /getUserOrders — иногда яснее для операций не в стиле CRUD.

**Сильный ответ:** последовательность в API; стратегия версионирования; не смешивать стили хаотично. Знает **Richardson maturity model** в общих чертах.

**Слабый ответ:** «REST = JSON» только.

**Мой ответ:**
**Последовательность в API:** API должно быть единообразным. Если выбрали REST, придерживайтесь ресурсных URL и корректного использования HTTP-методов во всех эндпоинтах.

✅ Хорошо:
```http
GET    /users/123
POST   /users
DELETE /users/123
```

❌ Плохо:
```http
GET  /users/123
POST /getUser
POST /createUser
```

**Стратегия версионирования:** заранее определить способ версионирования и использовать его последовательно. Например:
```http
/api/v1/users
/api/v2/users
```

**Не смешивать стили хаотично:** REST должен быть основным стилем API. RPC допустим для сложных бизнес-операций, которые плохо ложатся на CRUD. Например:
```http
GET  /users/123
POST /calculateDeliveryPrice
POST /generateReport
```

**Richardson Maturity Model (RMM) (Модель зрелости Ричардсона)** — это модель зрелости REST API. Она показывает, насколько API следует принципам REST и использует возможности HTTP.

- **Level 0 — RPC через HTTP:** HTTP используется только как транспорт.
  ```http
  POST /api
  ```
  ```json
  {
    "method": "getUser",
    "id": 123
  }
  ```
- **Level 1 — Ресурсы:** появляются отдельные URL для сущностей, но HTTP-методы ещё используются не по назначению.
  ```http
  POST /users
  POST /orders
  ```
- **Level 2 — Полноценный REST:** используются ресурсы, HTTP-методы и статус-коды.
  ```http
  GET    /users/123
  POST   /users
  PATCH  /users/123
  DELETE /users/123
  ```
  Это уровень большинства современных REST API.
- **Level 3 — HATEOAS:** сервер вместе с данными возвращает ссылки на возможные дальнейшие действия.
  ```json
  {
    "id": 123,
    "links": [
      { "rel": "orders", "href": "/users/123/orders" }
    ]
  }
  ```

### Q2. Идемпотентность: какие методы должны быть идемпотентны? Как сделать идемпотентным POST при необходимости?

**A:**
Идемпотентны по замыслу: **GET, PUT, DELETE**; **PATCH** зависит. **POST** создаёт — по умолчанию не идемпотентен.

**Сильный ответ:** заголовок **Idempotency-Key** для платежей/заказов; хранилище дедупликации; безопасные ретраи с клиента. Понимает двойное создание при ретрае POST.

**Слабый ответ:** «POST всегда безопасно ретраить».
Идемпотентность означает, что повторное выполнение одного и того же запроса не меняет итоговое состояние системы. По семантике HTTP идемпотентны GET, PUT и DELETE, PATCH зависит от операции, а POST по умолчанию неидемпотентен. Если нужно сделать POST идемпотентным, например при создании платежей или заказов, используют заголовок Idempotency-Key. Сервер сохраняет ключ и результат выполнения, а при повторном запросе с тем же ключом возвращает сохранённый ответ, не создавая ресурс повторно.
Idempotency-Key обычно генерирует клиент для одной логической операции. При ретраях клиент отправляет тот же ключ. Сервер атомарно сохраняет его в Redis через SET NX с TTL. Если ключ новый, сервер выполняет операцию и сохраняет результат. Если ключ уже существует, сервер не выполняет операцию повторно, а возвращает сохранённый ответ или сообщает, что запрос ещё обрабатывается.

### Q3. Коды ответа: примеры для 409, 422, 429 — помимо 200/404/500?

**A:**
**409 Conflict:** конфликт состояния (например неверная версия). **422 Unprocessable Entity:** семантика плавает — часто бизнес/валидация (иногда везде 400 — важна последовательность). **429 Too Many Requests:** лимит с Retry-After.

**Сильный ответ:** **Problem Details** / JSON ошибки; единая карта кодов по API.

**Слабый ответ:** всё 500 или 200 с ошибкой в теле для всех сбоев.

**Мой ответ:**
**Problem Details** — стандартный JSON-формат ошибок (RFC 9457), чтобы все ошибки API выглядели одинаково.

```json
{
  "type": "validation-error",
  "title": "Validation failed",
  "status": 422,
  "detail": "Email is already registered"
}
```

Даже без Problem Details желательно использовать единую структуру ошибок:

```json
{
  "code": "EMAIL_ALREADY_EXISTS",
  "message": "Email is already registered"
}
```

**Единая карта кодов:** команда заранее определяет, какой HTTP-код использовать в каждой ситуации, и все сервисы придерживаются этих правил. Например:
- `404 Not Found` — ресурс не найден.
- `409 Conflict` — конфликт состояния.
- `422 Unprocessable Entity` — ошибка бизнес-валидации.
- `429 Too Many Requests` — превышен лимит запросов.
- `500 Internal Server Error` — внутренняя ошибка сервера.

**Итог:** желательно использовать единый формат ошибок (например, **Problem Details**) и единую карту HTTP-кодов, чтобы одинаковые ситуации во всех сервисах возвращали одинаковые коды ответов.

### Q4. Версионирование: URI vs заголовок; ломающие изменения — как выкатывали?

**A:**
**URI** (/v1/) vs **Accept** vs кастомный заголовок — влияние на кеш, обнаружение, CDN.

Ломающие изменения: новая версия, **deprecation**, dual-write или **expand/contract** для полей. Матрица совместимости клиентов.

**Слабый ответ:** тихие изменения JSON без версии.

**Мой ответ:**
Версионирование чаще всего делают через URI (`/v1/...`), реже через `Accept` или отдельный заголовок. При ломающих изменениях выпускают новую версию API, старую помечают как **Deprecated** и некоторое время поддерживают обе версии. Для плавой миграции часто используют подход **Expand/Contract**: сначала добавляют новые поля, затем переводят клиентов и только после этого удаляют старые.

### Q5. Какие роутеры (stdlib mux, chi, gin, echo, fiber)? Почему выбрали?

**A:**
**stdlib** — минимализм, стабильность. **chi** — лёгкий, идиоматичный. **gin/echo** — скорость, middleware. **fiber** — похож на Express; база fasthttp (другая семантика vs net/http).

**Сильный ответ:** знакомство команды, middleware, совместимость с http.Handler. Не только «самый быстрый фреймворк».

**Слабый ответ:** только бенчмарки без экосистемы и найма.

**Мой ответ:**
Для новых Go-проектов чаще встречаются:
1. net/http + http.ServeMux (Go 1.22+) — самый современный и рекомендуемый вариант для большинства REST API.
2. chi — очень популярный минималистичный роутер с хорошей системой middleware.
3. gin — один из самых популярных полнофункциональных веб-фреймворков.
4. echo — тоже распространенный веб-фреймворк.

**`net/http` / `ServeMux`** — стандартный роутер Go из пакета `net/http`. *Плюсы:* минимум зависимостей, стабильность, полная совместимость с `http.Handler`. Подходит для небольших сервисов и случаев, когда возможностей стандартного роутера достаточно.

**`chi`** — лёгкий и идиоматичный роутер поверх `net/http`. *Плюсы:*
- полностью совместим с `http.Handler`;
- минимум зависимостей и небольшой overhead;
- удобные вложенные роуты (`Route`, `Group`, `Mount`);
- богатая система middleware (логирование, recovery, timeout, request ID, CORS и др.);
- поддержка параметров пути (`/users/{id}`);
- хорошо масштабируется при большом количестве эндпоинтов;
- легко интегрируется с любыми библиотеками из экосистемы `net/http`;
- простая миграция со стандартного `ServeMux`.

Хороший выбор для большинства REST API и микросервисов без тяжёлого фреймворка.

**`gin` / `echo`** — полноценные HTTP-фреймворки с роутингом, middleware, binding и валидацией. *Плюсы:* много готовых возможностей, быстрое начало разработки. *Минус:*
- более сильная зависимость от конкретного фреймворка (vendor lock-in);
- код становится менее переносимым на другой роутер или стандартный `net/http`;
- используют собственный `Context` вместо стандартного `http.Handler`.

**`fiber`** — по стилю похож на Express.js и работает поверх `fasthttp`. *Плюсы:* удобный API и высокая производительность. Но `fasthttp` имеет другую семантику и не полностью совместим с экосистемой `net/http`: «работает поверх net/http» означает, что библиотека использует стандартную HTTP-экосистему Go (`http.Handler`, `http.Request`, `http.ResponseWriter`), а Fiber построен на `fasthttp` и использует собственные типы, поэтому не совместим с библиотеками, написанными для `net/http`.

**Итог:** мы выбирали роутер не только по бенчмаркам, а с учётом опыта команды, необходимых middleware и совместимости с `http.Handler`. Для обычного микросервиса я бы выбрал `chi`: он лёгкий, идиоматичный и сохраняет совместимость со стандартной библиотекой. `gin` или `echo` удобны, когда нужно больше готовой функциональности, а `fiber` стоит выбирать только при осознанной готовности работать вне стандартной экосистемы `net/http`.

### Q6. Middleware: auth, логирование, трейсинг, recovery — как строили цепочку?

**A:**
Порядок важен: **recover** снаружи; **tracing** рано; **auth** до хендлеров; логирование с request ID.

**Сильный ответ:** распространение Context; **OpenTelemetry**; panic даёт 500 без падения процесса.

**Слабый ответ:** нет recovery — риск в проде.

**Мой ответ:**
Middleware выполняются вокруг HTTP-обработчика. Порядок важен, потому что каждый следующий middleware может использовать данные, созданные предыдущим. Типичная цепочка:

```text
Request
    ↓
Recovery
    ↓
Request ID
    ↓
Tracing (OpenTelemetry)
    ↓
Logging
    ↓
Authentication / Authorization
    ↓
Handler
    ↓
Response
```

**Почему такой порядок:**
- **Recovery** ставят снаружи, чтобы перехватить `panic` в любом следующем middleware или handler, вернуть `500 Internal Server Error` и не уронить процесс.
- **Request ID** создают как можно раньше, чтобы один идентификатор использовался во всех логах и трассировках запроса.
- **Tracing** запускают рано, чтобы создать span и передать `trace_id` через `context.Context` во все последующие слои.
- **Logging** ставят после Request ID и Tracing, чтобы логи содержали `request_id`, `trace_id`, статус ответа и время выполнения.
- **Authentication / Authorization** выполняют до handler, чтобы не запускать бизнес-логику для неавторизованного пользователя.
- **Handler** вызывается только после прохождения всех проверок.

Данные запроса, пользователя, trace и дедлайны передаются дальше через `context.Context`.

**Итог:** порядок middleware важен, потому что каждый следующий слой использует контекст предыдущего. Снаружи ставим `Recovery`, чтобы перехватывать любые `panic`. Затем создаём `Request ID` и OpenTelemetry span, после чего логирование уже может записывать `request_id` и `trace_id`. Далее выполняем authentication и authorization, чтобы не допустить неавторизованный запрос до бизнес-логики. Все данные и дедлайны распространяются через `context.Context`.

### Q7. Валидация запросов: в хендлере или в домене?

**A:**
**Handler:** JSON/схема (форма, типы). **Домен:** бизнес-правила («дата окончания после начала»).

**Сильный ответ:** ясное разделение; сгенерированные типы из OpenAPI; ошибки в 422/400.

**Слабый ответ:** валидация только в БД — поздний сбой.

**Мой ответ:**
**Идея (в двух словах):** это не "хендлер vs домен" как физическое место в файле, а два разных вопроса — синтаксис (формат запроса) и семантика (бизнес-правила). Синтаксис проверяется на границе, до бизнес-логики; семантика — в домене, потому что должна работать одинаково независимо от транспорта (HTTP/gRPC/Kafka).

**Как должно быть:**
- Синтаксическая валидация (JSON парсится, обязательные поля присутствуют, типы данных корректны, формат — email/UUID/длина строки) — не пишется руками в хендлере, а описывается в самом контракте: OpenAPI-схема (required, format, minLength) или Protobuf + protovalidate/buf.validate. Из контракта генерируются типы (oapi-codegen, protoc), и валидация происходит автоматически на этапе биндинга запроса — до того, как выполнение дойдёт до бизнес-кода. Хендлер в этом случае получает уже гарантированно валидную по формату структуру и сам валидационный код не пишет — только маппинг DTO и обработку ошибок домена.
- Бизнес-валидация (дата окончания позже даты начала, пользователь не заблокирован, товара достаточно на складе, сумма не превышает лимит) — живёт в домене. Причины: во-первых, она требует знания предметной области, а не просто "правильной формы данных"; во-вторых, часто требует обращения к текущему состоянию (сходить в БД проверить остаток/уникальность), то есть не может быть чистой синтаксической проверкой; в-третьих — и это главное — она должна переиспользоваться из любого транспорта: HTTP, gRPC, Kafka-консьюмера, CLI. Если продублировать бизнес-правило в каждом хендлере отдельно, оно рано или поздно разойдётся между транспортами. Правильный паттерн — инкапсулировать правило в конструкторе/методе домена (NewOrder(...), order.Validate()), чтобы невалидный объект физически не мог быть создан, независимо от того, кто его создаёт.
- Домен не знает о HTTP/gRPC вообще — он возвращает типизированные доменные ошибки (ErrDateRangeInvalid, ErrLimitExceeded), а не HTTP-коды. Маппинг "доменная ошибка → код ответа" — обязанность транспортного слоя (хендлера), и один и тот же набор доменных ошибок мапится по-разному для HTTP и для gRPC (codes.InvalidArgument, codes.FailedPrecondition).

**Коды ошибок:**
- 400 Bad Request — не смогли даже понять запрос: битый JSON, нет обязательного поля, неверный тип, невалидный формат UUID/email. Это ловится на границе, до домена.
- 422 Unprocessable Entity — запрос синтаксически корректен, распарсился, все типы верны, но нарушает бизнес-правило (дата в прошлом, лимит превышен). Это возвращает домен через usecase.
- 409 Conflict, отдельно от обоих — запрос сам по себе валиден, но конфликтует с текущим состоянием системы (email уже занят, оптимистичная блокировка по версии).

**Итог:**
> Синтаксис — на границе транспорта, максимально автоматизированный за счёт генерации из контракта (OpenAPI/Protobuf), хендлер валидацию руками не пишет. Бизнес-правила — строго в домене, инкапсулированы в конструкторе или Validate()-методе, чтобы невалидный объект нельзя было создать в принципе, и чтобы правило переиспользовалось между всеми транспортами через общий usecase-слой. Домен возвращает только доменные ошибки, а маппинг в конкретный HTTP/gRPC код — задача транспортного слоя, при этом 400 (не поняли запрос) явно разведён с 422 (поняли, но не разрешено бизнес-правилами) и с 409 (конфликт с текущим состоянием).

### Q8. Spec-first (OpenAPI пишут, потом codegen) или code-first (аннотации → spec)?

**A:**
**Spec-first:** контракт до кода — хорошо для межкомандных API. **Code-first:** быстрее для маленьких сервисов; риск рассинхрона.

**Сильный ответ:** CI (линт spec, diff на PR). **Breaking-change** (Buf breaking, Spectral).

**Слабый ответ:** «спека не нужна» для публичных API — проблема сопровождения.

**Мой ответ:**
**Spec-first:** сначала пишут **OpenAPI-спецификацию**, согласовывают контракт с потребителями API, а затем по ней реализуют сервер и при необходимости генерируют модели или клиентский SDK. *Плюсы:*
- контракт согласован до написания кода;
- фронтенд и бэкенд могут работать параллельно;
- документация всегда существует с самого начала;
- меньше риск сломать клиентов.

**Code-first:** сначала пишут код обработчиков, а затем автоматически генерируют OpenAPI-документацию из кода или аннотаций. *Плюсы:* быстрее начать разработку; удобно для небольших внутренних сервисов. *Минус:* если не следить за спецификацией, она может перестать соответствовать реальной реализации.

**Что используют на практике:** для API, которыми пользуются другие команды или внешние клиенты, обычно выбирают **Spec-first**, потому что контракт важнее реализации. Для небольших внутренних сервисов часто используют **Code-first**, так как он позволяет быстрее разрабатывать. Независимо от подхода, в CI обычно проверяют OpenAPI:
- линтинг спецификации (например, Spectral);
- сравнение изменений спецификации на PR, чтобы не допустить **breaking changes**.

### Q9. Какие инструменты генерировали стабы/типы (oapi-codegen, go-swagger, openapi-generator)?

**A:**
**Сильный ответ:** называет инструмент и опыт (типы, интерфейсы хендлеров, стабы для тестов). Боль: конфликты merge, layout generated.

**Слабый ответ:** codegen не использовал — ок для внутренних API; для роли публичного API — уточнить глубину.

**Мой ответ:**
Инструмент: **oapi-codegen** — генерирую из OpenAPI YAML-спеки (api/http/user_v1.yaml) сразу два артефакта: серверные типы + интерфейс хендлера (strict server interface) и HTTP-клиент, отдельными generate-конфигами в gen/http/user_v1/server и gen/http/user_v1/client.

Опыт использования — по трём категориям:

- Типы — DTO запроса/ответа генерятся из схем спеки (CreateUserInput и т.п.), руками не пишутся, всегда синхронны с контрактом.
- **Интерфейсы хендлеров (главное):** беру strict-режим — хендлер получает типизированный `...RequestObject` и обязан вернуть один из сгенерированных `...ResponseObject` (union по кодам ответа — `CreateUser201JSONResponse`, `CreateUser409JSONResponse` и т.д.). **Компилятор сам проверяет**, что все объявленные в спеке коды ответа где-то обработаны — забыть 409 или 400 не получится.
- Стабы для тестов — сгенерированный клиент (gen/http/user_v1/client) использую как typed HTTP-клиент в интеграционных тестах — не пишу руками сборку запросов/парсинг ответов, тестовый код обращается к API так же типобезопасно, как продовый.

Параллельно для gRPC — классическая связка protoc + protoc-gen-go/protoc-gen-go-grpc из .proto-файла, тот же принцип: контракт — источник истины, код — производный.

Боль, с которой сталкивался:

- Конфликты при merge — сгенерированные файлы (*.gen.go, *.pb.go) закоммичены в репозиторий, поэтому при параллельном изменении спеки двумя разработчиками получаешь задублированный конфликт и в самой спеке, и в сгенерированном коде — руками его не разрешить, нужно перегенерировать заново отдельным шагом после мержа спеки.
- Layout generated-кода — держу gen/ физически отдельно от internal/, чтобы не спутать "чужой" регенерируемый код с ручным. **Риск, который у меня сейчас не закрыт:** нет CI-шага "generate + diff", который падал бы, если сгенерированный код разошёлся со спекой — спеку могли поменять и забыть перегенерировать.

### Q10. Как синхронизировали сгенерированный код с хендлерами в CI?

**A:**
**Сильный ответ:** go generate или шаг CI; регенерация при смене spec; падение PR при diff; **openapi-diff** на совместимость.

**Слабый ответ:** ручное копипаст — неизбежный drift.

**Мой ответ:**
При изменении OpenAPI-спецификации код должен быть заново сгенерирован. Обычно это автоматизируют:
1. Разработчик изменяет `openapi.yaml`.
2. Запускается генерация кода (`go generate` или отдельный скрипт).
3. CI проверяет, что весь сгенерированный код актуален.
4. Если после генерации появились изменения (`git diff` не пустой), PR завершается ошибкой — значит, разработчик забыл обновить generated-код.

Кроме этого, CI обычно проверяет саму спецификацию:
- линтинг OpenAPI (например, Spectral);
- проверку на breaking changes (например, с помощью `openapi-diff`), чтобы изменения не ломали существующих клиентов.

### Q11. Как шарили модели между сервисами (артефакт vs копипаст)?

**A:**
Варианты: общий модуль (Go), сгенерированный клиент SDK, артефакт OpenAPI JSON, Protobuf для gRPC. Компромисс: **связность vs скорость**.

**Сильный ответ:** версионированный артефакт; контрактные тесты потребителя.

**Слабый ответ:** копипаст структур — тихие расхождения.

**Мой ответ:**
Важно понимать, что между сервисами обычно шарят **не доменные модели**, а **DTO контракта** — структуры запросов и ответов (OpenAPI для REST, Protobuf для gRPC). Внутренние бизнес-модели каждого сервиса остаются независимыми.

**1. Копипаст DTO** — каждый сервис самостоятельно описывает одинаковые структуры. *Плюсы:* быстро начать; не нужна дополнительная инфраструктура. *Минусы:* модели со временем расходятся; ошибки обнаруживаются только во время работы системы.

**2. Общий модуль** — типы выносятся в отдельный Go-модуль, который подключают несколько сервисов. *Плюсы:* нет дублирования; компилятор сразу обнаруживает несовместимые изменения. *Минусы:* сервисы становятся сильнее связаны; обновление библиотеки требует синхронизации между командами.

**3. Контракт как артефакт (предпочтительный вариант)** — сервис-провайдер является **единственным источником правды** для API-контракта. Он хранит OpenAPI-спецификацию в своём репозитории и публикует её как **версионированный артефакт**. Потребители не копируют модели вручную, а используют именно этот контракт:
- генерируют клиент и DTO из OpenAPI;
- либо используют готовый SDK, если он публикуется отдельно.

Главное — потребители работают с **конкретной версией** контракта, а не автоматически получают последнюю версию. Это защищает от неожиданных breaking changes.

**Как обеспечивают совместимость:** обычно в CI проверяют линтинг OpenAPI, отсутствие breaking changes (например, `openapi-diff`) и контрактные тесты потребителя (Consumer-Driven Contracts, например Pact), чтобы убедиться, что изменения не ломают существующих клиентов.

**Компромисс:** главный компромисс — **связность vs автономность**. Общий модуль уменьшает дублирование, но сильнее связывает сервисы. Версионированный контракт позволяет сервисам развиваться независимо и считается более предпочтительным вариантом для микросервисной архитектуры.

**Итог:** между сервисами я предпочитаю шарить не внутренние модели, а контракт API. Провайдер является единственным источником правды: хранит OpenAPI-спецификацию, публикует её как версионированный артефакт, а потребители генерируют из неё клиент и DTO либо используют готовый SDK. Это снижает связанность сервисов и позволяет независимо выпускать новые версии. В CI дополнительно проверяются breaking changes и запускаются контрактные тесты, чтобы изменения не ломали существующих потребителей. Общий Go-модуль использовал бы только в тех случаях, когда сервисы действительно тесно связаны и находятся в одном жизненном цикле.

### Q12. Как добавить поле в версионируемый JSON-ответ, не ломая старых клиентов?

**A:**
**Сильный ответ:** только **аддитивные изменения** (опциональное поле, поведение по умолчанию); не переименовывать и не убирать без версии; поведенческие изменения всё равно ломают — флаги. Контрактные тесты старых клиентов.

**Слабый ответ:** «клиенты игнорируют неизвестные поля» — часто верно для JSON, но смена поведения всё равно ломает.

**Мой ответ:**
Главный принцип — делать только **аддитивные изменения** (backward-compatible changes). Можно безопасно:
- добавить новое **необязательное** поле;
- задать для него разумное значение по умолчанию;
- сохранить поведение существующих полей.

Например, до:
```json
{
  "id": 1,
  "name": "Alice"
}
```

После:
```json
{
  "id": 1,
  "name": "Alice",
  "avatarUrl": "https://..."
}
```

Такое изменение считается совместимым, если контракт допускает появление новых необязательных полей.

**Что нельзя делать без новой версии API** — следующие изменения считаются **breaking changes**:
- удаление поля;
- переименование поля;
- изменение типа (`string` → `number`);
- изменение обязательности поля;
- изменение смысла существующего поля.

В таких случаях обычно выпускают новую версию API.

**Важный нюанс:** обратная совместимость — это не только структура JSON, но и **поведение сервиса**. Даже если формат ответа не изменился, клиентов могут сломать: новая бизнес-логика, изменение значений существующих полей, изменение семантики или порядка выполнения операций. Для таких изменений часто используют:
- **Feature flags** — новая логика скрывается за флагом и включается только для части пользователей или клиентов. Это позволяет безопасно протестировать изменение и быстро отключить его при возникновении проблем.
- **Постепенный rollout (Canary/Rolling deployment)** — новая версия сервиса выкатывается постепенно (например, сначала на 5% трафика, затем на 20%, 50% и 100%). Это позволяет вовремя обнаружить проблемы и минимизировать их влияние.
- **Новую версию API** — если изменение несовместимо с предыдущим контрактом (breaking change), создают новую версию API (например, `/v2/users`), а старую продолжают поддерживать до миграции всех клиентов.

**Как это контролируют:** в CI обычно выполняют проверку OpenAPI на breaking changes и контрактные тесты потребителей (Consumer-Driven Contracts), чтобы убедиться, что существующие клиенты продолжают работать.
