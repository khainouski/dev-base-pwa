# Базы данных

### 1. Транзакции, ACID (расшифровка), оптимистичные и пессимистичные блокировки, аномалии, уровни изоляции. select for update. {gen}

**Транзакция** — группа операций, которая выполняется целиком или не выполняется вовсе.

**ACID:**
* **Atomicity** — всё или ничего.
* **Consistency** — после транзакции данные удовлетворяют всем ограничениям (FK, CHECK, UNIQUE).
* **Isolation** — параллельные транзакции не видят «полуготовые» изменения друг друга.
* **Durability** — после `COMMIT` данные переживут падение сервера (WAL).

**Аномалии → уровни изоляции:**

| Уровень | Dirty read | Non-repeatable read | Phantom | Lost update / write skew |
|---|---|---|---|---|
| Read Uncommitted | возможен¹ | да | да | да |
| Read Committed (дефолт PG) | нет | да | да | да |
| Repeatable Read | нет | нет | нет в PG² | write skew — да |
| Serializable | нет | нет | нет | нет |

¹ В Postgres Read Uncommitted ведёт себя как Read Committed. ² В Postgres Repeatable Read реализован снапшотом, поэтому фантомов нет.

**Блокировки:**
* **Пессимистичная** — сразу блокируем строку: `SELECT ... FOR UPDATE`. Другие ждут. Хорошо, когда конфликты частые.
* **Оптимистичная** — не блокируем, а проверяем при записи по версии. Хорошо, когда конфликты редкие.

```sql
-- пессимистично
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;

-- оптимистично
UPDATE accounts SET balance = 900, version = version + 1
WHERE id = 1 AND version = 7;  -- 0 строк → кто-то успел раньше, повторяем
```

### 2. Что такое индекс? Зачем нужен? Может ли сделать запрос медленнее? Типы индексов в постгресе и монго + для каких операций какие нужны. Что такое btree? Сравнение с binary tree. AVL tree и красно-черные деревья. Составные индексы, префиксное правило. Селективность индексов, сложность поиска для btree, binary tree и hash. {gen}

**Индекс** — отдельная структура данных, по которой СУБД находит строки без полного скана таблицы.

**Может замедлить:** да — каждый `INSERT/UPDATE/DELETE` обновляет все индексы; лишние индексы занимают память и диск; при низкой селективности планировщик всё равно выберет seq scan.

**Типы в Postgres:**
* **B-tree** (по умолчанию) — `=`, `<`, `>`, `BETWEEN`, `ORDER BY`, `LIKE 'abc%'`.
* **Hash** — только `=`.
* **GIN** — массивы, `jsonb`, полнотекстовый поиск («содержит»).
* **GiST / SP-GiST** — геоданные, диапазоны, ближайшие соседи.
* **BRIN** — огромные таблицы, где данные физически упорядочены (логи по времени).

**Типы в Mongo:** single field, compound, multikey (массивы), text, 2dsphere (гео), hashed (для шардинга), TTL.

**B-tree vs binary tree:**
* Binary tree — у узла ≤2 потомков, высота большая → много обращений к диску.
* B-tree — у узла сотни ключей (узел = страница диска), дерево широкое и низкое: миллиард строк — это 3–4 уровня. Всегда сбалансировано.
* AVL и красно-чёрное — самобалансирующиеся *бинарные* деревья для памяти (AVL строже сбалансирован → быстрее поиск; RB дешевле вставка). Для диска не подходят — слишком высокие.

**Сложность поиска:** B-tree `O(log n)`, сбалансированное binary tree `O(log n)` (несбалансированное — до `O(n)`), hash `O(1)` в среднем, но без диапазонов и сортировки.

**Составной индекс и префиксное правило:** индекс `(a, b, c)` работает для `a`, `a,b`, `a,b,c`, но не для одного `b` или `c`.

```sql
CREATE INDEX idx ON orders (user_id, created_at);
-- ✅ WHERE user_id = 1
-- ✅ WHERE user_id = 1 AND created_at > now() - interval '1 day'
-- ❌ WHERE created_at > ...   (нет левого префикса)
```

**Селективность** = доля уникальных значений. Высокая (email, id) — индекс полезен; низкая (`is_active`, пол) — почти бесполезен.

### 3. Профилирование запросов, explain analyze, как по explain-у понять, медленно или быстро, красные флаги в выводе explain {gen}

* `EXPLAIN` — план, который выбрал планировщик (оценка).
* `EXPLAIN ANALYZE` — реально выполняет запрос и показывает фактическое время и число строк.
* `EXPLAIN (ANALYZE, BUFFERS)` — плюс сколько страниц прочитано из кэша и с диска.

**Как читать:** смотреть на самый «дорогой» узел по `actual time`, и сравнивать `rows` (оценка) с `actual rows` (факт).

**Красные флаги:**
* `Seq Scan` по большой таблице с фильтром, который возвращает мало строк — нужен индекс.
* Оценка строк отличается от факта в 10+ раз — устаревшая статистика, нужен `ANALYZE`.
* `Nested Loop` по большим наборам — должен был быть Hash/Merge Join.
* `Sort` с `external merge Disk` — не хватило `work_mem`.
* `Rows Removed by Filter` огромный — индекс не тот или не используется.
* Много `Buffers: read` вместо `hit` — данные не в кэше.

Для поиска медленных запросов в проде — `pg_stat_statements` и `log_min_duration_statement`.

### 4. MVCC, vacuum (analyze), autovacuum. {gen}

**MVCC** (Multi-Version Concurrency Control) — `UPDATE` в Postgres не меняет строку на месте, а создаёт новую версию; старая остаётся для транзакций, которые начались раньше. Поэтому **читатели не блокируют писателей и наоборот**.

Обратная сторона — копятся «мёртвые» версии строк (**bloat**).

* **VACUUM** — помечает место от мёртвых строк как свободное для повторного использования (файл не уменьшается). Ещё защищает от wraparound счётчика транзакций.
* **VACUUM FULL** — переписывает таблицу целиком и возвращает место ОС, но берёт эксклюзивную блокировку.
* **ANALYZE** — обновляет статистику для планировщика.
* **autovacuum** — фоновый процесс, запускает VACUUM и ANALYZE сам, когда изменилась заметная доля строк.

Проблемы на практике: длинная открытая транзакция не даёт VACUUM чистить; на таблицах с интенсивными апдейтами autovacuum приходится настраивать агрессивнее.

### 5. Виды джойнов и union. Where vs Having, агрегатные функции (примеры), оконные функции {gen}

**JOIN:**
* `INNER` — только совпавшие строки.
* `LEFT` / `RIGHT` — все строки одной стороны + совпавшие из другой (иначе `NULL`).
* `FULL` — все строки обеих сторон.
* `CROSS` — декартово произведение.

**UNION** склеивает результаты *по вертикали* и убирает дубли; `UNION ALL` — без удаления дублей (быстрее).

**WHERE vs HAVING:** `WHERE` фильтрует строки *до* группировки, `HAVING` — группы *после*.

**Агрегатные функции:** `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`.

```sql
SELECT user_id, SUM(amount) AS total
FROM orders
WHERE status = 'paid'          -- строки
GROUP BY user_id
HAVING SUM(amount) > 1000;     -- группы
```

**Оконные функции** считают по группе строк, но *не схлопывают* строки:

```sql
SELECT user_id, amount,
       ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC) AS rn,
       SUM(amount)  OVER (PARTITION BY user_id) AS user_total
FROM orders;
-- rn = 1 → последний заказ каждого пользователя
```

Частые: `ROW_NUMBER`, `RANK`, `LAG/LEAD`, `SUM ... OVER`.

### 6. Что такое хранимые процедуры? А триггеры? на чем писал (plpgsql)? {gen}

* **Хранимая процедура / функция** — код, который хранится и выполняется внутри БД (`plpgsql`, SQL). Плюс — меньше round-trip'ов, логика рядом с данными. Минус — бизнес-логика расползается по БД, её сложнее тестировать, версионировать и отлаживать.
* **Триггер** — функция, которая автоматически вызывается на `INSERT/UPDATE/DELETE` (до или после).

Типичное применение триггеров: `updated_at`, аудит изменений, денормализованные счётчики.

```sql
CREATE FUNCTION set_updated_at() RETURNS trigger AS $$
BEGIN
  NEW.updated_at := now();
  RETURN NEW;
END $$ LANGUAGE plpgsql;

CREATE TRIGGER t_upd BEFORE UPDATE ON users
FOR EACH ROW EXECUTE FUNCTION set_updated_at();
```

В Go-сервисах бизнес-логику обычно держат в коде, а в БД оставляют только такие технические вещи.

### 7. Связи one-to-one, one-to-many, many-to-many. {gen}

* **One-to-one** — `user` ↔ `user_profile`. FK с `UNIQUE` в одной из таблиц.
* **One-to-many** — `user` → много `orders`. FK `orders.user_id`.
* **Many-to-many** — `students` ↔ `courses`. Через промежуточную таблицу:

```sql
CREATE TABLE student_courses (
  student_id BIGINT REFERENCES students(id),
  course_id  BIGINT REFERENCES courses(id),
  PRIMARY KEY (student_id, course_id)
);
```

### 8. Какое поле обычно делают primary key? Плюсы и минусы serial vs uuid {gen}

Обычно — суррогатный ключ `id` (`BIGSERIAL`/`IDENTITY` или `UUID`), а не бизнес-поле вроде email: бизнес-данные меняются.

| | `serial` / `bigint` | `uuid` |
|---|---|---|
| Размер | 8 байт | 16 байт |
| Индекс | компактный, вставки в конец | у UUIDv4 случайные вставки → фрагментация B-tree |
| Генерация | только в БД | где угодно, в т.ч. на клиенте |
| Распределённые системы, шардинг | конфликты | без координации |
| Безопасность | id можно перебрать (`/users/5`) | не угадать |

Компромисс — **UUIDv7**: уникален глобально и упорядочен по времени, поэтому индекс не фрагментируется.

### 9. Что такое внешний ключ? Сослаться можно на любое поле или нет (кроме pk)? {gen}

**Внешний ключ (FK)** — ограничение: значение в колонке должно существовать в другой таблице. Гарантирует ссылочную целостность (нельзя сослаться на несуществующего пользователя).

Сослаться можно **не на любое поле**, а только на колонку (или набор колонок) с `PRIMARY KEY` или `UNIQUE`-ограничением — иначе ссылка была бы неоднозначной.

Поведение при удалении родителя: `ON DELETE CASCADE / SET NULL / RESTRICT`. FK-колонку стоит индексировать — иначе удаление родителя и джойны будут медленными.

### 10. SQL vs NoSQL. Вертикальное и горизонтальное масштабирование {gen}

| | SQL | NoSQL |
|---|---|---|
| Модель | таблицы, строгая схема | документы, ключ-значение, колонки, графы |
| Транзакции | полноценный ACID | часто ограниченные, eventual consistency |
| Запросы | JOIN, сложные выборки | под заранее известные паттерны доступа |
| Масштабирование | в основном вертикальное | изначально горизонтальное |

Выбор: сложные связи и деньги — SQL; огромный объём, простые запросы по ключу, гибкая схема — NoSQL.

* **Вертикальное** — более мощный сервер (CPU, RAM). Просто, но есть потолок и единая точка отказа.
* **Горизонтальное** — больше серверов: реплики для чтения, шардинг для записи. Потолка почти нет, но сложнее (распределённые транзакции, ребалансировка).

### 11. OLAP vs OLTP бд с примерами. {gen}

* **OLTP** (Online Transaction Processing) — много мелких быстрых операций с отдельными строками: заказы, платежи, пользователи. Строковое хранение. **Примеры:** PostgreSQL, MySQL.
* **OLAP** (Online Analytical Processing) — тяжёлые аналитические запросы по миллиардам строк: агрегаты, отчёты. Колоночное хранение, сжатие. **Примеры:** ClickHouse, BigQuery, Snowflake, Redshift.

Типичная схема: прод пишет в OLTP, данные через CDC/ETL уезжают в OLAP для аналитики.

### 12. Key-value stores. Redis: data types, common use cases, deployment & scaling, performance & features {gen}

**Key-value store** — хранилище «ключ → значение» с доступом только по ключу. Очень быстро, но без сложных запросов.

**Redis — типы данных:** String, List, Set, Sorted Set (ZSET), Hash, Stream, Bitmap, HyperLogLog, Geo.

**Use cases:**
* кэш (`SET key val EX 60`);
* сессии;
* rate limiting (`INCR` + `EXPIRE`);
* лидерборды (ZSET);
* распределённые блокировки (`SET key val NX PX 30000`);
* очереди и pub/sub, Streams.

**Деплой и масштабирование:**
* **Replication** — master + реплики для чтения.
* **Sentinel** — автоматический failover.
* **Cluster** — шардинг по 16384 hash slot'ам.

**Производительность:** всё в памяти, команды выполняются в одном потоке (I/O многопоточный) → нет гонок, сотни тысяч операций в секунду. Персистентность — RDB (снапшоты) и/или AOF (журнал). Минусы: объём ограничен памятью, одна тяжёлая команда (`KEYS *`) блокирует всех.

### 13. Redis, Postgres, Mongo, Cassandra - классифицируй по CAP теореме {gen}

**CAP:** при сетевом разделении (P) система выбирает между **C**onsistency и **A**vailability.

| БД | Класс | Почему |
|---|---|---|
| **Postgres** (primary + реплики) | CP | запись только в primary; без него запись недоступна |
| **MongoDB** (replica set) | CP | при потере большинства primary не выбирается, запись останавливается |
| **Cassandra** | AP | пишет на любой узел, сходится позже (настраивается через consistency level) |
| **Redis** (Sentinel/Cluster) | ближе к AP | асинхронная репликация — при failover последние записи можно потерять |

Важная оговорка: это упрощение. Многие БД настраиваются (у Cassandra `QUORUM` делает её ближе к CP, у Mongo — `writeConcern`/`readConcern`).

### 14. Что такое write concern и read concern в MongoDB {gen}

* **Write concern** — сколько узлов должно подтвердить запись, прежде чем драйвер вернёт успех.
  * `w: 1` — только primary (быстро, можно потерять при failover);
  * `w: "majority"` — большинство реплик (надёжно);
  * `j: true` — дождаться записи в журнал.
* **Read concern** — какие данные можно читать.
  * `local` — что есть на узле сейчас (может откатиться);
  * `majority` — только подтверждённое большинством;
  * `linearizable` — самое свежее и строгое, медленно.

Компромисс — скорость против надёжности. Для денег: `w: "majority"` + `readConcern: "majority"`.

### 15. Как обновить только одно поле у документа, не перезаписав весь документ? {gen}

Оператором `$set` — он меняет только указанные поля:

```js
db.users.updateOne(
  { _id: id },
  { $set: { email: "new@mail.com" } }
)
```

Без `$set` (`replaceOne` или update целым документом) документ заменится полностью. Другие частичные операторы: `$inc`, `$unset`, `$push`, `$pull`.

### 16. Как удалить все документы с условием (deleteMany) и чем это отличается от drop()? {gen}

```js
db.orders.deleteMany({ status: "cancelled" })  // по условию
db.orders.drop()                               // коллекция целиком
```

* `deleteMany` удаляет документы по одному: медленно на больших объёмах, коллекция и **индексы остаются**.
* `drop()` удаляет коллекцию целиком вместе с индексами — мгновенно.

Чтобы очистить всё, но сохранить индексы — `deleteMany({})`; если не жалко индексов и важна скорость — `drop()` и создать заново.

### 17. Как выбрать только некоторые поля из документа (projection)? {gen}

Вторым аргументом `find` — projection: `1` — включить поле, `0` — исключить.

```js
db.users.find(
  { age: { $gt: 18 } },
  { name: 1, email: 1, _id: 0 }
)
```

`_id` возвращается по умолчанию — его исключают явно. Смешивать `1` и `0` нельзя (кроме `_id`). Плюс: меньше трафика, а если все поля есть в индексе — запрос покрывается индексом.

### 18. Как искать в массиве: разница между $in, $all, $elemMatch? {gen}

* `$in` — поле совпадает **хотя бы с одним** значением из списка.
* `$all` — массив содержит **все** перечисленные значения.
* `$elemMatch` — **один и тот же элемент** массива удовлетворяет всем условиям сразу.

```js
{ tags: { $in:  ["go", "rust"] } }   // есть go ИЛИ rust
{ tags: { $all: ["go", "rust"] } }   // есть go И rust

// хотя бы один отзыв, где одновременно score > 4 и author = "ann"
{ reviews: { $elemMatch: { score: { $gt: 4 }, author: "ann" } } }
```

Без `$elemMatch` условия по массиву объектов могут сработать на *разных* элементах.

### 19. Как понять, используется ли индекс в Mongo запросе? {gen}

Через `explain`:

```js
db.orders.find({ userId: 42 }).explain("executionStats")
```

Смотреть:
* `winningPlan.stage`: **`IXSCAN`** — индекс используется, **`COLLSCAN`** — полный скан коллекции.
* `totalDocsExamined` vs `nReturned` — в идеале близки. Просмотрено 1 млн, вернулось 10 — плохой индекс.
* `executionTimeMillis` — время.

В проде медленные запросы ловит **profiler** (`db.setProfilingLevel(1, { slowms: 100 })`).

### 20. Разница между sparse и partial index? {gen}

* **Sparse** — индексирует только документы, **где поле существует**.
* **Partial** — индексирует только документы, **подходящие под произвольный фильтр**. Более гибкий, рекомендуется вместо sparse.

```js
db.users.createIndex({ phone: 1 }, { sparse: true })

db.orders.createIndex(
  { createdAt: 1 },
  { partialFilterExpression: { status: "active" } }
)
```

Оба экономят место. Но partial-индекс используется только если запрос содержит то же условие (`status: "active"`).

### 21. Что будет, если упадет primary в MongoDB? {gen}

1. Остальные узлы replica set перестают получать heartbeat (около 10 секунд).
2. Запускаются **выборы**: secondary с самыми свежими данными становится новым primary — если доступно **большинство** узлов.
3. Драйвер сам находит нового primary; с `retryWrites` запись повторится автоматически.

На время выборов (обычно секунды) **запись недоступна**, чтение с secondary возможно. Записи, которые старый primary не успел реплицировать, **откатываются** (rollback), когда он вернётся — поэтому для важных данных `w: "majority"`.

Если большинства нет (например, живой 1 узел из 3) — primary не выбирается, кластер работает только на чтение.

### 22. Как работает шардинг в MongoDB? {gen}

Данные коллекции делятся между несколькими **шардами** (каждый — свой replica set).

* **Shard key** — поле, по которому документы распределяются.
* **Chunks** — диапазоны значений ключа; **balancer** переносит их между шардами для равномерности.
* **mongos** — роутер: приложение подключается к нему, он отправляет запрос на нужный шард.
* **Config servers** — хранят карту «какой chunk на каком шарде».

Стратегии: **ranged** (хорошо для диапазонов, но риск «горячего» шарда при монотонном ключе вроде времени) и **hashed** (ровное распределение, но диапазонные запросы идут на все шарды).

Главное — правильный shard key: высокая кардинальность, равномерная запись и чтобы он был в большинстве запросов. Иначе запрос уходит на все шарды (scatter-gather).
