# Docker

### 1. Чем отличается докер от виртуальных машин? {gen}

* **Виртуальная машина** — эмулирует целый компьютер: у каждой ВМ **своё ядро ОС** поверх гипервизора. Сильная изоляция, но тяжело: гигабайты, старт за минуты.
* **Контейнер** — обычный процесс хоста, изолированный механизмами ядра (namespaces, cgroups). **Ядро общее** с хостом. Легко: мегабайты, старт за секунды, плотнее упаковка на сервере.

Минус контейнеров — изоляция слабее: уязвимость ядра затрагивает всех. Поэтому для недоверенного кода используют ВМ или gVisor / Firecracker.

---

### 2. Как его настроить, чтобы все работало быстро и безопасно? {gen}

**Быстро:**
* маленькие базовые образы (`alpine`, `distroless`, `scratch`);
* multi-stage build;
* правильный порядок слоёв: сначала зависимости (`go.mod`), потом код — кэш сборки не сбрасывается;
* `.dockerignore`;
* лимиты CPU и памяти, чтобы один контейнер не съел хост.

**Безопасно:**
* запуск **не от root** (`USER 65532`);
* read-only файловая система (`--read-only`), `--cap-drop ALL`, без `--privileged`;
* секреты не класть в образ и в `ENV`;
* сканировать образы на уязвимости (Trivy);
* фиксировать версии базовых образов (тег или digest, а не `latest`).

---

### 3. Как уменьшить размер образа? {gen}

* **Multi-stage build** — собираем в образе с компилятором, а в финальный копируем только бинарник.
* **Минимальная база** — `distroless` или `scratch` для статического Go-бинарника.
* **`.dockerignore`** — не тащить `.git`, тесты, локальные файлы.
* Объединять `RUN` и чистить кэш пакетного менеджера в том же слое.
* Собирать Go-бинарник без отладочной информации: `-ldflags="-s -w"`.

```dockerfile
FROM golang:1.26 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -ldflags="-s -w" -o /app ./cmd/api

FROM gcr.io/distroless/static
COPY --from=build /app /app
USER nonroot
ENTRYPOINT ["/app"]
```

Результат — вместо ~1 ГБ образ на 10–20 МБ.

### 4. Что такое Docker image и чем он отличается от контейнера? {gen}

* **Image** — неизменяемый шаблон: набор read-only слоёв (файловая система + метаданные: команда запуска, переменные).
* **Container** — **запущенный экземпляр** образа: поверх слоёв образа добавляется тонкий writable-слой, плюс процесс, сеть и ресурсы.

Аналогия из Go: образ — это тип (или бинарник), контейнер — запущенный процесс. Из одного образа можно запустить сколько угодно контейнеров. Изменения внутри контейнера пропадут вместе с ним — образ не меняется.

### 5. Что знаешь про docker-compose? Чем отличаются docker-compose и docker swarm? {gen}

**Docker Compose** — описывает несколько контейнеров в одном `docker-compose.yml` (сервисы, сети, тома) и поднимает их одной командой `docker compose up`. Работает **на одной машине**. Типичное применение — локальная разработка и тесты: сервис + Postgres + Redis + Kafka.

**Docker Swarm** — оркестратор: объединяет **несколько машин** в кластер, умеет реплики, rolling update, балансировку, перезапуск упавших контейнеров. Формат файла почти тот же (`docker stack deploy`).

Коротко: Compose — один хост, разработка; Swarm — кластер, прод. На практике в проде вместо Swarm почти всегда Kubernetes.

---

### 6. Как работать с секретами? {gen}

**Нельзя:** класть секреты в образ (`COPY .env`), в `ENV` в Dockerfile и в git — они остаются в слоях и истории.

**Можно:**
* передавать при запуске: `--env-file` (файл не в git);
* **Docker / Swarm secrets** — монтируются файлом в `/run/secrets/<name>`;
* в Kubernetes — `Secret` (лучше с шифрованием или External Secrets);
* внешние хранилища — HashiCorp Vault, AWS Secrets Manager;
* секреты **на время сборки** (приватный репозиторий):

```dockerfile
RUN --mount=type=secret,id=netrc,target=/root/.netrc go mod download
```

```bash
docker build --secret id=netrc,src=$HOME/.netrc .
```

Так секрет не попадает ни в один слой образа.

### 7. Как подождать другой сервис при старте? {gen}

`depends_on` сам по себе ждёт только **запуска** контейнера, а не готовности (Postgres стартовал, но ещё не принимает соединения).

**Правильно в Compose** — healthcheck + условие:

```yaml
services:
  db:
    image: postgres:17
    healthcheck:
      test: ["CMD", "pg_isready", "-U", "postgres"]
      interval: 2s
      retries: 15
  api:
    build: .
    depends_on:
      db:
        condition: service_healthy
```

**Надёжнее всего** — чтобы сам сервис при старте **ретраил подключение** с backoff: в проде (Kubernetes) порядок запуска никто не гарантирует. Старые способы — скрипты `wait-for-it.sh`, `dockerize`.

### 8. Что такое docker exec -it bash и зачем его используют? {gen}

`docker exec` запускает **новый процесс внутри уже работающего контейнера**:
* `-i` — держать stdin открытым;
* `-t` — выделить терминал (TTY);
* `bash` — запускаемая команда.

```bash
docker exec -it my-api sh       # в alpine нет bash — только sh
docker exec my-db psql -U postgres -c "select 1"
```

Зачем: отладка — посмотреть файлы, переменные окружения, сеть (`curl` до соседнего сервиса), зайти в БД.

В distroless и scratch оболочки нет вообще — там используют `docker debug` или `kubectl debug` с эфемерным контейнером.

### 9. Какие типы сетей поддерживает Docker? {gen}

* **bridge** (по умолчанию) — виртуальная сеть на хосте. В пользовательской bridge-сети контейнеры находят друг друга **по имени** (встроенный DNS). Наружу — через проброс портов `-p 8080:8080`.
* **host** — контейнер использует сеть хоста напрямую, без изоляции и NAT. Быстрее, но порты могут конфликтовать.
* **none** — сети нет вообще.
* **overlay** — сеть поверх нескольких хостов (Swarm), контейнеры на разных машинах общаются как в одной сети.
* **macvlan** — контейнер получает свой MAC и IP в физической сети, выглядит как отдельное устройство.

```bash
docker network create app-net
docker run --network app-net --name db postgres
docker run --network app-net my-api   # ходит на db:5432
```

### 10. Что такое volume и чем отличается от bind mount? {gen}

Оба нужны, чтобы данные жили **вне** контейнера.

* **Volume** — хранилище, которым **управляет Docker** (`/var/lib/docker/volumes/...`). Не зависит от структуры хоста, удобно бэкапить, работает одинаково везде. **Для данных в проде** (БД).
* **Bind mount** — монтирование **конкретной папки хоста** в контейнер. Полный доступ к файлам хоста. **Для разработки**: смонтировал код — изменения видны сразу.

```bash
docker run -v pgdata:/var/lib/postgresql/data postgres   # volume
docker run -v $(pwd):/app my-dev-image                   # bind mount
```

Ещё есть **tmpfs** — данные только в памяти, исчезают при остановке.

### 11. Как сделать, чтобы данные не потерялись после удаления контейнера? {gen}

Записывать их **не в файловую систему контейнера**, а в **volume** (или bind mount). Writable-слой контейнера удаляется вместе с ним, а volume живёт отдельно.

```bash
docker volume create pgdata
docker run -d -v pgdata:/var/lib/postgresql/data postgres:17
docker rm -f <id>   # контейнер удалён — данные в pgdata остались
```

Осторожно: `docker compose down -v` и `docker volume prune` **удаляют** тома. Для важных данных — регулярные бэкапы, а в облаке — управляемые БД вместо контейнера.

### 12. Чем отличается COPY от ADD в Dockerfile? {gen}

* **COPY** — просто копирует файлы с хоста в образ.
* **ADD** — то же, плюс «магия»: **распаковывает локальные tar-архивы** и умеет **скачивать по URL**.

Рекомендация — **всегда COPY**: поведение предсказуемо. `ADD` — только когда нужна именно распаковка архива. Для скачивания лучше `RUN curl ...` — так можно проверить контрольную сумму и почистить файл в том же слое.

### 13. Чем отличается ENTRYPOINT и CMD? {gen}

* **ENTRYPOINT** — что запускается всегда (исполняемый файл).
* **CMD** — аргументы по умолчанию, их легко заменить при `docker run`.

```dockerfile
ENTRYPOINT ["/app"]
CMD ["--port", "8080"]
```

```bash
docker run img                   # /app --port 8080
docker run img --port 9090       # /app --port 9090 (CMD заменён)
docker run --entrypoint sh img   # заменить ENTRYPOINT
```

Писать в **exec-форме** (`["..."]`), а не shell-форме (`ENTRYPOINT /app`): иначе процесс запускается через `sh -c`, становится не PID 1 и **не получает SIGTERM** — graceful shutdown не работает.

### 14. Как посмотреть логи контейнера? {gen}

```bash
docker logs my-api              # все логи
docker logs -f my-api           # следить в реальном времени
docker logs --tail 100 my-api   # последние 100 строк
docker logs --since 10m my-api  # за последние 10 минут
docker compose logs -f api      # в compose
```

Docker собирает то, что процесс пишет в **stdout/stderr** — поэтому приложение в контейнере должно логировать туда, а не в файлы. В проде логи забирает агент (Fluent Bit, Vector) и отправляет в Loki / ELK.

### 15. Как узнать, какие контейнеры запущены? {gen}

```bash
docker ps                       # запущенные
docker ps -a                    # все, включая остановленные
docker ps --format "table {{.Names}}\t{{.Status}}\t{{.Ports}}"
docker compose ps               # контейнеры текущего compose-проекта
docker stats                    # запущенные + потребление CPU и памяти
```

### 16. Как удалить все остановленные контейнеры и ненужные образы? {gen}

```bash
docker container prune         # остановленные контейнеры
docker image prune             # «висячие» образы (без тега)
docker image prune -a          # все образы, которые не используются
docker system prune            # контейнеры, сети, висячие образы, кэш сборки
docker system prune -a --volumes   # всё неиспользуемое, включая тома ⚠️

docker system df               # сколько места занимает
```

С `--volumes` осторожно — удалятся данные (например, локальной БД).

### 17. Как ограничить использование CPU и памяти контейнером? {gen}

```bash
docker run --memory=512m --cpus=1.5 my-api
```

* `--memory` — жёсткий лимит; превысил — контейнер убивает **OOM killer**.
* `--cpus` — сколько ядер можно использовать (через CFS quota). Превысил — **троттлинг**, а не убийство.
* `--memory-swap`, `--cpu-shares`, `--pids-limit` — тоньше.

В Compose:

```yaml
deploy:
  resources:
    limits:
      cpus: "1.5"
      memory: 512M
```

Для Go: с 1.25 `GOMAXPROCS` сам учитывает CPU-лимит контейнера, а под лимит памяти стоит выставить `GOMEMLIMIT` (~90% от лимита), чтобы GC работал активнее до OOM.

### 18. Как работает Docker под капотом? {gen}

Контейнер — это обычный процесс Linux, которому ядро ограничило «что видно» и «сколько можно».

* **Namespaces** — изоляция того, что процесс **видит**: `pid` (свои процессы, сам — PID 1), `net` (своя сеть), `mnt` (своя файловая система), `uts` (hostname), `ipc`, `user`.
* **cgroups** — ограничение того, сколько процесс **потребляет**: CPU, память, I/O, число процессов.
* **Union filesystem** (OverlayFS) — образ собран из read-only слоёв, сверху — writable-слой контейнера (copy-on-write).
* Безопасность: capabilities, seccomp, AppArmor/SELinux.

**Цепочка:** `docker` CLI → `dockerd` → `containerd` → `runc` (по стандарту OCI создаёт namespaces и cgroups и запускает процесс).

### 19. Как мониторить контейнеры? {gen}

* **Быстро руками:** `docker stats` (CPU, память, сеть, I/O), `docker logs`, `docker inspect`, `docker events`.
* **Метрики:** **cAdvisor** собирает метрики контейнеров → **Prometheus** → **Grafana** (дашборды и алерты). Плюс node-exporter для самого хоста.
* **Логи:** stdout → Fluent Bit / Vector → Loki или ELK.
* **Приложение:** свои метрики `/metrics` (Prometheus client), трейсы через OpenTelemetry.
* **Здоровье:** `HEALTHCHECK` в Dockerfile, статус `healthy/unhealthy` в `docker ps`.

На что алертить: перезапуски контейнеров, OOM kill, память близко к лимиту, CPU-троттлинг, unhealthy.

Готовые платформы — Datadog, New Relic; в Kubernetes то же самое делает стек kube-prometheus.
