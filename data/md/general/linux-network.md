# Linux и сеть

### 1. Какие знаешь syscalls? {gen}

**Syscall** — вызов ядра из пользовательской программы: всё, что касается файлов, сети, процессов и памяти, идёт через ядро.

* **Файлы:** `open`, `read`, `write`, `close`, `lseek`, `stat`, `fsync`.
* **Процессы:** `fork`, `execve`, `exit`, `wait`, `kill`, `clone` (потоки).
* **Память:** `mmap`, `munmap`, `brk`.
* **Сеть:** `socket`, `bind`, `listen`, `accept`, `connect`, `send`, `recv`.
* **Мультиплексирование I/O:** `select`, `poll`, `epoll` — на `epoll` построен сетевой поллер Go.

Посмотреть, какие вызовы делает процесс: `strace -p <pid>`.

---

### 2. Чем процесс отличается от потока? {gen}

* **Процесс** — изолированная программа: своё адресное пространство, свои файловые дескрипторы. Падение одного не трогает другие. Создание и переключение — дорогие.
* **Поток** — исполнение внутри процесса: потоки **делят память** процесса, у каждого только свой стек и регистры. Дешевле, но общая память → нужна синхронизация (гонки).

В Go поверх этого ещё **горутины** — лёгкие потоки рантайма (стек от 2 КБ), которые планировщик Go распределяет по OS-потокам (модель M:N).

---

### 3. Чем отличается hard link от soft link? {gen}

* **Hard link** — ещё одно имя для **того же inode** (тех же данных). Удалили оригинал — данные живы, пока есть хоть одна жёсткая ссылка. Нельзя на директории и между файловыми системами.
* **Soft (symbolic) link** — отдельный файл, в котором записан **путь** к цели. Удалили оригинал — ссылка «битая». Можно на директории и между файловыми системами.

```bash
ln  file.txt hard.txt     # hard link
ln -s file.txt soft.txt   # symlink
ls -li                    # у hard link тот же номер inode
```

### 4. Разница между kill, kill -9 и kill -15 {gen}

* `kill <pid>` — по умолчанию отправляет **SIGTERM (15)**, то же, что `kill -15`.
* **SIGTERM (15)** — вежливая просьба завершиться. Процесс может перехватить сигнал и корректно закрыться: дообработать запросы, закрыть соединения (graceful shutdown).
* **SIGKILL (9)** — немедленное убийство ядром. Перехватить нельзя, очистки не будет. Только если процесс не реагирует на SIGTERM.

Так работает и Kubernetes: сначала SIGTERM, через `terminationGracePeriodSeconds` (30 с) — SIGKILL.

```go
ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGTERM, os.Interrupt)
defer stop()
<-ctx.Done()
srv.Shutdown(context.Background()) // graceful shutdown
```

### 5. Как посмотреть, какой процесс слушает порт? {gen}

```bash
ss -tulpn | grep :8080        # современный вариант
lsof -i :8080                 # кто открыл порт
netstat -tulpn | grep :8080   # старый, часто не установлен
```

Флаги `ss`: `t` — TCP, `u` — UDP, `l` — только слушающие, `p` — показать процесс, `n` — без резолва имён. Для чужих процессов нужен `sudo`.

### 6. Что такое swap и зачем он нужен? {gen}

**Swap** — область на диске, куда ядро выгружает редко используемые страницы памяти, когда не хватает RAM.

* **Плюс:** система не падает сразу при нехватке памяти, есть запас.
* **Минус:** диск в тысячи раз медленнее RAM — при активном свопинге всё начинает «тормозить» (thrashing).

`vm.swappiness` (0–100) — насколько охотно ядро свопит. Для БД и latency-чувствительных сервисов swap часто отключают или ставят минимум; Kubernetes исторически требует swap выключенным.

Посмотреть: `free -h`, `swapon --show`.

### 7. На голом сервере запущен какой-то сервис и в нем есть утечка памяти. Что произойдет, когда память закончится? Речь не про кубер и ограничения контейнеров, а про голый сервер {gen}

1. Память растёт, ядро вытесняет **page cache** (кэш файлов) — диск начинает работать медленнее.
2. Если есть **swap** — страницы уходят в него, сервер сильно тормозит (thrashing), может почти перестать отвечать.
3. Когда кончаются и RAM, и swap, срабатывает **OOM Killer**: ядро выбирает процесс с наибольшим `oom_score` (обычно тот, кто съел больше всех памяти, — наш сервис) и убивает его через SIGKILL.
4. Если сервис под systemd с `Restart=always` — он перезапустится, и цикл повторится.

Убить могут и не тот процесс (например, БД рядом). Следы — в `dmesg` / `journalctl -k`: `Out of memory: Killed process ...`. Защита: `oom_score_adj`, лимиты через systemd (`MemoryMax`), мониторинг памяти.

### 8. Как узнать, какой процесс грузит CPU? {gen}

```bash
top                  # нажать P — сортировка по CPU
htop                 # удобнее, F6 — сортировка
ps aux --sort=-%cpu | head
pidstat 1            # по процессам, раз в секунду
top -H -p <pid>      # потоки конкретного процесса
```

Для Go-сервиса дальше — `pprof`: какая именно функция ест CPU (`go tool pprof http://host/debug/pprof/profile`).

---

### 9. Чем отличается top и htop? {gen}

Оба показывают процессы и нагрузку в реальном времени.

* **top** — есть везде по умолчанию, управление горячими клавишами, текстовый вид.
* **htop** — нужно ставить отдельно; цветной, графики загрузки по каждому ядру, прокрутка, мышь, дерево процессов (F5), поиск (F3), можно убить процесс прямо из интерфейса (F9).

На проде под рукой обычно только `top`, поэтому его горячие клавиши стоит знать: `P` — по CPU, `M` — по памяти, `1` — по ядрам, `k` — убить.

---

### 10. Что означает load average? {gen}

**Load average** — среднее число процессов, которые **выполняются или ждут** CPU (и в Linux — ещё ждут диск, состояние `D`). Три числа — среднее за **1, 5 и 15 минут**.

```bash
uptime
# load average: 3.20, 2.10, 1.05
```

Сравнивать с **числом ядер** (`nproc`):
* load ≈ числу ядер — загружено полностью;
* больше — процессы стоят в очереди;
* меньше — есть запас.

Пример выше на 4 ядрах: нагрузка растёт (1 мин > 15 мин), но пока в норме. Высокий load при низком CPU — обычно проблема с диском (I/O wait).

### 11. Как найти файлы больше 1 GB в системе? {gen}

```bash
find / -type f -size +1G 2>/dev/null

# с размерами, по убыванию
find / -type f -size +1G -exec ls -lh {} + 2>/dev/null | sort -k5 -rh

# какие директории занимают место
du -h --max-depth=1 / 2>/dev/null | sort -rh | head
```

`2>/dev/null` прячет ошибки «Permission denied». Удобная интерактивная альтернатива — `ncdu`.

### 12. Чем отличается TCP от UDP? {gen}

| | TCP | UDP |
|---|---|---|
| Соединение | устанавливается (handshake) | нет |
| Доставка | гарантирована, с повторами | не гарантирована |
| Порядок | сохраняется | нет |
| Контроль перегрузки | есть | нет |
| Скорость, задержка | медленнее | быстрее, меньше накладных |
| Где используется | HTTP/1–2, БД, SSH, почта | DNS, видео, голос, игры, QUIC |

TCP — когда важен каждый байт (API, файлы). UDP — когда важна скорость, а потерянный пакет проще пропустить (стрим, звонок).

---

### 13. Как TCP гарантирует доставку пакетов? {gen}

* **Three-way handshake** (`SYN → SYN-ACK → ACK`) — стороны договариваются о соединении и начальных номерах.
* **Sequence numbers** — каждый байт пронумерован: получатель собирает данные в правильном порядке и отбрасывает дубли.
* **ACK** — получатель подтверждает принятое.
* **Retransmission** — нет ACK за таймаут (или пришли 3 дублирующих ACK) — пакет отправляется снова.
* **Checksum** — проверка целостности, битый пакет отбрасывается.
* **Flow control** (окно получателя) — отправитель не шлёт больше, чем получатель успевает принять.
* **Congestion control** (slow start, CUBIC, BBR) — не перегружать сеть.

---

### 14. Почему DNS работает поверх UDP, а не TCP? {gen}

DNS-запрос и ответ обычно маленькие и помещаются в один пакет. По UDP это **один пакет туда и один обратно**, без handshake — быстро и дёшево для серверов, которые обслуживают миллионы запросов.

Потерялся пакет — клиент просто повторит запрос.

Но DNS **умеет и TCP**: когда ответ большой (не влез в UDP-пакет, флаг truncated), для передачи зоны между серверами (AXFR), а также DNS-over-TLS / DNS-over-HTTPS для шифрования.

### 15. Что такое QUIC? {gen}

**QUIC** — транспортный протокол от Google поверх **UDP**, основа **HTTP/3**.

Что решает:
* **Быстрое соединение** — транспорт и TLS 1.3 устанавливаются за 1 RTT, при повторном подключении — 0-RTT.
* **Нет head-of-line blocking** — потерянный пакет тормозит только свой поток, а не все (в HTTP/2 поверх TCP тормозят все).
* **Миграция соединения** — сменился IP (Wi-Fi → мобильная сеть), а соединение живо: оно идентифицируется по connection ID, а не по IP и порту.
* **Шифрование всегда**, встроено в протокол.

Работает в user space, поэтому развивается быстрее, чем TCP в ядре.

### 16. Как работает HTTP протокол? Виды запросов, идемпотентность. Стандартные коды http респонзов. {gen}

**HTTP** — текстовый протокол «запрос → ответ» без состояния. Запрос: метод, путь, заголовки, тело. Ответ: код, заголовки, тело.

**Методы и идемпотентность** (идемпотентный — повтор даёт тот же результат):

| Метод | Назначение | Идемпотентен | Безопасен |
|---|---|---|---|
| GET | получить | да | да |
| HEAD | только заголовки | да | да |
| POST | создать / действие | **нет** | нет |
| PUT | заменить целиком | да | нет |
| PATCH | изменить частично | не гарантируется | нет |
| DELETE | удалить | да | нет |
| OPTIONS | что поддерживается (CORS) | да | да |

Чтобы безопасно ретраить POST (платёж) — заголовок `Idempotency-Key`.

**Коды:**
* **2xx** — успех: `200 OK`, `201 Created`, `204 No Content`.
* **3xx** — редирект: `301`, `302`, `304 Not Modified`.
* **4xx** — ошибка клиента: `400`, `401` (не аутентифицирован), `403` (нет прав), `404`, `409 Conflict`, `422`, `429 Too Many Requests`.
* **5xx** — ошибка сервера: `500`, `502 Bad Gateway`, `503 Service Unavailable`, `504 Gateway Timeout`.

### 17. В чем разница между HTTP/1.1, HTTP/2 и HTTP/3? {gen}

* **HTTP/1.1** — текстовый. Одно соединение обрабатывает один запрос за раз → браузеры открывают по 6 соединений. Заголовки не сжимаются.
* **HTTP/2** — бинарный, **мультиплексирование**: много запросов параллельно в одном TCP-соединении; сжатие заголовков (HPACK). Минус — потеря одного TCP-пакета тормозит все потоки (head-of-line blocking на уровне TCP).
* **HTTP/3** — поверх **QUIC (UDP)**: потоки независимы, нет HOL-блокировки, быстрое установление соединения (0–1 RTT), переживает смену сети.

gRPC работает поверх HTTP/2.

### 18. Https vs httpS. TLS Хэндшэйк. Как проверяется сертификат. Чем отличается подлинный от самоподписного? {gen}

**HTTPS = HTTP поверх TLS**: шифрование (никто не прочитает), целостность (никто не изменит) и аутентификация сервера (это действительно тот сайт).

**TLS 1.3 handshake (упрощённо, 1 RTT):**
1. **ClientHello** — версии, шифры, ключевая часть клиента для обмена ключами (ECDHE).
2. **ServerHello** — выбранный шифр, ключевая часть сервера, **сертификат** и подпись.
3. Обе стороны вычисляют общий **сеансовый ключ**, дальше данные шифруются симметрично (быстро).

**Проверка сертификата клиентом:**
* подпись выстраивается в цепочку до **корневого CA**, которому доверяет ОС/браузер;
* домен совпадает с CN/SAN;
* срок действия не истёк;
* сертификат не отозван (OCSP / CRL).

**Подлинный vs самоподписной:** подлинный подписан доверенным CA, который проверил владение доменом. Самоподписной подписан сам собой — шифрование такое же, но **нет доказательства, кто на той стороне**, поэтому браузер показывает предупреждение. Годится для локальной разработки и внутренних сетей со своим CA.

### 19. Как проверить, открыт ли порт на сервере? {gen}

```bash
nc -zv host 5432                  # netcat: доступен ли порт
telnet host 5432                  # старый способ
curl -v telnet://host:5432
nmap -p 5432 host                 # сканер портов

ss -tlnp | grep 5432              # на самом сервере: слушает ли кто-то
```

Если на сервере порт слушается, а снаружи закрыт — смотреть firewall (`iptables`, `ufw`, security groups в облаке) и на каком адресе слушает сервис (`127.0.0.1` или `0.0.0.0`).

### 20. Разница между Cookie, Session, JWT {gen}

* **Cookie** — механизм браузера: небольшие данные, которые сервер ставит через `Set-Cookie`, а браузер сам отправляет с каждым запросом. Это **транспорт**, а не способ аутентификации.
* **Session** — состояние хранится **на сервере** (в Redis/БД), клиенту отдаётся только случайный `session_id` (обычно в cookie). Легко отозвать (удалил сессию), но нужно общее хранилище для всех инстансов.
* **JWT** — подписанный токен, внутри которого лежат данные пользователя (`user_id`, роли, срок действия). Сервер **ничего не хранит**, только проверяет подпись — удобно для микросервисов. Минус: до истечения срока токен **нельзя просто отозвать**, поэтому делают короткий access token + refresh token.

Для безопасности cookie: `HttpOnly` (недоступна JS), `Secure` (только HTTPS), `SameSite` (защита от CSRF).

### 21. Команды шелла, которыми пользуешься каждый день (ls, cd, grep, find, history, cat, less, wc, chmod, chown, ps, kill, netstat, lsof, ping, wget, curl, touch, make, head, tail, ifconfig, top, tar, unzip, bg, jobs, diff, scp, ssh, rsync и т. п.) {gen}

* **Файлы и навигация:** `ls -la`, `cd`, `cat`, `less`, `head`/`tail -f` (логи в реальном времени), `touch`, `cp`, `mv`, `rm`, `diff`.
* **Поиск:** `grep -rn "text" .`, `find . -name "*.go"`, `wc -l`.
* **Права:** `chmod +x script.sh`, `chown user:group file`.
* **Процессы:** `ps aux`, `top`/`htop`, `kill`, `jobs`, `bg`/`fg`.
* **Сеть:** `curl -v`, `wget`, `ping`, `ss`/`netstat`, `lsof -i`, `ip a` (вместо `ifconfig`).
* **Удалённая работа:** `ssh`, `scp`, `rsync -avz`.
* **Архивы:** `tar -czf` / `tar -xzf`, `unzip`.
* **Прочее:** `make`, `history | grep`, `Ctrl+R` — поиск по истории.

Пример из жизни:

```bash
tail -f app.log | grep -i error
ps aux | grep myservice
```

### 22. HTTP2 и GRPC. Multiplexing & Streaming. Плюсы и минусы с REST. Protobuf, protoc. 4 types of RPC calls. Headers (metadata). Versioning. GRPC gateway. {gen}

**gRPC** — RPC-фреймворк поверх **HTTP/2**, данные в **Protobuf**.

* **Multiplexing** — много вызовов параллельно в одном соединении.
* **Streaming** — поток сообщений в одном вызове в любую сторону.

**Protobuf + protoc:** контракт описывается в `.proto`, `protoc` (с плагинами `protoc-gen-go`, `protoc-gen-go-grpc`) генерирует код клиента и сервера.

```proto
service Users {
  rpc Get(GetReq) returns (User);                       // unary
  rpc List(ListReq) returns (stream User);              // server streaming
  rpc Upload(stream Chunk) returns (Result);            // client streaming
  rpc Chat(stream Msg) returns (stream Msg);            // bidirectional
}
```

**4 типа вызовов:** unary, server streaming, client streaming, bidirectional streaming.

**Metadata** — аналог HTTP-заголовков: auth-токен, trace id, request id (`metadata.NewOutgoingContext`).

**Versioning:** не менять номера и типы полей, только добавлять новые; при ломающих изменениях — новый пакет `users.v2`.

**gRPC-Gateway** — генерирует REST/JSON прокси из `.proto` (по аннотациям), чтобы внешние клиенты и браузер ходили по REST, а внутри был gRPC.

**gRPC vs REST:**
* ➕ быстрее и компактнее, строгий контракт, кодогенерация, стриминг, deadline'ы.
* ➖ не читается глазами, браузер напрямую не умеет (нужен gRPC-Web или gateway), сложнее отлаживать (`grpcurl`), HTTP-кэширование не работает.

Обычно: gRPC — между сервисами, REST — наружу.
