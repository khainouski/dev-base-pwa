## Вопросы и ответы

### 1. Что нравится и не нравится в Го?

**EN:** What do you like and dislike about Go?

**Нравится**

- **Простота** — маленькая спецификация, минимум магии (нет наследования, перегрузки операторов, скрытых конструкторов). Читаю чужой код и понимаю его сразу.
- **Конкурентность в языке** — `go func()` и каналы прямо в синтаксисе, горутины на порядки дешевле OS-потоков.
- **Явные ошибки** — ошибка обычное значение, а не скрытое исключение: видно каждую точку отказа.
- **Сильная стандартная библиотека** — `net/http`, `encoding/json`, `database/sql` закрывают большинство задач без фреймворков.
- **Один статический бинарник** — не нужен VM или рантайм на сервере, как у JVM/Node.

**Не нравится**

- **Многословность обработки ошибок** — `if err != nil` занимает половину кода, и без `%w` легко потерять контекст.
- **Дженерики появились поздно и ограничены** — нет методов с type-параметрами, вывод типов слабоват.
- **Нет полноценных enum** — `iota` + константы не дают исчерпывающей проверки в `switch`, компилятор не подскажет про забытый вариант.
- **Ловушки с nil** — typed nil (`err != nil`, хотя внутри nil-указатель), запись в nil-мапу паникует.

Но это осознанный размен: язык намеренно жертвует выразительностью ради простоты и читаемости в больших командах — и в проде это себя оправдывает.

### 2. Как выглядит структура по папкам у ваших сервисов?

**EN:** What does the folder structure of your services look like?

```text
user-service/
├── api/                          # контракты: user_v1.proto, user_v1.yaml
├── cmd/
│   ├── app/main.go            # точка входа: HTTP + gRPC серверы, Kafka consumer, outbox worker
│   └── http_client/main.go    # демо-клиент для нагрузки/дашбордов
├── config/config.go              # конфиг сервиса (envconfig)
├── gen/                          # сгенерированный код (protoc, oapi-codegen)
├── internal/                     # приватный код, недоступен извне
│   ├── adapter/                  # реализации интерфейсов usecase
│   │   ├── kafka_producer/
│   │   └── postgres/             # CRUD + outbox (save/read)
│   ├── app/app.go                 # сборка приложения, graceful shutdown
│   ├── controller/                # входные точки — транспортный слой
│   │   ├── grpc/v1/                # gRPC-хендлеры (сгенерированы из proto)
│   │   ├── http/v1/                # REST-хендлеры (сгенерированы из OpenAPI)
│   │   ├── kafka_consumer/         # consumer topic'а user-events
│   │   └── worker/                 # OutboxKafka — вычитывает outbox и публикует в Kafka
│   ├── domain/                    # сущности: User, Event, Status, Error
│   ├── dto/                       # DTO на каждую операцию (create/get/update/delete)
│   └── usecase/                   # бизнес-логика, транспорт-агностичная + тесты/mocks
├── migration/postgres/           # SQL-миграции
├── observability/                # конфиги Grafana/Prometheus/Loki/Tempo
├── pkg/                          # переиспользуемая инфраструктурная обвязка

├── test/integration/             # интеграционные тесты (build tag integration)
```

Логика разбивки:
- **`cmd/`** — только точки входа, минимум логики, вся сборка приложения делегируется в `internal/app`.
- **`internal/`** — по слоям (`controller` → `usecase` → `adapter`), не по фичам: транспорт (HTTP/gRPC/Kafka) отделён от бизнес-логики (`usecase`), а та — от конкретных реализаций хранилища (`adapter`).
- **`pkg/`** — переиспользуемая инфраструктурная обвязка (логгер, метрики, БД-пул), не завязанная на конкретный домен.

**Альтернативный вариант (news-explorer)** — здесь внутри каждого слоя дополнительно разбито **по доменам** (`article`, `auth`, `source`, `tag`), а не только по операциям, как в `user-service`:

```text
│   │       ├── article/
│   │       ├── session/
│   │       ├── source/
│   │       ├── tag/
│   │       └── user/
│   ├── app/app.go                # сборка приложения, graceful shutdown
│   ├── controller/http/
│   │   ├── article/
│   │   ├── auth/
│   │   ├── middleware/
│   │   ├── shared/
│   │   └── source/
│   ├── domain/                   # сущности: Article, Session, Source, Tag, User, Error
│   └── usecase/
│       ├── article/
│       ├── auth/
│       ├── source/
│       ├── sync/                 # логика фоновой синхронизации фидов
```

- Нет gRPC/Kafka — только HTTP, сервис проще по транспорту.
- `usecase`, `controller/http`, `adapter/postgres` разбиты **по доменам** (`article`, `auth`, `source`, `tag`) — в каждой папке файлы конкретного домена, а не общий набор операций на весь сервис.
- Есть **`web/`** — сервис сам рендерит HTML на сервере (шаблоны + Tailwind), а не отдаёт JSON для отдельного SPA-фронтенда.
- Второй `cmd/` — `syncjob`, отдельный бинарник для фоновой синхронизации данных, не часть основного HTTP-процесса.

### 4. Что из себя представляет тип string? Что происходит при конкатенации строк? Как эффективно слить 100к строк в одну?

**EN:** What is the `string` type under the hood? What happens when you concatenate strings? How would you efficiently join 100k strings into one?

**Что такое `string`**

Не массив символов, а структура из двух полей: указатель на байты (UTF-8) и длина. 16 байт на 64-битной системе, сами байты лежат отдельно.
```go
type string struct {
    Data uintptr // адрес первого байта
    Len  int     // длина в байтах
}
```
- При копировании/передаче копируются только эти 16 байт — дёшево независимо от длины текста.
- **Неизменяема**: `s[0] = 'H'` не компилируется. Изменить = создать новую: `[]byte(s)` → правка → `string(...)`.
- `len(s)`/`s[i]` считают **байты**, не символы: `len("привет") == 12`, а `len([]rune("привет")) == 6`.

**Что происходит при конкатенации**

- `s += x` не меняет строку на месте — аллоцирует новый блок и копирует туда обе части.
- В цикле копирование накапливается: каждая итерация переписывает весь накопленный текст → **O(n²)**.
- На 100k строк это уже заметно тормозит.

**Как эффективно слить 100k строк**

```go
var b strings.Builder
b.Grow(estimatedSize)
for _, s := range strs {
    b.WriteString(s)
}
result := b.String()
```
- Один растущий буфер вместо новой строки на каждой итерации → **O(n)**. `Grow(n)` убирает реаллокации совсем.
- Если строки уже в слайсе — то же самое даёт `strings.Join(strs, "")`.
- Вручную через `buf := make([]byte, 0, n)` + `append` — та же O(n), но финальный `string(buf)` делает лишнюю копию, а `Builder.String()` — нет.

### 5. Что такое ошибка в Го? как с ней работать? Как отдаешь ошибку http клиенту?

**EN:** What is an error in Go? How do you work with errors? How do you return an error to an HTTP client?

**Что такое ошибка**

- `error` — обычный интерфейс с одним методом `Error() string`.
- Исключений в Go нет: ошибка возвращается значением, последним из результатов — `func Do() (Result, error)`.
- `nil` = «ошибки не было».

**Как с ней работать**

Все доменные sentinel-ошибки объявлены один раз, в `internal/domain/error.go`:
```go
var (
    ErrNotFound           = errors.New("not found")
    ErrEmailAlreadyExists = errors.New("email already exists")
    ErrBirthDateInFuture  = errors.New("birth date is in the future")
)
```
- **Адаптер** переводит ошибку БД в доменную, остальное оборачивает контекстом:
  ```go
  if errors.Is(err, pgx.ErrNoRows) {
      return domain.User{}, domain.ErrNotFound
  }
  return domain.User{}, fmt.Errorf("txOrPool.QueryRow: %w", err)
  ```
- **Usecase и `domain.User.Validate()`** возвращают эти же sentinel-ошибки — что считать ошибкой, решается один раз в домене.
- `errors.Is(err, ErrX)` — ищет ошибку по всей цепочке `%w`, а не просто `==`.
- `errors.As(err, &target)` — достаёт из цепочки ошибку конкретного типа, если она несёт данные (код, id).
- `panic` — не замена `error`: только для багов, а не для «не нашли» / «невалидный ввод».

**Как отдаёшь клиенту**

Транспорты (`controller/http`, `controller/grpc`) правило не перепроверяют — только распознают готовую ошибку через `errors.Is` и мапят в свой код ответа:
```go
switch {
case errors.Is(err, domain.ErrNotFound):
    // HTTP: 404JSONResponse | gRPC: status.Error(codes.NotFound, ...)
case errors.Is(err, domain.ErrEmailAlreadyExists):
    // HTTP: 409JSONResponse | gRPC: status.Error(codes.AlreadyExists, ...)
default:
    log.Error().Err(err).Msg("...")  // полная ошибка — в лог
    // HTTP: 400 | gRPC: codes.InvalidArgument
}
```
- Клиенту никогда не отдаём `err.Error()` целиком — там могут быть детали SQL и инфраструктуры.
- Плюс подхода: ошибка объявлена один раз в домене, а каждый транспорт переводит её по-своему. Добавится Kafka — переиспользует тот же `errors.Is`.

### 6. Слайсы: внутреннее устройство, сравнение с массивами, append, потокобезопасность

**EN:** Slices: internals, how they compare to arrays, `append`, thread safety.

**Внутреннее устройство**

Слайс — динамический массив: структура из трёх полей, описывающая кусок обычного массива. Сами элементы лежат отдельно, слайс их не хранит.
```go
type slice struct {
    ptr *T   // с какого элемента массива начинается
    len int  // сколько элементов видно сейчас
    cap int  // сколько доступно вправо от ptr до конца массива
}
```
- Копируется только эти три поля — массив с данными остаётся общим.

**Сравнение с массивом**

- Массив `[5]int` — значение, длина часть типа, копируется целиком.
- Слайс `[]int` — окно (view) на массив, длина не часть типа.
- Несколько слайсов могут смотреть на один массив: `x := a[1:3]`, `y := a[2:]` — правка `x[1]` видна в `y[0]`.

**append**

- Влезает в `cap` — пишет в тот же массив, память общая.
- Не влезает — новый массив вдвое больше + копирование, память больше не общая.
- Отсюда: делят два слайса память или нет — на глаз не видно, зависит от `cap`. Знаешь объём — задавай `cap` через `make`.
- `nil`-слайс vs `[]int{}`: у обоих `len == 0`, но `s == nil` только у первого. В JSON: `null` vs `[]`.

**Потокобезопасность**

- Своей синхронизации нет — защищает тот, кто пользуется.
- Читать из нескольких горутин можно, писать параллельно — гонка данных, ловится `go test -race`.
- `append` опаснее всего: меняет сам заголовок (`len`, при росте `ptr`) — ломается даже при записи в разные индексы.
- Решение: `sync.Mutex`/`RWMutex` или одна горутина-владелец + канал.

### 7. Мапы: внутреннее устройство, бакеты, хэш-функция, эвакуация, что может быть ключом, потокобезопасность, сравнение с sync.Map, новые Swiss maps

**EN:** Maps: internals, buckets, hash function, evacuation, what can be a key, thread safety, comparison with `sync.Map`, the new Swiss maps.

**Внутреннее устройство (до Go 1.24)**

- Хеш-таблица на **бакетах** с закрытой адресацией. Основная структура — `hmap` + массив бакетов.
- **Хеш ключа** считает рантайм: под каждый тип ключа компилятор подставляет свою хеш-функцию (для строк — по байтам, для чисел — по битам значения), плюс подмешивается случайное зерно `hash0`, своё у каждой мапы. Из-за него хеши одного и того же ключа различаются между мапами и запусками — это защита от hash-flooding атак и причина, почему порядок `range` не воспроизводится.
- **Как ищем `m[k]`:** считаем хеш ключа → младшие биты (маска) дают номер бакета → внутри бакета пробегаем 8 байт `tophash` → для совпавших сравниваем полный ключ → нет в бакете, идём по цепочке overflow-бакетов.
- В бакете до **8** пар ключ-значение + массив `tophash` (старшие биты хеша) — по нему быстро отсеиваются неподходящие ключи до полного сравнения.
- Коллизии: бакет заполнен → создаётся **overflow-бакет**, получается цепочка (pointer chasing, плохая локальность и cache miss).

**Эвакуация (рост)**

- Растём при load factor ≈ **6.5** элементов на бакет, бакетов становится вдвое больше.
- Рост **не одномоментный**: старые бакеты переносятся в новые постепенно (incremental grow), по чуть-чуть на каждой обычной операции insert/get. Это и есть эвакуация.

**Swiss maps (с Go 1.24)**

- Новая реализация на идеях **Swiss Table**: **открытая** адресация вместо overflow-цепочек.
- Вместо `tophash` — компактные **control bytes**, которые сканируются группой через **SIMD**-инструкции: одна инструкция проверяет сразу всю группу слотов, а не по одному.
- **SIMD** (Single Instruction, Multiple Data) — инструкции процессора, применяющие одну операцию сразу к нескольким данным: в 64-битный регистр влезает 8 control-байт, и они сравниваются за одну инструкцию вместо восьми.
- **Как ищем `m[k]`:** считаем хеш → находим группу слотов → одной SIMD-инструкцией сравниваем все control bytes группы разом → для совпавших сравниваем полный ключ → не нашли, переходим к следующей группе (пробирование), без прыжков по указателям.
- **Коллизии — без новых бакетов.** Раньше: место в бакете кончилось → аллоцируем overflow-бакет где-то ещё в памяти и вешаем по указателю. Теперь: ничего не аллоцируем, а кладём элемент в другой, уже существующий свободный слот того же массива — просто идём дальше по нему, пока не найдём пустой. Это и есть **пробирование** (probing): шаг вперёд по фиксированной формуле (в Go — квадратичной: +1, +4, +9... группы).

```text
БЫЛО (overflow-цепочка):        массив бакетов
       ┌──────────┬──────────┬──────────┬──────────┐
       │ bucket 0 │ bucket 1 │ bucket 2 │ bucket 3 │
       └──────────┴─────┬────┴──────────┴──────────┘
              все 8 слотов заняты, а нужен 9-й
                        │ overflow-указатель
                        ▼
              ┌──────────────────┐   ← НОВАЯ аллокация в куче,
              │ overflow-бакет   │      далеко от массива
              │ k9 ...           │──► возможен ещё один overflow...
              └──────────────────┘      (прыжки по указателям = cache miss)

СТАЛО (пробирование):     один непрерывный массив групп
       ┌──────────┬──────────┬──────────┬──────────┐
       │ группа 0 │ группа 1 │ группа 2 │ группа 3 │
       └──────────┴─────┬────┴─────▲────┴──────────┘
                хеш привёл сюда,   │ свободный слот — кладём здесь
                группа полна ──────┘ (шаг пробирования)
              ничего не аллоцируем, всё в том же массиве
```
- Поиск повторяет ровно тот же путь пробирования; встретили **пустой** слот — значит ключа в мапе точно нет, можно останавливаться.
- Поэтому при удалении слот нельзя просто пометить пустым (это оборвало бы чужие цепочки поиска) — ставится маркер «удалён» (tombstone), слот считается занятым для поиска, но свободным для вставки.
- Рост в 2× при заполнении **~86%** и **одномоментно**: при открытой адресации чем плотнее таблица, тем длиннее пробирование, поэтому расти надо не дожидаясь полного заполнения.
- Итог: все данные в одном непрерывном массиве — нет прыжков по указателям, лучше локальность памяти и cache-hit, быстрее поиск.

**Что может быть ключом**

- Любой **comparable**-тип (поддерживающий `==`): числа, строки, bool, указатели, интерфейсы, структуры и массивы — если все их поля/элементы тоже comparable.
- Нельзя: слайс, мапа, функция — не компилируется.
- `&m["k"]` взять нельзя: значения мапы не адресуемы (при росте элементы физически переезжают, адрес был бы нестабилен).

**Потокобезопасность**

- Мапа **не потокобезопасна**, причём в рантайме есть явная проверка: параллельная запись → `fatal error: concurrent map writes` (это не паника, её не поймать через `recover`).
- Читать из нескольких горутин параллельно — можно, но только если никто в этот момент не пишет.
- Защита: `sync.Mutex`/`RWMutex`, `sync.Map`, либо одна горутина-владелец + канал.
- Отдельно: у `nil`-мапы читать можно (вернёт нулевое значение), а запись — паника `assignment to entry in nil map`.

**sync.Map vs map + RWMutex**

- `sync.Map` — не универсальная замена: внутри две структуры (read + dirty), выигрыш только в конкретных паттернах.
- Подходит, когда: ключ пишется один раз и много читается (кэш неизменяемых объектов), либо разные горутины работают с непересекающимися ключами.
- Не подходит: обычная нагрузка со смешанным чтением/записью и частым churn (постоянные insert/delete) — там `map` + `RWMutex` обычно быстрее.
- Минус: API через `any` (`Load`/`Store`/`LoadOrStore`/`Range`) — теряется compile-time типобезопасность.
- По умолчанию беру `map` + `RWMutex`, `sync.Map` — только под конкретный паттерн и после бенчмарка.

### 8. Каналы: виды (буферизованные/нет, открытые/закрытые), аксиомы, внутреннее устройство, есть ли мьютекс в канале

**EN:** Channels: kinds (buffered/unbuffered, open/closed), the axioms, internals — is there a mutex inside a channel?

**Виды: буферизованный / небуферизованный**

```go
ch := make(chan int)     // небуферизованный
ch := make(chan int, 10) // буферизованный, ёмкость 10
```
- **Небуферизованный** — rendezvous: send блокируется, пока кто-то не прочитает, receive — пока кто-то не отправит. Строгая синхронизация «встретились и передали».
- **Буферизованный** — send блокируется только когда буфер полон, receive — когда пуст. Сглаживает разницу в скорости producer/consumer.
- Буфер не убирает блокировки, а **откладывает** их: заполнится — всё равно заблокируемся (back-pressure).
- Частый приём — буферизованный канал как **семафор**: `sem := make(chan struct{}, 3)`, запись = занять слот, чтение = освободить. Ограничивает число одновременно работающих горутин.

**Аксиомы (что происходит с nil и закрытым каналом)**

| Канал | Операция | Результат |
|---|---|---|
| `nil` | `ch <- v` / `<-ch` | блокируется **навсегда**, без паники |
| `nil` | `close(ch)` | **паника**: close of nil channel |
| `nil` | `case` в `select` | никогда не выбирается — канал как будто выключен |
| закрытый | `<-ch` | не паника: сначала остатки буфера, потом нулевое значение и `ok == false` |
| закрытый | `ch <- v` | **паника**: send on closed channel |
| закрытый | `close(ch)` повторно | **паника**: close of closed channel |

- Правило: **закрывает только отправитель**, и только один. Отправителей несколько → закрывает отдельная горутина-координатор после `wg.Wait()`.
- Закрытие — это не «освобождение ресурса», а **сигнал** «данных больше не будет». Не закрывать канал не утечка, если на нём никто не висит.
- Приём: присвоив каналу `nil`, можно на ходу отключить ветку `select`, не убирая сам `case`.

**Внутреннее устройство (`hchan`)**

Канал — указатель на структуру `hchan` в рантайме:
- `buf` — кольцевой буфер (ring buffer) под элементы, `dataqsiz` — его ёмкость, `qcount` — сколько лежит сейчас;
- `sendx` / `recvx` — индексы записи и чтения в кольце;
- `sendq` / `recvq` — очереди заблокированных горутин, ждущих отправки/получения;
- `closed` — флаг закрытия;
- `lock` — **мьютекс**.

**Есть ли мьютекс в канале — да**

- Внутри `hchan` есть обычный `mutex`, он берётся на каждую операцию send/recv/close — поэтому канал потокобезопасен «из коробки» и оборачивать его своим мьютексом не нужно.
- Но канал — это не только мьютекс: если операция не может выполниться сразу, горутина **паркуется** планировщиком (уходит в `sendq`/`recvq`) и будится, когда появится встречная сторона. Это дешевле, чем спин на локе.
- Оптимизация: при передаче ожидающей горутине значение копируется **напрямую из отправителя в получателя**, минуя буфер.

### 9. Что такое контекст? Для чего используется? Дерево контекстов. Что будет если отменить родительский? А дочерний?

**EN:** What is context? What is it used for? The context tree. What happens if you cancel the parent? And if you cancel a child?

**Что это и зачем**

`context.Context` — интерфейс для управления временем жизни операции и передачи служебных данных по цепочке вызовов. Три задачи:
- **отмена** — сказать всей цепочке «работу можно прекращать» (клиент отвалился, приложение останавливается);
- **таймаут/дедлайн** — ограничить время запроса к БД, HTTP, gRPC;
- **request-scoped значения** — request ID, trace ID, данные трассировки.

Четыре метода: `Done()` — канал, закрывается при отмене; `Err()` — причина (`context.Canceled` / `context.DeadlineExceeded`); `Deadline()`; `Value()`.

- Раз это интерфейс, тип переменной всегда один — `context.Context`. Какой именно контекст, по типу не понять, только по тому, чем создан, или через `Err()`/`Deadline()`. За интерфейсом — разные структуры: `emptyCtx` (Background/TODO), `cancelCtx` (WithCancel), `timerCtx` (WithTimeout/Deadline), `valueCtx` (WithValue); каждая хранит ссылку на родителя — из них и складывается дерево.
- Передаётся **первым параметром** с именем `ctx`: `func GetUser(ctx context.Context, id string) error`. У меня в `user-service` `ctx` идёт сквозь все слои: контроллер → usecase → адаптер, и в нём же летят спаны трассировки (`tracer.Start(ctx, ...)`).
- Отмена **не убивает** горутину принудительно — она сама обязана слушать `<-ctx.Done()` и завершиться.

**Как создаются**

```go
ctx := context.Background()                                    // корневой, пустой
ctx := context.TODO()                                           // заглушка, пока не решил какой нужен
ctx, cancel := context.WithCancel(parent)                       // отмена руками
ctx, cancel := context.WithTimeout(parent, 5*time.Second)       // автоотмена через 5 сек
ctx, cancel := context.WithDeadline(parent, someTime)           // автоотмена в момент времени
ctx := context.WithValue(parent, key, val)                      // несёт значение, cancel нет
defer cancel()                                                  // обязательно, иначе течёт
```
- Внутри обработки запроса `context.Background()` создавать **нельзя** — берём контекст от вызывающей стороны (`r.Context()` в HTTP-хендлере), иначе потеряем отмену и дедлайн всей цепочки.

**Дерево контекстов**

- Каждый `WithXxx` берёт `parent` первым аргументом — это **обёртка** над родителем, а не новый независимый контекст. Так из одного корня вырастает дерево.
- Отмена идёт **только сверху вниз**: родитель → все его потомки, каскадом.

**Отменили родительский**

- Отменяются **все** дочерние контексты — мгновенно и каскадом, даже если у них свой таймаут ещё не истёк.
- У потомка `Done()` закроется, `Err()` вернёт `context.Canceled`.

```go
parent, cancelParent := context.WithCancel(context.Background())
child, cancelChild := context.WithTimeout(parent, 10*time.Second)
defer cancelChild()

cancelParent()
<-child.Done()             // уже закрыт, хотя 10 секунд не прошли
fmt.Println(child.Err())   // context.Canceled
```

**Отменили дочерний**

- На родителя и на «соседей» (другие потомки того же родителя) это **не влияет** — они продолжают работать.
- Отменяется только сам потомок и его собственное поддерево.

### 10. Есть ли в Го структура set, а исключения? А деструкторы?

**EN:** Does Go have a set type? What about exceptions? Destructors?

Короткий ответ на все три: **нет**. Дальше — чем заменяем.

**Set — нет, делается на мапе**

```go
set := map[string]struct{}{}
set["a"] = struct{}{}          // добавить
_, ok := set["a"]              // проверить
delete(set, "a")               // удалить
```
- Значение `struct{}{}` занимает **0 байт** — платим только за ключи. `map[string]bool` тоже рабочий вариант, но там на каждый элемент лишний байт, и появляется бессмысленное состояние «ключ есть, а значение `false`».
- Минус — многословно (`struct{}{}` вместо `set.Add(x)`), поэтому иногда берут готовую generic-обёртку, но в стандартной библиотеке set так и нет.

**Исключений нет — ошибки это значения**

- Нет `try/catch/throw`: функция возвращает `error`, вызывающий решает, что делать (см. вопрос 5).
- `panic`/`recover` похожи на исключения, но это **не замена**: паника для багов и нарушенных инвариантов, а не для штатных ситуаций.
- `recover()` работает только внутри `defer` и только **в своей горутине** — паника в соседней горутине уронит весь процесс, её не поймать.
- Практическое применение `recover` — HTTP-middleware, чтобы паника в одном хендлере не положила весь сервис.

**Деструкторов нет — есть `defer` и GC**

- Деструктор — это метод, который язык вызывает **сам**, когда объект уничтожается (в C++ `~File()` закрывает файл при выходе из области видимости; в Rust — `Drop`).
- В Go такого нет: момент «смерти» объекта решает сборщик мусора, и он недетерминирован — вешать на него закрытие файла или соединения опасно (дескрипторы кончатся раньше, чем GC проснётся).
- Ресурсы (файлы, соединения, локи) закрываем **явно** через `defer`: `defer f.Close()`, `defer mu.Unlock()`, `defer cancel()`.
- Есть `runtime.SetFinalizer`, но это не деструктор: вызов не гарантирован (при выходе программы может не отработать), поэтому для закрытия ресурсов не используется. В Go 1.24 добавили более предсказуемый `runtime.AddCleanup`.

### 11. Что такое горутина? Сравнение с системными тредами. Планировщик в Го, сравнение с системным. GMP модель, состояния горутин, GOMAXPROCS, NUMCPU. Netpoller. Goroutine leaks - как бороться?

**EN:** What is a goroutine? How does it compare to an OS thread? The Go scheduler vs the OS scheduler. The GMP model, goroutine states, GOMAXPROCS, NumCPU. The netpoller. Goroutine leaks — how do you deal with them?

**Горутина vs OS-тред**

Горутина — лёгкая единица выполнения, которой управляет рантайм Go, а не ОС.

| | Горутина | OS-тред |
|---|---|---|
| Кто планирует | Рантайм Go (user space) | Ядро ОС |
| Стек | ~2 КБ, растёт динамически | 1–2 МБ, фиксированный |
| Переключение | Дешёвое, без входа в ядро | Дорогое: syscall, сохранение регистров, потеря кеша |
| Сколько можно | Сотни тысяч | Тысячи максимум |

**GMP-модель**

- **G** — горутина (сама задача).
- **M** — machine, реальный OS-тред, исполняет код на CPU.
- **P** — processor, «разрешение» исполнять Go-код: держит локальную очередь горутин и контекст. **P ≠ процесс ОС** — это структура внутри рантайма.

Как связано: `P` привязывается к `M` и скармливает ему горутины из своей очереди. Число `P` фиксировано (`GOMAXPROCS`), а `M` может быть **больше** — когда горутины залипают в блокирующих syscall'ах, рантайм добавляет потоки.

**Очереди и work stealing**

- У каждого `P` — своя **локальная** очередь (до 256 G), без блокировок. Плюс одна **глобальная**, под мьютексом.
- `P` остался без работы → смотрит глобальную очередь → если пусто, **ворует** половину горутин у другого `P` (work stealing).
- Примерно раз в 61 итерацию `P` лезет в глобальную очередь принудительно — чтобы горутины оттуда не голодали.

**Планировщик Go vs планировщик ОС**

- ОС — вытесняющая многозадачность: может прервать поток в любой момент.
- Go — **кооперативно-вытесняющая**: горутина обычно сама уступает управление в точках вызова функций, работы с каналом, syscall. Но если крутится дольше **~10 мс**, `sysmon` вытесняет её принудительно (с Go 1.14 — асинхронно, через сигнал, даже из чистого цикла без вызовов).
- `sysmon` — служебный поток рантайма: следит за долгими горутинами, будит таймеры, помогает netpoller и GC.

**Состояния горутины**

- `runnable` — готова, ждёт очереди на `P`.
- `running` — выполняется на `M`.
- `waiting` — заблокирована: канал, мьютекс, `time.Sleep`, сеть. Не занимает `M`.
- `syscall` — в системном вызове, `M` при этом занят.
- `dead` — завершилась, структура `g` уходит в переиспользование.

**GOMAXPROCS и NumCPU**

- `runtime.NumCPU()` — сколько логических ядер видит процесс (просто число, ничего не настраивает).
- `runtime.GOMAXPROCS(n)` — сколько `P`, то есть сколько горутин реально выполняются **параллельно**. Ограничивает только Go-код, не число системных потоков.
- **Важно для k8s:** до Go 1.24 по умолчанию бралось `NumCPU()`, и в контейнере с лимитом `0.5 CPU` рантайм всё равно видел все ядра ноды — отсюда лишние `P` и тормоза (лечили через `uber-go/automaxprocs`). **С Go 1.25** рантайм сам учитывает cgroup-квоту и даже обновляет значение на лету.

**Netpoller — почему сеть дешёвая**

- Блокирующий **syscall** (диск) реально занимает `M` целиком → рантайм поднимает новый поток, чтобы остальные горутины работали.
- Блокировка на **сети** поток не занимает вообще: горутина паркуется, сокет регистрируется в netpoller (epoll/kqueue/IOCP), и горутина будится, когда придут данные.
- Поэтому десятки тысяч горутин, ждущих ответа по сети, почти ничего не стоят — на этом и держится модель «горутина на запрос».

**Goroutine leaks**

Утечка — горутина, которая никогда не завершится: висит на канале или в бесконечном цикле, держит стек и всё, на что ссылается.

Типичные причины:
- пишем в канал, который никто не читает (или читаем из канала, куда никто не пишет);
- забыли `cancel()` у контекста, горутина ждёт отмену вечно;
- воркер без выхода по `ctx.Done()`.

Как бороться:
- всегда давать горутине **условие выхода**: `select` с `<-ctx.Done()`;
- `defer cancel()` для каждого `WithCancel`/`WithTimeout`;
- закрывать канал на стороне отправителя, чтобы читатели вышли из `range`;
- ловить: `runtime.NumGoroutine()` в метриках (растёт монотонно → течёт), `pprof` `/debug/pprof/goroutine`, в тестах — `go.uber.org/goleak`.

### 12. Stacks vs Heap. Escape анализ. Garbage collector - как работает? как посмотреть, убегает переменная в хип или нет

**EN:** Stack vs heap. Escape analysis. How does the garbage collector work? How do you check whether a variable escapes to the heap?

**Stack vs Heap**

| | Стек | Куча (heap) |
|---|---|---|
| Что хранит | Локальные переменные, кадры вызовов | Всё, что должно жить дольше функции |
| Освобождение | Автоматически при выходе из функции (LIFO) | Сборщик мусора |
| Скорость | ~в 10 раз быстрее | Медленнее + нагрузка на GC |
| Размер | Должен быть известен на этапе компиляции | Динамический |

- У каждой горутины **свой** стек: стартует с ~2 КБ и растёт по мере необходимости.
- **GC следит только за кучей** — стек чистится сам, без его участия. Отсюда правило: меньше аллокаций в куче → меньше работы GC → стабильнее latency.

**Escape-анализ**

Компилятор сам решает, где разместить значение. Если он **не может доказать**, что переменная умрёт вместе с функцией, — она «убегает» в кучу.

Типичные причины убегания:
- возвращаем указатель на локальную переменную (`return &x`);
- передаём в `interface{}` — например, любой `fmt.Println(x)`;
- захватываем переменную в горутину или замыкание, которое живёт дольше функции;
- сохраняем в глобальную переменную, в мапу или в поле структуры, живущей дальше;
- слишком большое значение, которое не помещается на стек.

**Как посмотреть, убегает или нет**

```sh
go build -gcflags="-m" ./...      # решения escape-анализа
go build -gcflags="-m -m" ./...   # подробнее, с причинами
```
В выводе ищем строки `escapes to heap` и `moved to heap: x`. Против `does not escape` — значит осталась на стеке.

Дополнительно:
```sh
go test -bench=. -benchmem        # покажет allocs/op — сколько аллокаций на операцию
```
`-benchmem` — самый практичный способ: оптимизировали код → число `allocs/op` упало.

**Как работает GC**

- **Трассирующий, mark & sweep, конкурентный, не перемещающий** (объекты не двигаются в памяти, поэтому адреса стабильны).
- Работает по **трёхцветной** схеме: белые — кандидаты на удаление, серые — найдены, но их ссылки ещё не просмотрены, чёрные — просмотрены полностью. Стартуем от корней (стеки горутин, глобальные переменные), красим достижимое; что осталось белым — мусор, память переиспользуется.
- Основная работа идёт **параллельно с программой**. Stop-the-world паузы есть, но короткие (обычно доли миллисекунды) — только на старте и в конце фазы разметки.
- **Когда запускается:** по умолчанию когда куча выросла на `GOGC` процентов от размера после прошлой сборки (`GOGC=100` — при удвоении). Есть `GOMEMLIMIT` — мягкий потолок памяти, полезен в контейнерах с лимитом; GC начнёт стараться сильнее, приближаясь к нему.
- Компромисс всегда один: чаще собирать → меньше памяти, но больше CPU; реже → наоборот.

### 13. Какие бывают мьютексы и чем отличаются? Сравнение с атомиками. Как сделать через канал?

**EN:** What kinds of mutexes are there and how do they differ? How do they compare to atomics? How would you build one with a channel?

**Два вида мьютексов**

- **`sync.Mutex`** — эксклюзивная блокировка: `Lock()`/`Unlock()`, внутри критической секции одна горутина, неважно читает она или пишет.
- **`sync.RWMutex`** — разделяет доступ: `RLock()` — читателей может быть много одновременно, `Lock()` — писатель один и в этот момент никто не читает.

Когда что: `RWMutex` берут, когда **чтений сильно больше записей** (кэш на мапе, конфиг, справочник). Если операции короткие и конкуренции мало, обычный `Mutex` быстрее — у `RWMutex` больше накладных расходов внутри.

Что важно помнить про оба:
- Нулевое значение готово к работе: `var mu sync.Mutex`, инициализировать не надо.
- **Нельзя копировать** после первого использования — копия структуры с мьютексом внутри ломает защиту. Отсюда правило передавать такие структуры по указателю; `go vet` это ловит.
- **Не реентерабельный**: повторный `Lock()` в той же горутине = deadlock.
- Не привязан к горутине — `Unlock()` может сделать другая горутина, рантайм это допускает.
- Всегда `defer mu.Unlock()` сразу после `Lock()`, чтобы не потерять разблокировку на раннем `return` или панике.

**Сравнение с атомиками (`sync/atomic`)**

```go
var counter atomic.Int64   // Go 1.19+: типизированные атомики
counter.Add(1)
v := counter.Load()
```
- Атомик — **одна** операция над **одной** переменной (счётчик, флаг, указатель), выполняется процессорной инструкцией, без блокировок и парковки горутин → заметно быстрее.
- Мьютекс — для **критической секции**: несколько связанных действий, которые должны выглядеть атомарно снаружи (проверил и изменил, обновил два поля разом).
- Правило: одно действие над одной переменной (`counter.Add(1)`) — атомик. Несколько действий подряд, между которыми никто не должен влезть («прочитать значение → посчитать → записать обратно») — мьютекс: с атомиком другая горутина вклинится в середине и её изменение потеряется.
- `CompareAndSwap` («сравни и поменяй») — меняет значение, только если оно всё ещё равно ожидаемому, иначе возвращает `false` и мы пробуем заново. На этом строят lock-free алгоритмы, но писать их руками сложно и легко ошибиться — на практике почти всегда достаточно мьютекса.

**Мьютекс через канал**

Буферизованный канал ёмкостью 1: положили значение — захватили, забрали — освободили.

```go
mu := make(chan struct{}, 1)

mu <- struct{}{}          // Lock: если занято, блокируемся
// критическая секция
<-mu                       // Unlock
```
- Медленнее `sync.Mutex` — канал внутри и так содержит мьютекс плюс очереди ожидания.
- Но умеет то, чего `sync.Mutex` не умеет: **захват с таймаутом или отменой**, потому что канал работает в `select`:
  ```go
  select {
  case mu <- struct{}{}:   // захватили
  case <-ctx.Done():        // не дождались — выходим
      return ctx.Err()
  }
  ```
- Если увеличить ёмкость до N — получится семафор, ограничивающий число одновременно работающих горутин.
- В обычном коде — `sync.Mutex`; канал берут именно ради `select` с `ctx`.

### 14. sync.Once vs init()

**EN:** `sync.Once` vs `init()`.

Оба гарантируют «выполнить ровно один раз», но отличаются **моментом** запуска и гибкостью.

| | `init()` | `sync.Once` |
|---|---|---|
| Когда выполняется | При инициализации пакета, **до `main()`** | При **первом вызове** `Do()` — лениво |
| Кто вызывает | Рантайм, автоматически | Вы сами, явно |
| Можно вернуть ошибку | Нет — только `panic`/`log.Fatal` | Да, сохранить в переменную |
| Параметры | Нет | Да, через замыкание |
| Если функциональность не нужна | Всё равно отработает | Не отработает вообще |
| Тестируемость | Плохая — не отключить, не подменить | Хорошая |

**`init()`**

```go
var re = regexp.MustCompile(`^\d+$`)

func init() {
    // выполнится один раз при загрузке пакета
}
```
- Порядок: импортируемые пакеты → переменные пакета → `init()` → `main()`.
- В одном пакете может быть несколько `init()` (даже в одном файле), вызвать вручную нельзя.
- Подходит для: регистрации в реестре (драйверы `database/sql`, кодеки), компиляции регулярок, простой настройки пакета.
- Минусы: скрытая магия — код выполняется, хотя его никто явно не звал; нельзя вернуть ошибку; замедляет старт, даже если фича не используется.

**`sync.Once`**

```go
var (
    once sync.Once
    db   *sql.DB
    err  error
)

func GetDB() (*sql.DB, error) {
    once.Do(func() {
        db, err = sql.Open("postgres", dsn)
    })
    return db, err
}
```
- Все параллельные вызовы `Do()` блокируются, пока первый не завершится — после возврата значение гарантированно готово.
- Подходит для ленивой инициализации дорогого ресурса: соединение с БД, клиент, тяжёлый кеш.
- **Подвох:** если функция внутри `Do` запаниковала — `Once` всё равно считается использованным, повторно она не вызовется. Ошибку надо сохранять и возвращать самому.
- Копировать `sync.Once` нельзя (внутри мьютекс).
- С Go 1.21 есть удобные обёртки: `sync.OnceFunc`, `sync.OnceValue`, `sync.OnceValues` — то же самое, но без ручной возни с переменными.

**Итог одной фразой**

`init()` — когда инициализация нужна всегда и не может провалиться. `sync.Once` — когда она дорогая, может понадобиться не всегда или может вернуть ошибку.

### 15. Waitgroups и sync.Pool - зачем нужны? Изменения в waitgroups в версии Go 1.25

**EN:** What are WaitGroups and `sync.Pool` for? What changed in WaitGroups in Go 1.25?

**`sync.WaitGroup` — дождаться группы горутин**

Счётчик: `Add(n)` увеличивает, `Done()` уменьшает, `Wait()` блокирует, пока счётчик не станет нулём.

```go
var wg sync.WaitGroup
for _, url := range urls {
    wg.Add(1)
    go func() {
        defer wg.Done()
        fetch(url)
    }()
}
wg.Wait()
```
- `Add` вызывать **до** запуска горутины, а не внутри неё — иначе `Wait` может проскочить раньше, чем счётчик увеличится.
- `Done` — всегда через `defer`, иначе при панике или раннем `return` счётчик не уменьшится и `Wait` зависнет навсегда.
- Копировать нельзя — передавать только по указателю (`*sync.WaitGroup`).
- WaitGroup только **ждёт**, ошибки не собирает. Нужны ошибки и отмена остальных задач при первой неудаче — берём `errgroup.Group`: он поверх WaitGroup + Context.

**Изменение в Go 1.25 — метод `WaitGroup.Go`**

```go
var wg sync.WaitGroup
wg.Go(task1)      // сам делает Add(1), запускает горутину и Done() по завершении
wg.Go(task2)
wg.Wait()
```
- Убирает главный источник багов: не забудешь `Add(1)` и `defer wg.Done()`.
- Ограничение: функция внутри `Go` **не должна паниковать**.

**`sync.Pool` — переиспользовать объекты, чтобы не грузить GC**

Вместо «создал → выбросил» делаем «взял → попользовался → вернул». `Get()` берёт объект из пула (или создаёт через `New`), `Put()` возвращает обратно.

```go
var bufPool = sync.Pool{
    New: func() any { return new(bytes.Buffer) },
}

buf := bufPool.Get().(*bytes.Buffer)
defer func() {
    buf.Reset()          // обязательно чистим перед возвратом
    bufPool.Put(buf)
}()
```
**Проблема, которую решает.** Сервер на 10k RPS создаёт по временному объекту на каждый запрос (буфер под JSON, парсер) — это 10 000 объектов в секунду, и все сразу становятся мусором. GC вынужден постоянно их подчищать и жрёт CPU. С пулом вместо тысяч новых объектов крутится десяток одних и тех же.

*Зачем вообще буфер, если можно писать сразу в `w`: чтобы собрать ответ целиком до отправки — узнать `Content-Length`, а если сериализация упадёт на середине, ещё успеть вернуть 500 вместо статуса 200 с обрезанным JSON.*

- Экономится не время (~5%), а **память**: в замерах на JSON в 8 КБ — 8269 B/op без пула против 24 B/op с пулом. Меньше мусора → меньше работы GC → стабильные p99 на проде.
- Выигрыш тем больше, чем крупнее объект: переиспользуемый буфер уже вырос до нужного размера, новый каждый раз растёт с нуля с переаллокациями.
- **Это не пул соединений:** GC чистит пулы, объекты оттуда могут исчезнуть в любой момент. Для БД — `database/sql`. И вообще не для хранения состояния.
- Перед `Put` обязательно `Reset()`, иначе следующий запрос получит чужие данные.

**Когда использовать.** Только в горячем пути, где профилировка (`-benchmem`, `pprof`) показала проблему с аллокациями. В обычном CRUD-сервисе не нужен — там узкое место сеть и БД, а не GC.

**Где он уже работает у меня — chi.** Роутер держит в `sync.Pool` объект `RouteContext` (там URL-параметры и паттерн маршрута) и на каждый HTTP-запрос берёт его из пула, сбрасывает и в конце возвращает обратно — иначе это была бы аллокация на каждый входящий запрос. Я с этим объектом работаю в `pkg/router`: достаю оттуда паттерн маршрута для метрик через `chi.RouteContext(ctx)`.

Так же устроены и другие библиотеки: `fmt` держит в пуле структуру принтера на каждый `Printf`, `net/http` — bufio-буферы, `encoding/json` — состояние энкодера. Общее правило: **`sync.Pool` — инструмент библиотек на горячем пути, а не прикладного кода.**

### 16. Чем отличается value от pointer ресивера? Какой когда применять?

**EN:** What is the difference between a value receiver and a pointer receiver? When do you use each?

**В чём разница**

```go
func (u User) SetName(n string)  { u.Name = n }  // копия — изменение НЕ видно снаружи
func (u *User) SetName(n string) { u.Name = n }  // оригинал — изменение видно
```
Value receiver получает **копию** структуры, pointer receiver — **указатель** на оригинал.

**Какой когда**

Pointer receiver, если:
- метод **меняет** состояние — иначе правка уйдёт в копию;
- тип **большой** — копировать на каждый вызов дорого;
- внутри есть `sync.Mutex`, `sync.WaitGroup`, `atomic.*` — их **нельзя копировать**, копия сломает защиту (`go vet` ругается).

Value receiver — для маленьких неизменяемых значений: `Point{X, Y float64}`, `time.Time`, свои типы вроде `type Email string`.

Практика: **не смешивать** receivers на одном типе. Если хоть один метод требует указателя — делать указателями все, чтобы не путаться.

**Главный подвох — интерфейсы (method set)**

- Метод с **value receiver** → входит в method set и `T`, и `*T`.
- Метод с **pointer receiver** → входит только в method set `*T`.

Отсюда: если метод объявлен с pointer receiver, интерфейс реализует **только `*T`**:
```go
type Speaker interface{ Hello() }
func (u *User) Hello() {}

var s Speaker = User{}   // ❌ не компилируется: User does not implement Speaker
var s Speaker = &User{}  // ✅
```

**Почему тогда обычный вызов работает**

```go
u := User{}
u.Hello()      // ✅ компилятор сам подставляет (&u).Hello()
```
Это отдельное правило — **автоматическое взятие адреса** для адресуемых значений, к method set отношения не имеет. Не сработает там, где значение неадресуемо:
```go
User{}.Hello()      // ❌ композитный литерал не адресуем
m["key"].Hello()    // ❌ элемент мапы не адресуем
```
При присваивании в интерфейс адрес автоматически **не берётся** — там проверяется только формальный method set.

### 17. Что такое интерфейс? а под капотом? примеры стандартных интерфейсов. Где размещать интерфейсы? Сравнение с Java интерфейсами

**EN:** What is an interface? What does it look like under the hood? Examples of standard library interfaces. Where should interfaces be declared? How do they compare to Java interfaces?

**Что это**

Набор сигнатур методов. Тип реализует интерфейс **неявно** — просто имея все его методы, без ключевого слова `implements`.
```go
type Stringer interface{ String() string }

type Point struct{ X, Y int }
func (p Point) String() string { return "point" }

var s Stringer = Point{1, 2}   // Point реализует Stringer сам собой
```

**Под капотом**

Интерфейсное значение — это **пара из двух полей** (16 байт): тип и указатель на данные.
- `iface` — интерфейс с методами: `itab` (таблица методов конкретного типа + сам тип) + указатель на значение.
- `eface` — пустой интерфейс `any`: просто тип + указатель на значение.

Отсюда главная ловушка — **typed nil**:
```go
var p *MyErr = nil
var err error = p    // пара (*MyErr, nil) — тип заполнен!
err == nil           // false
```
Интерфейс равен `nil`, только если пусты **обе** части пары. Поэтому функция, возвращающая интерфейс, должна возвращать литеральный `nil`, а не nil-указатель конкретного типа.

**Стандартные интерфейсы**

- `error` — `Error() string`
- `io.Reader` / `io.Writer` — `Read`/`Write`, на них держится вся работа с потоками
- `fmt.Stringer` — `String() string`, вызывается при печати
- `sort.Interface` — `Len`, `Less`, `Swap`
- `http.Handler` — `ServeHTTP`
- `context.Context`

Все они **маленькие**, по 1–3 метода. Правило Роба Пайка: *«чем больше интерфейс, тем слабее абстракция»*.

**Где размещать**

Интерфейс объявляют **у потребителя**, а не в пакете с реализацией. Пакет-реализация про интерфейс вообще не знает — просто пишет структуру с нужными методами.

У меня в `user-service`: интерфейсы `Postgres` и `Kafka` объявлены в `internal/usecase/usecase.go` — там, где их вызывают. А `internal/adapter/postgres` ничего про них не импортирует, просто реализует методы. Благодаря этому в тестах вместо реального адаптера подставляется мок.

Исключение — общие абстракции вроде `io.Writer`: их и потребляют, и реализуют десятки пакетов, поэтому они живут в отдельном общем пакете.

**Сравнение с Java**

| | Go | Java |
|---|---|---|
| Реализация | Неявная — есть методы, значит реализует | Явная: `class X implements Y` |
| Кто объявляет | Потребитель | Обычно автор реализации |
| Зависимость | Реализация **не знает** про интерфейс | Класс жёстко привязан к интерфейсу |
| Размер | Маленькие, 1–3 метода | Часто крупные контракты |
| Реализация по умолчанию | Нет | Есть `default`-методы |

Главное отличие: в Java интерфейс — это контракт **сверху вниз** (сначала объявили, потом реализовали). В Go — **снизу вверх**: потребитель описывает, что ему нужно, а любой подходящий тип автоматически подходит. Поэтому в Go легко обернуть чужой тип из библиотеки в свой интерфейс, не трогая его код.

### 18. Что такое мок? Какие пакеты использовал для моков?

**EN:** What is a mock? Which packages have you used for mocking?

**Что такое мок**

Подставная реализация интерфейса для тестов: вместо реальной БД возвращает заранее заданный ответ и запоминает, как её вызывали. Нужен, чтобы юнит-тест не ходил в настоящую базу и чтобы легко воспроизвести редкие сценарии (таймаут, «нет строки», сетевая ошибка).

Работает это благодаря тому, что интерфейсы объявлены **у потребителя** (вопрос 17): usecase зависит от интерфейса `Postgres`, поэтому в тесте вместо адаптера подставляется мок.

**Чем пользуюсь — mockery + testify**

Конфиг в `.mockery.yml`: моки генерируются для всех интерфейсов пакета `usecase` и складываются в `internal/usecase/mocks`. Генерация — `make mocks`, файлы помечены `// Code generated ... DO NOT EDIT` и руками не правятся.

В тесте задаём, что мок должен вернуть на конкретный вызов:
```go
postgres.On("GetUser", Any, id).Return(domain.User{ID: id}, nil)          // успех
postgres.On("GetUser", Any, id).Return(domain.User{}, domain.ErrNotFound) // «не найдено»
postgres.On("GetUser", Any, id).Return(domain.User{}, errors.New("conn refused")) // сбой БД
```
Mockery сам вешает `t.Cleanup` с `AssertExpectations` — тест упадёт, если ожидаемый вызов так и не произошёл.

**Другие варианты**

- **mockgen** (`go.uber.org/mock`, форк заброшенного `golang/mock`) — второй популярный генератор, синтаксис `EXPECT().Method(args).Return(...)`, строже следит за порядком и количеством вызовов.
- **Заглушка руками** — для интерфейса из 1–2 методов проще написать самому, чем тащить генератор.
- **testcontainers** — уже не мок: поднимает настоящую БД в Docker. У меня на этом интеграционные тесты в `test/integration` с build-тегом.

**Mock vs fake**

- **Mock** — проверяет **факт вызова**: что вызвали, с какими аргументами, сколько раз (behavior verification).
- **Fake** — упрощённая рабочая реализация с состоянием (`map[uuid.UUID]domain.User` вместо Postgres): записали → можно прочитать (state verification).

Критерий выбора:
- Сценарий create → update → get, где важно **состояние между вызовами** → fake. С моком пришлось бы прописывать ответ на каждый шаг вручную, и тест начинает сам симулировать правильное поведение — то есть уже ничего не проверяет.
- Внешняя система (платёжный шлюз, брокер), где важен **контракт взаимодействия** → mock.

Риски: мок завязывает тест на то, *как* вызывается зависимость, — рефакторинг без смены поведения его ломает. Fake может незаметно разойтись с реальностью (не воспроизвести ошибку unique-constraint) и давать ложную уверенность, поэтому контракт стоит сверять интеграционным тестом.

Общий плюс: моки типизированы, поэтому смена сигнатуры интерфейса ломает тест **на этапе компиляции**, а не в рантайме.

### 19. Есть ли наследование в Го?

**EN:** Is there inheritance in Go?

**Нет.** Вместо него — композиция через embedding.

```go
type Engine struct{ HP int }
func (e Engine) Start() { fmt.Println("start") }

type Car struct {
    Engine        // встраивание: анонимное поле
    Brand string
}

car := Car{}
car.Start()       // работает — метод "продвинулся" (promotion)
car.HP = 150      // поля тоже продвигаются
```

**Почему это не наследование**

- Нет `super`, виртуальных методов и `override`. Promotion — сахар компилятора: `car.Start()` разворачивается в `car.Engine.Start()`.
- Метод есть и у `Car`, и у `Engine` — внешний **затеняет** внутренний, а не переопределяет. Receiver внутри остаётся `Engine`, полей `Car` он не видит.
- Нельзя передать `Car` туда, где ждут `Engine` — это разные типы, subtype-полиморфизма нет.

**Столпы ООП в Go**

| Столп | Есть? | Чем реализован |
|---|:---:|---|
| Инкапсуляция | ✅ | Регистр первой буквы имени |
| Полиморфизм | ✅ | Интерфейсы |
| Наследование | ❌ | Композиция (embedding) |

Полиморфизм даёт **интерфейс**, а не embedding: то, что одна структура содержит другую, динамического поведения само по себе не добавляет.

### 21. Panic, defer, recover. 3 правила defer. Паниковать - хорошо?

**EN:** Panic, defer, recover. The three rules of defer. Is panicking a good thing?

**Что это**

- `defer` — отложить вызов до выхода из функции (обычного или через панику).
- `panic` — аварийно прервать выполнение: разворачивается стек, по пути отрабатывают все `defer`.
- `recover` — перехватить панику и вернуть управление, работает **только внутри `defer`**.

**3 правила defer**

1. **LIFO** — отложенные вызовы выполняются в обратном порядке, последний зарегистрированный первым.
2. **Аргументы вычисляются сразу**, в момент `defer`, а не при выполнении:
   ```go
   i := 0
   defer fmt.Println(i)               // напечатает 0 — значение зафиксировано здесь
   defer func() { fmt.Println(i) }()  // напечатает 100 — замыкание читает позже
   i = 100
   ```
3. **Выполняется всегда** при выходе из функции — в том числе при `return` и при панике. Поэтому `defer` и используют для освобождения ресурсов: `defer f.Close()`, `defer mu.Unlock()`, `defer cancel()`.

**recover**

```go
defer func() {
    if r := recover(); r != nil {
        log.Error().Any("panic", r).Msg("recovered")
    }
}()
```
- Работает, только если вызван **напрямую** в теле `defer func(){...}()`. Уровнем глубже — не сработает.
- Ловит панику **только в своей горутине**: паника в соседней горутине уронит весь процесс.
- Через именованный результат можно превратить панику в ошибку: `defer func(){ if r := recover(); r != nil { err = fmt.Errorf("panic: %v", r) } }()`.

**Паниковать — хорошо?**

Нет, в обычном коде — плохо. Штатные ситуации («не нашли», «невалидный ввод») возвращаются как `error`. Паника — для того, что означает **баг или нарушенный инвариант**, когда продолжать бессмысленно.

Где уместно:
- на старте приложения, если конфиг битый или не поднялось соединение — лучше упасть сразу, чем работать наполовину (`log.Fatal`, `MustCompile`);
- функции с префиксом `Must*` — контракт «на входе заведомо валидные данные»;
- в тестах.

Где паника случается не по вашей воле — её надо ловить: HTTP-middleware `Recoverer` (у меня стоит в `pkg/router`) перехватывает панику в хендлере, чтобы один сломанный запрос не уронил весь сервис, и отвечает 500.

### 22. Что такое race condition? А data race? как их ловить/дебажить?

**EN:** What is a race condition? And a data race? How do you catch and debug them?

**Разница**

- **Data race** — техническая проблема: две горутины обращаются к одной памяти без синхронизации, и **хотя бы одна пишет**. Неопределённое поведение, ловится инструментом.
  - Двух писателей не требуется: один пишет + один читает — уже гонка. Читатель может поймать наполовину записанное значение: слайс — это три поля (`ptr`, `len`, `cap`), интерфейс — два, и присваивание такой структуры **не атомарно** — процессор пишет её за несколько операций. Читатель успевает влезть в середину и увидеть новый `ptr` со старым `len`. Плюс без синхронизации компилятор и процессор вправе переупорядочить операции. Безопасно только когда **никто** не пишет.
- **Race condition** — логическая проблема: результат зависит от того, кто успел первым. Может быть **без** data race — например, каждый шаг под мьютексом, но сама последовательность шагов неверна.

```go
// data race — счётчик без синхронизации
counter++                       // из нескольких горутин

// race condition без data race — каждая операция защищена, а логика сломана
mu.Lock(); v := balance; mu.Unlock()
v -= 100
mu.Lock(); balance = v; mu.Unlock()   // чужое списание между Lock'ами потеряется
```

Отсюда важное: **детектор находит только data race**. Race condition он не увидит — её ловят логикой, тестами и ревью.

**Как ловить**

```sh
go test -race ./...     # основной способ, в CI обязательно
go run -race .          # локально
go build -race          # редко, для отладочного билда
```
- Детектор перехватывает обращения к памяти в рантайме и печатает **обе** стороны гонки со стеками: кто читал, кто писал.
- Находит только то, что **реально произошло** во время выполнения — поэтому важны тесты, которые действительно гоняют конкурентный код (`t.Parallel()`, нагрузка в цикле).
- Цена: программа медленнее в 5–10 раз и ест больше памяти, поэтому в прод-сборку `-race` не кладут.

**Что ещё помогает**

- `go vet` — статический анализ, ловит часть проблем (например, копирование структуры с мьютексом).
- Явные проверки рантайма: `fatal error: concurrent map writes` — уже сигнал, что мапа не защищена.
- Ревью: если поле структуры пишется из горутины, спрашиваем, чем оно защищено.

**Как чинить** — мьютекс/`RWMutex` вокруг общего состояния, атомики для одиночных счётчиков, либо горутина-владелец и общение через канал.

### 23. Как профилировать гошный код?

**EN:** How do you profile Go code?

**Порядок действий:** сначала бенчмарк или метрика показывает, что проблема есть, потом профиль показывает, **где** она. Оптимизировать без замера — гадание.

**1. Бенчмарки — точечно, на функции**

Пишутся в файле `*_test.go`, функция обязательно начинается с `Benchmark` и принимает `*testing.B`:
```go
func BenchmarkEncodeUser(b *testing.B) {
    user := User{Name: "Alice"}   // подготовка не измеряется
    for b.Loop() {                 // Go 1.24+; до этого — for i := 0; i < b.N; i++
        json.Marshal(user)
    }
}
```
`b.Loop()` сам сбрасывает таймер после подготовки и останавливает перед очисткой — удобнее, чем ручной `b.ResetTimer()`.

```sh
go test -bench=. -benchmem -run='^$'    # все бенчмарки: ns/op, B/op, allocs/op
go test -bench=BenchmarkEncodeUser      # только нужный, -bench принимает regexp
go test -bench=. -benchmem -count=5     # несколько прогонов
```
`-run='^$'` — чтобы вместе с бенчмарками не гонялись обычные тесты (по умолчанию `-bench` их не отключает, и они искажают замер).

Сравнить до/после — `benchstat` (не встроен, ставится отдельно: `go install golang.org/x/perf/cmd/benchstat@latest`): сохраняем вывод в два файла и `benchstat old.txt new.txt` покажет разницу с учётом разброса.

`allocs/op` — первое, на что смотрю: лишние аллокации обычно и есть причина нагрузки на GC.

**2. pprof — на живом сервисе**

Подключается одной строкой — пакет в своём `init()` регистрирует хендлеры `/debug/pprof/*`:
```go
import _ "net/http/pprof"   // импорт ради side-effect

go http.ListenAndServe("localhost:6060", nil)   // nil = DefaultServeMux
```
Наружу этот порт не выставляем: через `/debug/pprof/` видны стеки и аргументы запуска. Только `localhost` или закрытый внутренний порт.

Снимаем и смотрим:
```sh
kubectl port-forward pod/user-service-xxx 6060:6060                    # в k8s
curl -s 'localhost:6060/debug/pprof/profile?seconds=30' > cpu.pprof    # CPU за 30 сек
curl -s 'localhost:6060/debug/pprof/heap' > mem.pprof                   # память
go tool pprof -http=:8080 cpu.pprof                                      # смотрю локально в браузере
```
Профиль — обычный файл: скачиваем с пода и открываем у себя, на сервере ничего смотреть не нужно.

Виды: `profile` (CPU), `heap` (память), `goroutine` (сколько горутин и где висят — так ловятся утечки), `mutex` и `block` (конкуренция за локи, включаются отдельно).

В веб-интерфейсе смотрю **flame graph** — видно, какая функция реально ест время, и Top — плоский список по `cum`/`flat`.

Альтернатива ручному снятию — **continuous profiling** (Pyroscope, Datadog): агент снимает профили постоянно, смотришь в UI как метрики и сравниваешь с прошлой неделей. Первая линия при этом всё равно метрики Prometheus — `go_goroutines`, `go_memstats_*`, паузы GC: они говорят «что-то не так», а профиль уже отвечает «где».

**3. trace — когда дело не в конкретной функции**

```sh
curl -s 'localhost:6060/debug/pprof/trace?seconds=5' > trace.out
go tool trace -http=:8080 trace.out
```
Показывает работу планировщика: сколько ждали горутины, паузы GC, блокировки на syscall. Нужен, когда CPU-профиль ровный, а latency плохая.

**4. Сравнение до/после**

```sh
go tool pprof -http=:8080 -base=old.pprof new.pprof
```
Главная проверка, что оптимизация реально сработала, а не переставила проблему в другое место.

**На интервью стоит добавить:** профилировать надо под нагрузкой, близкой к боевой, и на одном профиле выводов не делать — снимать несколько раз. И начинать всегда с метрик (p99, RPS, память), а не сразу с pprof: он говорит «где горячо», но не говорит, что это вообще проблема.

### 24. Каким логгером пользуешься? Какие знаешь?

**EN:** Which logger do you use? Which ones do you know?

**Пользуюсь zerolog** — обёрнут в `pkg/logger`: настройка вывода, gRPC-интерсептор на каждый вызов, адаптер для kafka-go.

```go
log.Error().Err(err).Str("user_id", id).Msg("get user failed")
```
Даёт JSON без настройки и типизированный chain-API (`.Str()`, `.Int()`, `.Err()`) — в отличие от `slog`, где поля идут парами `"key", val` и при лишнем аргументе получается битая запись. Выбор отчасти исторический: стоял в шаблоне проекта. Новый сервис начал бы с `log/slog` — он в стандартной библиотеке и не тянет зависимость.

**Какие знаю**

| Логгер | Зависимость | Стиль API | Скорость | Плюсы |
|---|---|---|---|---|
| `log` | stdlib | `log.Print("msg")`, без полей | — | ноль настройки, есть везде |
| `log/slog` | stdlib, 1.21+ | пары: `slog.Info("msg", "k", v)` | средняя | без зависимостей, свои handler'ы, общий стандарт для библиотек |
| `zerolog` | внешняя | chain: `.Str().Int().Msg()` | zero-alloc | типобезопасные поля, JSON из коробки, глобальный логгер |
| `zap` | внешняя | `zap.String(...)` / Sugared | zero-alloc | два режима — строгий и упрощённый, богатая экосистема |

Главное деление: `log` — не структурный, поля в него не положишь, поэтому для сервиса не годится. Остальные три структурные и отличаются в основном синтаксисом и тем, тянуть ли зависимость.

**Три правила в проде**

1. **Логировать ошибку один раз** — там, где по ней принимается решение, то есть в контроллере. Ниже по стеку только `%w` и проброс, иначе одна проблема даёт пять записей с разных слоёв.
2. **Структурно и с trace ID** — поля, а не `fmt.Sprintf`, иначе в Loki не отфильтровать; без trace ID не связать записи одного запроса.
3. **Уровни по делу** — `Error` только то, на что реагирует дежурный; «не нашли юзера» это не ошибка сервиса. `Debug` в проде выключен, логи стоят денег.

### 25. Что такое линтер? каким пользуешься?

**EN:** What is a linter? Which one do you use?

**Что это**

Статический анализатор: разбирает код, **не запуская его**, и ищет то, что компилируется, но является ошибкой или плохой практикой — необработанная ошибка, незакрытое тело ответа, копирование мьютекса, мёртвый код.

Отличие от компилятора: компилятор проверяет, что код валиден; линтер — что он корректен и единообразен.

**Чем пользуюсь — golangci-lint**

Это не один линтер, а агрегатор: запускает десятки анализаторов за один проход и параллельно, конфиг в `.golangci.yml`.

**Базовый набор (включён по умолчанию, самое нужное):**

```go
// errcheck — проглоченная ошибка. Самый важный линтер в Go
json.Unmarshal(data, &user)        // ❌ ошибка не проверена, user может остаться пустым
defer f.Close()                     // ❌ ошибка записи на диск потеряется

// govet — неверный Printf и копирование мьютекса
fmt.Printf("%d", "строка")          // ❌ несовпадение типа и глагола
func (m Mutex) Do() {}              // ❌ value receiver копирует мьютекс — защита не работает

// staticcheck — реальные баги и упрощения
if err != nil { return err }
return err                           // ❌ бессмысленно, всегда nil
strings.Replace(s, "a", "b", -1)     // ❌ есть strings.ReplaceAll

// ineffassign — присваивание, которое никто не прочитает
x := compute()
x = 5                                // ❌ результат compute() выброшен

// unused — мёртвый код
func helper() {}                     // ❌ нигде не вызывается
```

**Что добавляю сверху:**

```go
// bodyclose — утечка соединений, вылезает только под нагрузкой
resp, _ := http.Get(url)
data, _ := io.ReadAll(resp.Body)     // ❌ нет resp.Body.Close()

// noctx — запрос без контекста, значит без таймаута и отмены
http.Get(url)                        // ❌ надо http.NewRequestWithContext(ctx, ...)

// gosec — типовые уязвимости
db.Query("SELECT * FROM users WHERE id = " + id)  // ❌ SQL-инъекция
md5.New()                                          // ❌ слабый алгоритм

// unparam — параметр, который не используется
func send(msg string, retries int) {}  // ❌ retries нигде не читается

// unconvert — лишнее приведение
var i int = 5
_ = int(i)                            // ❌ i уже int
```

`gocritic` — дополнительная диагностика и стилевые замечания, `misspell` — опечатки в комментариях и строках.

Плюс форматтеры `gofmt` и `goimports`. Исключены `_test.go` и `gen/` — сгенерированный код править всё равно нельзя.

**Как запускается**

```sh
golangci-lint run          # локально, обычно через make lint
go vet ./...               # встроенный, часть проверок, без установки
```
Обязательно в CI отдельным шагом — чтобы нельзя было смёржить код, который не проходит проверку.

**Зачем это на практике:** снимает с ревью споры о стиле и ловит целый класс багов до прода. `bodyclose` и `errcheck` — самые полезные: незакрытые тела и проглоченные ошибки иначе всплывают только под нагрузкой.

### 26. Нужны ли ORM? Каким пользуешься? Какие знаешь?

**EN:** Do we need ORMs? Which one do you use? Which ones do you know?

**Нужны ли ORM**

Обязательными — нет. В Go принято писать SQL явно, а ORM прячет часть запросов: не видно, что уйдёт в базу, легко получить N+1, а нестандартный запрос всё равно придётся оптимизировать руками через `EXPLAIN`. Но это не «ORM — зло»: под быстрый однотипный CRUD они экономят много времени.

**Чем пользуюсь — чистый SQL на `pgx`**

```go
const sql = `INSERT INTO users (id, name, email, phone, birth_date, status)
             VALUES ($1, $2, $3, $4, $5, $6)`
_, err := txOrPool.Exec(ctx, sql, user.ID, user.Name, ...)
```
- *Почему:* запросы в сервисе простые, а контроль нужен полный — видно, что именно уйдёт в базу, и запрос можно скопировать в консоль. `pgx` даёт нативный протокол Postgres, его типы (`pgtype`) и пул соединений.
- *Минус:* ручной `Scan` и маппинг в структуру. Для CRUD-сервиса терпимо.

**Какие знаю**

**ORM (GORM, Ent)** — описываешь модели, SQL генерируется.
- **GORM** — на рефлексии, быстрый CRUD, админки, небольшие проекты.
- **Ent** — с кодогенерацией и типобезопасным API: меньше runtime-ошибок, но свой слой абстракции.
- *Минусы:* часть SQL скрыта, возможны N+1, сложно оптимизировать нестандартные запросы.

**Query Builder (Squirrel, goqu)** — SQL собирается программно, контроль сохраняется.
- *Когда:* динамические фильтры, поиск, сортировка, отчёты — много необязательных условий.

**sqlc** — генератор типобезопасного Go-кода из SQL.
- *Плюсы:* SQL остаётся явным, типы и запросы проверяются на этапе генерации, нет ручного `Scan` и рефлексии в рантайме.

**sqlc vs Squirrel** — разница в том, когда появляется финальный SQL: у `sqlc` на этапе сборки (ошибка видна сразу), у Squirrel в рантайме (узнаешь, когда запрос уйдёт в базу).

**Итог:** нужен контроль → `pgx`; убрать ручной `Scan`, сохранив явный SQL → `sqlc` (взял бы для проекта покрупнее); динамические запросы → `Squirrel`; быстрый CRUD без сложной логики → `GORM`.

Миграции при любом варианте отдельно: версионируемые SQL-файлы через `golang-migrate` (`migration/postgres`).

### 27. Что думаешь о дженериках в Го? Пользуешься? А go generate?

**EN:** What do you think about generics in Go? Do you use them? What about `go generate`?

**Дженерики — что это и зачем**

Появились в Go 1.18. Раньше, чтобы написать одну и ту же функцию для `int` и для `string`, было два пути — оба плохие: скопировать её дважды или взять `any` и потерять проверку типов.

```go
// было: работает с чем угодно, но компилятор не помогает
func Min(a, b any) any { ... }   // на выходе any, нужно приведение

// стало: один код, типы проверяются на компиляции
func Min[T int | float64 | string](a, b T) T {
    if a < b { return a }
    return b
}

Min(1, 2)        // T = int
Min("a", "b")     // T = string
Min(1, "a")       // ❌ ошибка компиляции
```
**Разбор синтаксиса**

```go
func Min[T int | float64 | string](a, b T) T {
//       └──────────┬───────────┘  └──┬──┘ └┬┘
//        type-параметр + ограничение │     └── тип возврата — тоже T
//                                    └── обычные аргументы, но их тип = T
```
При вызове тип подставляется автоматически:
```go
Min(1, 2)          // компилятор видит int → T = int
Min("a", "b")       // T = string
Min[int](1, 2)      // можно указать явно, если вывод не сработал
Min(1, "a")         // ❌ ошибка: T не может быть одновременно int и string
```
Ключевая идея: `T` — это «дырка», которую компилятор заполняет конкретным типом в момент вызова, и после этого проверяет всё как обычный типизированный код.

**Виды ограничений**

```go
[T any]                        // любой тип — как interface{}, но с проверкой
[T comparable]                 // поддерживает == и != : годится в ключи мапы
[T int | float64]              // перечисление конкретных типов
[T constraints.Ordered]        // готовые наборы из golang.org/x/exp/constraints
```
Ограничение — это **интерфейс**, просто расширенный: кроме методов в нём можно перечислять типы. Отсюда `~int` — тильда означает «`int` и любой тип с базовым `int`», чтобы работало и с `type UserID int`.

**Обобщать можно и типы, не только функции**

Напомню, как выглядит обычная структура — просто набор полей:
```go
type User struct {
    Name string
    Age  int
}
```

Теперь возьмём структуру-контейнер: внутри одно поле-слайс, куда складываем элементы.
```go
type Stack struct {
    items []int      // хранилище: слайс из int
}

func (s *Stack) Push(v int) {   // добавить элемент в конец
    s.items = append(s.items, v)
}

s := Stack{}
s.Push(1)
s.Push("a")   // ❌ нельзя: структура умеет только int
```
Проблема: такой контейнер работает **только с `int`**. Понадобился такой же для строк — придётся скопировать структуру и все её методы, заменив `int` на `string`.

С дженериком тип становится параметром — `int` заменяем на `T`:
```go
type Stack[T any] struct {
    items []T        // хранилище: слайс из T, тип решим позже
}

func (s *Stack[T]) Push(v T) {
    s.items = append(s.items, v)
}

s := Stack[int]{}       // здесь фиксируем: T = int
s.Push(1)
s.Push("a")              // ❌ нельзя: этот стек создан для int
```
`T` объявлен у структуры, методы просто им пользуются. Своих type-параметров у методов нет — это работает с 1.18.

**Чего нельзя**

- Специализации: «для `int` одна реализация, для остальных другая» — только `switch` внутри одной.
- Требовать наличие **поля**: ограничение проверяет только методы и типы, «у типа есть поле `ID`» не выразить.

**Как устроено внутри**

Ни как в C++ (копия кода под каждый тип), ни как в Java (типы стираются). В Go — промежуточный вариант: одна копия кода на группу типов с одинаковым представлением в памяти (все указатели делят одну, `int` и `float64` получают свои).

Практический вывод: дженерик **не обязательно быстрее** `interface{}` — для указателей внутри всё равно используется служебная таблица типов. Разницу нужно мерить бенчмарком, а не предполагать.

**Пользуюсь ли**

В бизнес-логике почти нет: там конкретные доменные типы, обобщать нечего. Зато постоянно пользуюсь готовыми — `slices` и `maps` из стандартной библиотеки (Go 1.21): `slices.Contains`, `slices.SortFunc`, `maps.Keys`. Раньше такие функции писали руками в каждом проекте.

Правило: дженерики — для утилит над коллекциями и библиотечного кода. Захотелось обобщить бизнес-логику — скорее всего, нужен интерфейс.

**Go 1.27 — появились дженерик-методы**

С 1.18 действовало ограничение: **метод не мог объявить свой type-параметр** — то есть `[...]` после имени метода писать было нельзя.

Пример: конфиг, который хранит всё строками, а отдавать должен нужным типом.
```go
type Config struct {
    values map[string]string
}

// ❌ до 1.27: method must have no type parameters
func (c *Config) Get[T int | string | bool](key string) T { ... }

port := cfg.Get[int]("port")       // хотим int
host := cfg.Get[string]("host")     // хотим string
```
Тип возврата зависит от того, что попросили — значит методу нужен свой параметр `T`. Именно `[T ...]` после имени метода и было запрещено.

Приходилось выносить в функцию пакета, хотя по смыслу это операция конфига:
```go
port := GetFromConfig[int](cfg, "port")   // вместо cfg.Get[int]("port")
```

В 1.27 запрет сняли. Пример из релиза: в `math/rand/v2` рядом с функцией `N[Int intType](Int) Int` появился метод `(*Rand) N[Int intType](Int) Int`.

Что осталось нельзя: объявлять методы с type-параметрами **в интерфейсах**, и дженерик-метод не может реализовать метод интерфейса.

Плюс в 1.27 расширили вывод типов — он теперь работает и когда дженерик-функцию присваивают переменной функционального типа.

**go generate**

Не генератор, а способ **положить команду генерации рядом с кодом**, чтобы её не искали в документации:

```go
//go:generate mockery
```
Запускается одной командой `go generate ./...` — она находит все такие комментарии и выполняет их.

У меня в проекте три точки генерации:
- `internal/usecase/usecase.go` → `mockery` — моки интерфейсов для тестов;
- `gen/http/...` → `oapi-codegen` — сервер и клиент из OpenAPI-спеки;
- gRPC-код из `.proto` через `protoc` (вызывается из `Makefile`).

Всё завёрнуто в `make generate`. Сгенерированное помечено `// Code generated ... DO NOT EDIT`, руками не правится и исключено из линтера — правим спеку и перегенерируем.

### 28. Для чего нужен пустой интерфейс? А пустая структура?

**EN:** What is the empty interface for? And the empty struct?

**Пустой интерфейс `interface{}` (он же `any` с Go 1.18)**

Интерфейс без методов — значит, ему удовлетворяет **любой** тип. Это способ сказать «сюда можно положить что угодно».

```go
var x any
x = 42
x = "hello"
x = &User{}
```
Где реально нужен:
- **`fmt.Println(a ...any)`** — печатать можно что угодно;
- **`encoding/json`** — `json.Unmarshal(data, &v)` принимает любую структуру;
- **`context.WithValue(ctx, key, val any)`** — значение произвольного типа.

Минусы: теряется проверка типов, чтобы достать значение — нужен type assertion (`v, ok := x.(int)`), и это ошибка уже в рантайме, а не при компиляции.

Поэтому **с приходом дженериков (1.18) `any` в новом коде нужен реже**: где раньше писали `func Min(a, b any) any`, теперь пишут `func Min[T ...](a, b T) T` с проверкой на компиляции (см. вопрос 27). Остаётся он там, где типов действительно заранее не знаем — сериализация, логирование, рефлексия.

**Пустая структура `struct{}`**

Тип, у которого **нет полей**, поэтому он занимает **0 байт**. Используется, когда важен сам факт, а не значение.

Три применения:

```go
// 1. Множество (set) — платим только за ключи
set := map[string]struct{}{}
set["a"] = struct{}{}
_, ok := set["a"]

// 2. Сигнальный канал — передаём «событие произошло», без данных
done := make(chan struct{})
close(done)          // сигнал всем читателям сразу

// 3. Семафор — ограничить число одновременно работающих горутин
sem := make(chan struct{}, 3)
sem <- struct{}{}    // занять слот
<-sem                 // освободить
```
Почему не `bool`: `bool` занимает 1 байт на элемент и добавляет бессмысленное состояние «ключ есть, а значение `false`». `struct{}` говорит прямо: значение не важно, важен факт.

**Не путать:** `interface{}` — «любой тип», 16 байт внутри. `struct{}` — конкретный тип без данных, 0 байт. Похожи только записью.

### 29. Как дебажишь Гошные программы?

**EN:** How do you debug Go programs?

**Обычный баг — тест и логи (90% случаев)**

Сначала пытаюсь воспроизвести проблему тестом: если получилось, дальше отладка занимает минуты, а тест остаётся и не даёт багу вернуться. Плюс структурные логи с trace ID — по ним видно путь запроса и где он свернул не туда. Для печати структуры `%+v`, а `%#v` — когда нужен ещё и тип (спасает с typed nil).

**Нужно пройти пошагово — Delve**

```sh
dlv debug ./cmd/app            # запустить приложение под отладчиком
dlv test ./internal/usecase    # отладить тест
dlv attach <pid>               # подключиться к работающему процессу
```
Команды внутри: `break main.go:42`, `continue`, `next`, `print v`, `goroutines`. Обычно пользуюсь через GoLand — под капотом там тот же Delve. Для отладки в контейнере его запускают в headless-режиме (`dlv --headless --listen=:2345`) и подключаются к нему из IDE по сети.

**Конкурентность и зависания — инструменты рантайма**

Тут отладчик бесполезен, у каждой проблемы свой инструмент:
- **гонка** → `go test -race`, покажет обе стороны конфликта;
- **дедлок** → рантайм сам печатает `fatal error: all goroutines are asleep` со стеками;
- **зависло, но не падает** → `kill -QUIT <pid>`: процесс выведет стеки всех горутин, видно кто на чём висит;
- **утечка горутин** → `/debug/pprof/goroutine?debug=2` плюс `runtime.NumGoroutine()` в метриках как первый сигнал.

**В проде отладчик не подключаю** — `dlv attach` останавливает процесс. Там только логи, метрики и pprof.
