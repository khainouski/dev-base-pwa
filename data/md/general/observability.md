# Observability

### 1. Три столпа observability (metrics, logs, traces). Чем отличаются? {gen}

* **Metrics** — числа во времени: RPS, процент ошибок, latency, память. Дёшево хранить, удобно для дашбордов и алертов. Отвечают на вопрос **«что-то не так?»**.
* **Logs** — события с подробностями: что произошло, с какими параметрами, какая ошибка. Отвечают на **«что именно произошло?»**. Дорого на больших объёмах.
* **Traces** — путь одного запроса через все сервисы с временем каждого шага. Отвечают на **«где именно тормозит или ломается?»**.

Как работают вместе: алерт по метрике (вырос p99) → трейс показал медленный сервис → логи этого сервиса по `trace_id` показали причину.

---

### 2. Три типа метрик {gen}

В Prometheus основных типа три (плюс Summary):

* **Counter** — только растёт (сбрасывается при рестарте): число запросов, ошибок. Смотрят скорость роста — `rate()`.
* **Gauge** — значение может расти и падать: память, число горутин, длина очереди.
* **Histogram** — распределение значений по корзинам (buckets): latency, размер ответа. Из него считают перцентили — `histogram_quantile()`.

**Summary** тоже считает перцентили, но на стороне клиента, и их нельзя агрегировать между инстансами — поэтому обычно берут Histogram.

```promql
rate(http_requests_total[5m])                                          # RPS
histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m])) # p99
```

### 3. Как измерять SLI, SLO и SLA? {gen}

* **SLI** (indicator) — **что измеряем**: метрика качества с точки зрения пользователя. Например, доля успешных запросов или доля запросов быстрее 300 мс.
* **SLO** (objective) — **внутренняя цель** для SLI: «99.9% запросов успешны за 30 дней».
* **SLA** (agreement) — **обещание клиенту** с последствиями (компенсации). Всегда мягче SLO, чтобы был запас.

**Как считать:**

```promql
# SLI доступности = успешные / все
sum(rate(http_requests_total{code!~"5.."}[30d]))
  / sum(rate(http_requests_total[30d]))
```

**Error budget** = 100% − SLO. При 99.9% это ~43 минуты простоя в месяц. Бюджет есть — можно смело релизить; кончился — замораживаем фичи и занимаемся надёжностью. Алертят по скорости сжигания бюджета (burn rate), а не по каждому всплеску.

### 4. Что такое high-cardinality метрик и чем это опасно? {gen}

**Кардинальность** — число уникальных комбинаций лейблов метрики. Каждая комбинация — отдельный временной ряд.

**High cardinality** — когда в лейбл кладут значения с огромным числом вариантов: `user_id`, `request_id`, email, полный URL с параметрами.

```
http_requests_total{user_id="..."}   # 1 млн пользователей = 1 млн рядов
```

**Чем опасно:**
* память и диск Prometheus растут взрывообразно, вплоть до OOM;
* запросы и дашборды тормозят;
* в платных системах (Datadog) — резкий рост счёта.

---

### 5. Как уменьшить high-cardinality метрики? {gen}

* **Не класть уникальные ID в лейблы** — `user_id`, `request_id` место в логах и трейсах, а не в метриках.
* **Нормализовать пути:** не `/users/123`, а шаблон роута `/users/{id}`.
* **Группировать значения:** коды ответов → `2xx/4xx/5xx`, неизвестные значения → `other`.
* **Удалять лишние лейблы** — `metric_relabel_configs` в Prometheus.
* **Агрегировать заранее** — recording rules.
* **Следить** — смотреть топ метрик по числу рядов (`/tsdb-status` в Prometheus).

### 6. Почему БД прометеуса так хороша для хранения метрик? {gen}

Prometheus TSDB заточена ровно под одну задачу — временные ряды:

* **Сжатие:** соседние точки почти одинаковые → хранятся разницы (delta-of-delta для времени, XOR для значений, алгоритм Gorilla). В среднем **~1.3 байта на точку**.
* **Запись** — только добавление в конец: сначала в память и WAL, потом блоками по 2 часа на диск.
* **Блоки по времени** — запрос за последний час читает только нужные блоки; старые данные удаляются целыми блоками.
* **Инвертированный индекс по лейблам** — быстро находит ряды по фильтру `{service="api", code="500"}`.
* Pull-модель и простота: один бинарник, без внешних зависимостей.

Ограничение: долго хранить и масштабировать горизонтально не умеет — для этого Thanos, Mimir, VictoriaMetrics.

### 7. Чем отличается 90-й перцентиль от 95-го? {gen}

**N-й перцентиль** — значение, быстрее которого выполняются N% запросов.

* **p90 = 200 мс** — 90% запросов быстрее 200 мс, 10% медленнее.
* **p95 = 350 мс** — 95% быстрее 350 мс, только 5% медленнее.

p95 всегда ≥ p90: он смотрит глубже в «хвост» медленных запросов. Чем выше перцентиль (p99, p99.9), тем лучше видны редкие, но болезненные задержки.

Почему не среднее: среднее прячет хвост. При 1000 RPS 1% медленных запросов — это 10 расстроенных пользователей **каждую секунду**.

### 8. Что такое структурированные логи и зачем они лучше, чем plain text? {gen}

**Структурированный лог** — запись в формате ключ-значение (обычно JSON), а не просто строка.

```
plain:       2026-05-01 12:00 ERROR failed to pay order 42 for user 7
structured:  {"time":"...","level":"ERROR","msg":"payment failed","order_id":42,"user_id":7,"trace_id":"abc"}
```

**Почему лучше:**
* **поиск и фильтрация** по полям: `order_id=42 AND level=ERROR` — без хрупких регулярок;
* машиночитаемы — легко разбирать в ELK / Loki, строить графики;
* единый формат во всех сервисах;
* легко связать с трейсом по `trace_id`.

В Go — стандартный `log/slog`:

```go
slog.Error("payment failed", "order_id", 42, "user_id", 7)
```

---

### 9. Какие обязательные поля стоит включать в лог? {gen}

* `time` — время в UTC, формат ISO 8601;
* `level` — уровень;
* `msg` — короткое неизменное сообщение («payment failed», без переменных внутри);
* `service`, `version`, `env` — какой сервис, какая версия, какое окружение;
* `trace_id`, `span_id` / `request_id` — связать с трейсом и запросом;
* контекст операции — `user_id`, `order_id`, метод и путь;
* `error` — текст ошибки, для ERROR — stack trace.

**Нельзя** писать пароли, токены, номера карт и персональные данные.

### 10. Уровни логирования {gen}

* **DEBUG** — подробности для разработки. В проде обычно выключен.
* **INFO** — нормальные значимые события: сервис запущен, заказ создан.
* **WARN** — что-то не так, но работаем: ретрай, деградация, близко к лимиту.
* **ERROR** — операция не выполнена, нужна реакция.
* **FATAL** — приложение не может работать и завершается.

Уровень задаётся конфигом без пересборки. Правило: на ERROR должно быть не стыдно разбудить дежурного; если ошибки «нормальные» и их игнорируют — это не ERROR.

### 11. Какие инструменты для логирования знаешь? (DataDog, Graylog, ELK, etc) {gen}

**Сбор и доставка:** Fluent Bit, Fluentd, Vector, Filebeat, Logstash, OpenTelemetry Collector.

**Хранение и поиск:**
* **ELK / EFK** (Elasticsearch + Logstash/Fluentd + Kibana) — мощный полнотекстовый поиск, но дорогой по ресурсам.
* **Grafana Loki** — индексирует только лейблы, а не текст — дешевле, хорошо дружит с Grafana и Prometheus.
* **Graylog** — self-hosted, удобные стримы и алерты.
* **ClickHouse** — для очень больших объёмов логов.

**SaaS:** Datadog, Splunk, New Relic, Sentry (ошибки), облачные — CloudWatch, Google Cloud Logging.

**В Go:** `log/slog` (stdlib), `zap`, `zerolog`.

### 12. Что такое distributed tracing и зачем он нужен? {gen}

**Distributed tracing** — отслеживание одного запроса через **все сервисы**, которые он затронул: API → auth → orders → БД → Kafka → payments.

Каждый сервис передаёт дальше идентификатор трейса (заголовок `traceparent`, стандарт W3C), и в итоге получается одна картина: какой сервис вызван, в каком порядке, сколько занял каждый шаг, где ошибка.

**Зачем:**
* найти, **где именно** медленно, когда задействовано 10 сервисов;
* увидеть причину ошибки в цепочке вызовов;
* понять реальные зависимости между сервисами;
* связать логи разных сервисов по `trace_id`.

Инструменты: OpenTelemetry (стандарт сбора) + Jaeger, Grafana Tempo, Zipkin, Datadog APM.

### 13. Что такое span и trace? {gen}

* **Trace** — весь путь одного запроса через систему. Имеет уникальный `trace_id`.
* **Span** — одна операция внутри трейса: HTTP-вызов, SQL-запрос, публикация в Kafka. У span есть имя, время начала и длительность, атрибуты (`http.status_code`, `db.statement`), статус и `parent_span_id`.

Спаны образуют **дерево**: трейс — это дерево спанов.

```
trace abc123                               [========= 420ms =========]
 ├─ span: GET /orders (api)                [========= 420ms =========]
 │   ├─ span: auth.Check (grpc)            [= 30ms =]
 │   └─ span: SELECT orders (postgres)              [==== 350ms ====]  ← тут проблема
```

### 14. Как добавить OpenTelemetry в микросервис? {gen}

1. **Подключить SDK** и настроить экспортёр + TracerProvider при старте.
2. **Инструментировать** входящие и исходящие вызовы готовыми обёртками (`otelhttp`, `otelgrpc`, драйверы БД) — они сами создают спаны и передают контекст.
3. **Свои спаны** — для важной бизнес-логики.
4. **Передавать `context.Context`** везде — через него спан связывается с родителем.

```go
exp, _ := otlptracegrpc.New(ctx) // адрес из OTEL_EXPORTER_OTLP_ENDPOINT
tp := sdktrace.NewTracerProvider(
    sdktrace.WithBatcher(exp),
    sdktrace.WithResource(resource.NewSchemaless(
        semconv.ServiceName("orders"))),
)
otel.SetTracerProvider(tp)
otel.SetTextMapPropagator(propagation.TraceContext{})
defer tp.Shutdown(ctx)

// входящие HTTP-запросы
http.Handle("/orders", otelhttp.NewHandler(h, "orders"))

// свой спан
ctx, span := otel.Tracer("orders").Start(ctx, "CalculatePrice")
defer span.End()
```

В проде ещё настраивают **sampling** (например, 10% трейсов), чтобы не платить за каждый запрос.

### 15. Как подключить OTLP exporter и куда он может слать данные? {gen}

**OTLP** (OpenTelemetry Protocol) — стандартный протокол передачи трейсов, метрик и логов. Работает по **gRPC (порт 4317)** или **HTTP (4318)**.

**Подключение** — создать экспортёр и передать его в provider (см. предыдущий вопрос). Адрес удобнее задавать переменными окружения, без изменения кода:

```bash
OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4317
OTEL_SERVICE_NAME=orders
OTEL_TRACES_SAMPLER=parentbased_traceidratio
OTEL_TRACES_SAMPLER_ARG=0.1
```

**Куда слать:**
* обычно — в **OpenTelemetry Collector**: он принимает данные, батчит, фильтрует, семплирует и раскидывает по бэкендам. Сервис при этом не знает, где хранится телеметрия;
* или напрямую в бэкенд с поддержкой OTLP: **Jaeger**, **Grafana Tempo** (трейсы), **Prometheus / Mimir** (метрики), **Loki** (логи), **Datadog**, **Honeycomb**, **New Relic**, **Elastic**.

Collector — рекомендуемый вариант: сменить бэкенд можно, не трогая сервисы.
