# Брокеры сообщений

### 1. Kafka vs RabbitMQ vs NATS {gen}

| | Kafka | RabbitMQ | NATS |
|---|---|---|---|
| Модель | распределённый **лог** | **очередь** с маршрутизацией | лёгкий pub/sub |
| Что с сообщением после чтения | хранится по retention, можно перечитать | удаляется после ack | core — не хранится; JetStream — хранится |
| Пропускная способность | очень высокая (млн/с) | средняя (десятки тысяч/с) | очень высокая, минимальная задержка |
| Порядок | внутри партиции | внутри очереди | внутри subject (JetStream) |
| Маршрутизация | по топику и ключу | гибкая: exchanges, routing keys | subjects с wildcards |

**Когда что:**
* **Kafka** — event streaming, большие объёмы, нужно перечитывать историю, event sourcing, аналитика.
* **RabbitMQ** — очереди задач, сложная маршрутизация, приоритеты, отложенные сообщения.
* **NATS** — быстрая связь между сервисами, request-reply, IoT, когда простота важнее гарантий.

### 2. Как устроена кафка? producers, consumers, brokers, partitions, topics, consumer groups, consumer lag {gen}

* **Broker** — сервер Kafka; несколько брокеров = кластер.
* **Topic** — логическая категория сообщений (`orders`).
* **Partition** — топик делится на партиции; каждая — упорядоченный append-only лог. Партиции — единица параллелизма и масштабирования. У каждой есть leader и реплики на других брокерах.
* **Producer** — пишет сообщения. Партицию выбирает по ключу (`hash(key) % N`): одинаковый ключ → одна партиция → сохраняется порядок.
* **Consumer** — читает сообщения и хранит позицию (**offset**).
* **Consumer group** — группа консьюмеров делит партиции между собой: одну партицию читает ровно один консьюмер группы. Разные группы читают топик независимо.
* **Consumer lag** — сколько сообщений записано, но ещё не прочитано группой (`последний offset − закоммиченный`). Растущий лаг — консьюмеры не успевают.

Координацию кластера раньше делал ZooKeeper, сейчас — встроенный **KRaft**.

### 3. Гарантии доставки в кафка на продюсере и консумере. Как достичь? {gen}

Три уровня: **at-most-once** (можно потерять), **at-least-once** (возможны дубли), **exactly-once**.

**Продюсер:**
* `acks=all` — запись подтверждается, когда её получили все in-sync реплики (плюс `min.insync.replicas=2`).
* `retries` + `enable.idempotence=true` — повтор при ошибке без дублей.

**Консьюмер:**
* At-most-once — коммит offset'а **до** обработки.
* At-least-once — коммит **после** обработки (`enable.auto.commit=false`). Самый частый вариант.
* Exactly-once — Kafka-транзакции (`transactional.id`, `isolation.level=read_committed`) для схемы «прочитал → записал в Kafka».

На практике: **at-least-once + идемпотентный обработчик** (дедупликация по id сообщения в БД). Если результат пишется во внешнюю БД, exactly-once от Kafka не спасает — нужна идемпотентность на своей стороне.

### 4. Как обеспечивается горизонтальное масштабирование консюмеров? {gen}

Через **consumer group**: партиции топика распределяются между консьюмерами группы. Добавили консьюмера — произошёл **rebalance**, и часть партиций перешла к нему.

Ограничение: **консьюмеров в группе больше, чем партиций, — бессмысленно**: лишние будут простаивать. Поэтому число партиций закладывают с запасом.

```
Топик: 6 партиций
2 консьюмера → по 3 партиции
6 консьюмеров → по 1
8 консьюмеров → 2 простаивают
```

Если обработка тяжёлая, а партиций мало — параллелят внутри консьюмера (пул воркеров), но так, чтобы сохранить порядок для одного ключа.

### 5. Что такое offset и как им управлять? {gen}

**Offset** — порядковый номер сообщения внутри партиции. Консьюмер-группа хранит последний обработанный offset в служебном топике `__consumer_offsets` — отсюда продолжит чтение после рестарта.

**Управление:**
* **Auto commit** (`enable.auto.commit=true`) — коммит по таймеру. Просто, но можно потерять или продублировать сообщения.
* **Manual commit** — коммитим сами после обработки: синхронно (`CommitSync`) или асинхронно.
* `auto.offset.reset` — откуда читать, если offset'а нет: `earliest` (с начала) или `latest` (только новые).
* Ручной сдвиг — перечитать историю или пропустить битые сообщения:

```bash
kafka-consumer-groups --group billing --topic orders \
  --reset-offsets --to-datetime 2026-01-01T00:00:00.000 --execute
```

### 6. Когда использовать queue-based брокеры (RabbitMQ) и когда log-based (Kafka)? {gen}

**Queue-based (RabbitMQ)** — сообщение = задача, которую нужно выполнить один раз и забыть:
* фоновые задачи (отправить письмо, сгенерировать отчёт);
* сложная маршрутизация, приоритеты, отложенные сообщения;
* умеренная нагрузка.

**Log-based (Kafka)** — сообщение = событие, которое могут читать многие и в любое время:
* много независимых потребителей одного потока;
* нужно перечитать историю (replay, новый сервис, исправили баг);
* огромные объёмы, event sourcing, стриминг, аналитика;
* важен строгий порядок по ключу.

Коротко: **«сделай работу» → очередь, «вот что произошло» → лог.**

### 7. Что такое backpressure и как брокеры его решают? {gen}

**Backpressure** — ситуация, когда производитель шлёт данные быстрее, чем потребитель успевает обрабатывать. Без контроля растёт память, задержки, система падает.

**Как решают брокеры:**
* **Kafka** — pull-модель: консьюмер сам забирает данные со своей скоростью, сообщения просто копятся на диске (растёт lag). Продюсер ограничен буфером (`buffer.memory`, блокировка на `send`).
* **RabbitMQ** — `prefetch` (QoS): сколько неподтверждённых сообщений можно выдать консьюмеру; при переполнении памяти или диска брокер блокирует продюсеров (flow control).
* **NATS JetStream** — `MaxAckPending`, pull-консьюмеры.

На стороне приложения — ограниченные буферы и пулы воркеров, rate limiting, автоскейлинг консьюмеров по лагу.

### 8. Транзакции в брокерах {gen}

* **Kafka** — транзакции позволяют атомарно записать в несколько топиков/партиций и закоммитить offset'ы: схема «прочитал → обработал → записал» превращается в exactly-once. Консьюмеры с `isolation.level=read_committed` не видят незакоммиченные сообщения.
* **RabbitMQ** — `tx`-режим есть, но медленный; вместо него используют **publisher confirms**.

**Главная проблема** — атомарно записать и в БД, и в брокер. Распределённой транзакции между ними нет. Решение — **Transactional Outbox**:

1. В одной транзакции БД пишем данные и запись в таблицу `outbox`.
2. Отдельный процесс (или CDC, например Debezium) читает `outbox` и публикует в брокер.
3. Доставка — at-least-once, поэтому консьюмеры идемпотентны.

### 9. Чем отличается ack от nack? {gen}

* **ack** — «обработал успешно»: брокер удаляет сообщение из очереди.
* **nack** (в RabbitMQ — `basic.nack` / `basic.reject`) — «обработать не смог»:
  * `requeue=true` — вернуть в очередь и попробовать снова;
  * `requeue=false` — выбросить или отправить в **DLQ** (если она настроена).

Если консьюмер упал, не отправив ни ack, ни nack, сообщение вернётся в очередь и уйдёт другому консьюмеру.

Ловушка: `nack` с `requeue=true` для «ядовитого» сообщения создаёт бесконечный цикл. Поэтому считают попытки и после N отправляют в DLQ.

В Kafka ack/nack нет — роль ack играет коммит offset'а.

### 10. Что такое quorum queues (в RabbitMQ) {gen}

**Quorum queue** — тип очереди в RabbitMQ, реплицированный на несколько узлов по алгоритму **Raft**. Сообщение подтверждается, когда его записало **большинство** узлов.

* Переживает падение узла без потери данных (из 3 узлов — падение 1, из 5 — 2).
* Замена устаревших classic mirrored queues: надёжнее и предсказуемее при сбоях.
* Встроенный счётчик доставок: `x-delivery-limit` — после N неудачных попыток сообщение уходит в DLQ.
* Минусы: медленнее classic-очереди, больше расход диска и памяти, нет некоторых фич (например, приоритетов в старых версиях).

Использовать там, где важна надёжность, а не максимальная скорость.

### 11. DLQ в разных брокерах {gen}

**DLQ (Dead Letter Queue)** — отдельная очередь для сообщений, которые не удалось обработать. Чтобы одно «ядовитое» сообщение не блокировало остальные и не потерялось.

* **RabbitMQ** — встроено: очереди задают `x-dead-letter-exchange`. Сообщение уходит туда после `nack` без requeue, истечения TTL, переполнения очереди или превышения `x-delivery-limit`.
* **Kafka** — встроенной DLQ нет. Делается вручную: после N неудачных попыток консьюмер пишет сообщение в отдельный топик `orders.DLQ` (часто с промежуточными retry-топиками с задержкой). В Kafka Connect — есть настройка.
* **AWS SQS** — встроено: redrive policy с `maxReceiveCount`.
* **NATS JetStream** — `MaxDeliver` + advisory-события.

Важно: DLQ мониторить (алерт на рост) и иметь способ переотправить сообщения после исправления бага.

### 12. Как мониторить состояние брокеров (метрики, лаги консюмеров, задержки) {gen}

**Ключевые метрики:**
* **Consumer lag** — главная: растёт → консьюмеры не успевают.
* **Throughput** — сообщений/байт в секунду на вход и выход.
* **Latency** — время от публикации до обработки, время запроса продюсера.
* **Kafka:** under-replicated partitions, offline partitions, active controller count, ISR shrink/expand.
* **RabbitMQ:** длина очередей, unacked messages, число консьюмеров, memory/disk alarms.
* Ресурсы: диск, сеть, CPU, GC брокеров.

**Инструменты:** Prometheus + Grafana (JMX exporter, kafka-exporter, встроенный плагин RabbitMQ), Burrow для лагов, Kafka UI / AKHQ, RabbitMQ Management UI.

**Алерты:** лаг выше порога и растёт, under-replicated partitions > 0, переполнение очереди, рост DLQ.

### 13. Какие типичные проблемы бывают при использовании Kafka в продакшене? {gen}

* **Растущий consumer lag** — медленная обработка или мало партиций.
* **Частые rebalance** — консьюмер не успевает вызвать `poll` за `max.poll.interval.ms`, его выкидывают из группы; во время rebalance чтение стоит.
* **Дубли** — at-least-once без идемпотентного обработчика.
* **Нарушение порядка** — неправильный ключ партиционирования или ретраи без идемпотентного продюсера.
* **Горячие партиции** — неравномерный ключ, один консьюмер перегружен.
* **Потеря сообщений** — `acks=1`, `min.insync.replicas=1`, `unclean.leader.election=true`.
* **Ядовитое сообщение** — консьюмер падает на одном и том же сообщении; нужна DLQ.
* **Ломающая смена формата** сообщений — нужен Schema Registry.
* **Переполнение диска** — неправильный retention.

### 14. Как организовать схему сообщений (Avro, Protobuf, JSON Schema)? {gen}

Схема — это **контракт** между продюсером и консьюмерами. Без неё любое изменение поля может сломать чужой сервис.

| | Avro | Protobuf | JSON Schema |
|---|---|---|---|
| Формат | бинарный, компактный | бинарный, компактный | текстовый JSON |
| Скорость | высокая | высокая | ниже |
| Читаемость | нет | нет | да |
| Где популярен | экосистема Kafka | gRPC, Go | простые интеграции |

**Schema Registry** (Confluent, Apicurio) хранит версии схем и проверяет **совместимость** при публикации.

**Правила эволюции:**
* новые поля — только опциональные / с значением по умолчанию;
* не удалять и не переиспользовать номера полей (Protobuf);
* не менять тип поля;
* режим совместимости `BACKWARD` — новые консьюмеры читают старые сообщения.

### 15. Какие есть альтернативы брокеру сообщений в event-driven архитектуре? {gen}

* **Transactional outbox + polling** — события в таблице БД, потребители опрашивают её. Без отдельной инфраструктуры.
* **CDC** (Change Data Capture, Debezium) — события берутся прямо из журнала БД (WAL / binlog).
* **Postgres `LISTEN/NOTIFY`** — простые уведомления внутри одной БД.
* **Redis Streams / Pub/Sub** — лёгкая очередь, если Redis уже есть.
* **Облачные сервисы** — AWS SNS/SQS, EventBridge, Google Pub/Sub — без своей инфраструктуры.
* **Webhooks** — прямые HTTP-вызовы подписчиков.
* **Workflow-движки** (Temporal) — для долгих бизнес-процессов вместо цепочки событий.

Выбор зависит от объёма: на малой нагрузке outbox + polling часто проще, чем поддерживать Kafka.

### 16. У нас 1 млн событий в минуту, как построить систему на Kafka/RabbitMQ? {gen}

**1 млн/мин ≈ 17 тыс. событий/сек.** Для Kafka это умеренная нагрузка, RabbitMQ тоже справится, но выбираю **Kafka**: запас по пропускной способности, хранение, replay.

**Кластер:** 3+ брокера, `replication.factor=3`, `min.insync.replicas=2`.

**Партиции:** считаем от скорости консьюмера. Если один обрабатывает 1000 событий/сек → нужно ≥17 консьюмеров → берём **32–48 партиций** с запасом на рост.

**Продюсер:**
* `acks=all`, `enable.idempotence=true`;
* батчинг: `linger.ms=5–20`, `batch.size`, сжатие `lz4` / `zstd`;
* ключ — по сущности (`user_id`), чтобы сохранить порядок.

**Консьюмеры:**
* consumer group, число инстансов ≤ числа партиций, автоскейлинг по лагу (KEDA);
* обработка батчами, батчевая запись в БД;
* ручной коммит после обработки + идемпотентность;
* retry-топики и DLQ.

**Остальное:** Schema Registry, retention под требования replay, мониторинг лага и under-replicated partitions, нагрузочный тест на x2–x3 от пика.
